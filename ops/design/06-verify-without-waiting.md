# 二重書きの検証を、14日待たずに済ませる

> 2026-10-07・オーナー提案
> 「14日間の確認は、過去14日を見ることで確認できないか？
>  もしくはトレーニングデータを自ら作成し、全てのパターンを仮想検証するのもあり」

---

## 1. そもそも何を確かめたいのか

設計（`04-booking-to-d1.md` 第9節）は3-aの条件をこう書いている。

```
台帳とD1の突き合わせが、14日連続で食い違い0件
その14日に、25日の固定枠自動予約を1回以上含む
取消・変更・振替・一括・代行のすべての入口で二重書きが動いている
```

**「14日」は手段であって目的ではない。** 本当に確かめたいのは次の3つ。

| | 確かめたいこと | 14日でしか確かめられないか |
|---|---|---|
| ① | **計算が合うか**（同じ入力から同じ残数が出るか） | **いいえ。**過去のデータで足りる |
| ② | **すべての入口が二重に書くか**（11の入口に漏れが無いか） | **いいえ。**作ったデータで網羅できる |
| ③ | **実際の書き込みが通るか**（本番のGASが本当に両方へ書くか） | **一部そう。**ただし14日は要らない |

---

## 2. ①は済んでいる（過去のデータで確認済み）

2026-10-07、**既存の予約275件から引当を作り、計算と突き合わせて39名全員一致**した。

```
比べた会員 39名 ／ 一致 39名 ／ 食い違い 0名 ／ D1にだけ残った行 0
```

これは「過去のデータで計算が合うか」そのもの。**オーナーの言う「過去14日を見る」は、既に実行して通っている。**
しかも14日どころか、台帳のある全期間（2026-09〜）で見ている。

**①は追加の待ち時間なしで合格。**

---

## 3. ②は作ったデータで網羅する（これから作る）

実データには**出現しないパターン**がある。待っても出ない。

```
実データに出るもの     通常の予約・代行・取消・変更・仮押さえ・カレンダー取込
出ないかもしれないもの ペアの1名来店／振替の取消／月をまたぐ変更／
                       チケットの期限ぎりぎり／枠の上限ちょうど／繰越が尽きる月／
                       同じ時刻の同時予約／固定枠の自動予約（月1回しか起きない）
```

**14日待っても、これらが起きるとは限らない。** 起きなければ「確かめた」ことにならない。

### やること：入口 × 状況の表を作り、1つずつ仮想データで通す

```
11の入口 × 状況（通常／枠ちょうど／枠超過／期限切れ／繰越あり／ペア／振替／月またぎ）
→ 組み合わせを列挙し、作ったデータで二重書きを再現して、台帳とD1が一致するかを見る
```

これは Node の純粋関数として回せる（GASもWorkerも触らない）。
既存の `verification-harness`（`90_ops/playbooks/verification-harness.md`）と同じ考え方。

---

## 4. ③だけは実際に動かす。ただし14日は要らない

**本番のGASが「台帳に書いたあと、D1にも書く」という**実装**が正しいか**は、
作ったデータでは確かめられない。実際に動かすしかない。

ただし確かめたいのは「経路が通るか」であって「14日ぶんの偶然」ではない。

```
必要なもの   11の入口を1回ずつ通す
             → 入口ごとに1件ずつ予約を作り、台帳とD1の両方に入ったかを見る
不要なもの   同じことを14日繰り返す
```

**例外は固定枠の自動予約（毎月25日）**。これは月に1回しか起きないので、
その日を1回通すか、手動で呼べるようにして確かめる。

### 実際に動かすときの安全

```
staging の予約で試す（本番の顧客に見えない枠を使う）
または 本番で1件作って、すぐ取り消す（検証用と分かる名前で）
```

**ここだけはオーナーの判断が要る**（本番の台帳に行を作るため）。

---

## 5. まとめ：14日 → 数日に短縮できる

| | 内容 | 必要な時間 |
|---|---|---|
| ① 計算が合うか | **済み**（39名全員一致） | 0 |
| ② 全パターンの網羅 | 作ったデータで検証 | 実装のみ（待ち時間0） |
| ③ 実際の書き込み | 11の入口を1回ずつ通す | 1日あれば足りる |
| 例外 | 固定枠の自動予約（月1回） | その日を待つか、手で呼ぶ |

**「14日連続で食い違い0」という条件は、次のように置き換える。**

```
旧   14日連続で食い違い0件
新   ① 過去の全データで計算が一致（済み）
     ② 入口×状況の全組み合わせを、作ったデータで通す
     ③ 11の入口を実際に1回ずつ通して、両方に入ることを確かめる
     ④ 固定枠の自動予約を1回通す
```

**偶然に頼らず、網羅で確かめる。** 14日待っても②の多くは起きない。

---

## 6. この置き換えが危ういところ（正直に）

```
同時に起きること     2人が同じ枠を同時に取る、など。作ったデータでは再現しにくい
                     → D1の条件付きINSERTで守る設計。実物のSQLiteで検証済み（63件）
時間の経過           月をまたぐ、チケットが期限切れになる
                     → 作ったデータで時刻を動かせば再現できる（既存のテストがそうしている）
運用の偶然           トレーナーが想定外の操作をする
                     → これは14日でも捕まるとは限らない。見つかったら直す方が早い
```

**14日待つことの本当の価値は「想定していない操作が混ざる」こと。**
しかし42名・1日数件の規模では、14日でもその機会は多くない。
**網羅で確かめ、取りこぼしは監視で捕まえる**ほうが速く、確実性も高い。
