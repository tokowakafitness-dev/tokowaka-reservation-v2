## 1. いまの給与計算の弱点（1つに集約される）

```
会計の正しさが「カレンダーの手入力の表記」に依存している
```

`billing.gs` の `_parseEventTitle` が、イベント名を `_` で区切って
**種別・担当名・顧客名**を読む。顧客は**氏名の文字列**でマスタと照合する。

| | 症状 | 実例（記録に残っているもの） |
|---|---|---|
| ① | 命名規約の逸脱で**会計に載らない** | 2026-08、`【振替】通常_鈴木_小倉滉太様` を診断で発見。**売上¥5,500・報酬¥1,000が消えたまま7月を締めるところだった** |
| ② | マスタとの照合が氏名の文字列 | 種別違い・契約期間外で**単価0・報酬0**のまま静かに通る（`ミウ`／`中野龍之介様` が実例） |
| ③ | 毎月オーナーが診断して直す | `diagnoseBeforeClose()` が0になるまで締められない |

★`billing/memory.md` にすでに書いてある：
　「会計の正しさがカレンダーの手入力表記に依存している限り、この確認は続ける。
　**LINE予約が本稼働してCLOSED記録が正になれば、この経路は縮小する**」

## 2. D1が正本になると何が変わるか

```
いま   カレンダーのイベント名 → 文字列で種別・担当・顧客名を読む
あと   reservations（ID）
       ＋ reservation_allocations（どの枠／どのパックから引いたか）
       ＋ contracts（単価・報酬率）
       ＋ customers（ID）
```
**文字列の照合が、IDの結合に変わる。** ①②は構造的に消える。③の手間も消える。

---

## 3. ★「正式なものが出せるか」はここで決まる

D1から給与を出せるのは、**カレンダーの予定とD1の予約が1対1に対応しているとき**だけ。
対応が崩れる経路を、コードと実データから洗い出した。

| | 経路 | いまの実数 | どこで見えるか |
|---|---|---|---|
| A | **カレンダーにあって台帳に無い**（手入力の予定） | **1件**（10/10 13:30 森脇浩子様） | 日次点検の「手動作成（台帳に無い）」 |
| B | 台帳にあってカレンダーに無い（担当calの残骸） | **1件**（10/22 20:00 野崎天平様） | 日次点検の「担当calの残骸」 |
| C | 会員が特定できず未紐付け | **0件** | 日次点検の `resv_unlinked`（`line_unlinked` シート） |
| D | 台帳の範囲が9月から | — | `billing` はカレンダー（3月以降）、D1は台帳（9月以降） |

★**A・B・Cは既に日次点検で見えている。** 新しく作る必要がない。
★Dがあるため、**7月の正解（¥878,525・136件）とは照合できない**。照合できるのは9月以降。

## 4. 照合の手順（書き込みはしない）

```
① D1から9月の売上・報酬を計算する（Worker側・新しい窓口・読み取りだけ）
② billing が出した9月の数字を取る（★オーナーの操作が1回必要・下記）
③ 1円単位で突き合わせる
④ 差が出たら、第3節のA〜Dのどれかに必ず分類できるはず。分類できない差が
   残るなら、**まだ構造を変えてはいけない**
```

## 5. D1から計算するときの規則（①の中身）

```
対象の予約   reservations の status IN ('booked','consumed')
             ★語彙に注意（台帳 confirmed → D1 booked。MODEL.md §4）
振替         book_type='transfer' は枠を使わない。別の単価（店舗¥5,500／レンタル¥2,000）
消化先       reservation_allocations の source（monthly / ticket / pair / transfer）
単価・報酬率 contracts（unit_price / reward_rate）★顧客IDで結合する
ペアの人数   attendee_count（売上に直接かかる）
社内の予定   会計対象外（カレンダーにしか無い＝D1には最初から入らない）
```

★**ここで新しい計算を持ち込まない。** billing の規則をそのまま写す。
　違う答えが出たら、それは「構造を変えた」ではなく「間違えた」。

## 6. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 社内の予定（撮影・MT）はカレンダーにしか無い | 会計対象外なので差にならない。**ただし「差が0」の根拠として数える** |
| ② | HPB体験・入会金はカレンダーの命名で表す | D1に対応する列が無い。**第3節のAと同じ扱い**（差として出る） |
| ③ | 単価の改定が期中に起きる | `contracts` は履歴を持つ（start_date / end_date）。実施日で引く |
| ④ | マスタとD1の `customers` がずれている | IDで結合するので表記ゆれは消えるが、**マスタ側が真実の月もある** |
| ⑤ | 照合が一致しても、それは「その月だけ」 | 2か月（9月・10月）で一致を見る。1か月では足りない |

# ★第2版：調査で分かったこと（2026-10-09）

## 既に実装されている（作る必要がない）

```
lineSwitchForPeriod(monthKey, master)      billing.gs:2071
  LB_CUTOVER_MONTH が未設定 or cutover前  → { apply: false }（旧経路＝カレンダー）
  cutover以降                              → _lbBillComputeSwitch で載せ替え

_lbBillComputeSwitch                       billing.gs:2080
  ① lineSwitchData(monthKey)        載せ替えの準備ができているか
  ② _lbBillReadClosed(monthKey)     ★pt-gas の line_allocations から
                                      CLOSED の manifest 行を読む
  ③ _lbBillCloseCompleteness        当月のLINE予約で CLOSED 未収録＝部分締めを検知
  ④ _lbBuildLineInjectionRows       LINE予約から注入する行（売上・報酬）を作る
  → excludeEventIds（カレンダーから除外）＋ injectionRows（代わりに入れる）
```
検証用の関数まで揃っている：
```
lineSwitchData(monthKey)          準備の状態と、除外件数・売上・報酬・issues を出す
lineRevenueShadow(monthKey)       ★shadow 検証（旧経路と新経路を比べる）
testLineSwitchDataJuly()          引数なしのラッパ（GASエディタのRunボタン用）
```

★**オーナーの「構造は換えてもいい」に対して、構造を換える必要はない。**
　用意された切り替えを有効にするだけ。

## ★本当のブロッカー：締めが一度も実行されていない

```
_lbBillReadClosed が返す理由
  NO_ALLOC                 line_allocations シートが無い／空
  ★NOT_CLOSED              CLOSED の manifest 行が無い ← **いまここ**
  AMBIGUOUS_RUN            CLOSED が2つ以上
  LOGIC_VERSION_MISMATCH   締めのロジック版が受理集合に無い
  PAYLOAD_CORRUPT          detail の中身が壊れている
```
つまり**給与計算をD1の記録ベースにする前提は、pt-gas 側で月次の締めを1回通すこと。**

★**いまの給与計算は健全。** 移行は「壊れているから」ではなく**手間と脆さを消すため**。

## 新しい順序

```
1. shadow のベースライン（段階3-b を終わらせる）        ← いまここ
2. pt-gas 側で月次の締めを1回通す（★CLOSED記録ができる）
     ★締めは不可逆な記録を作る＝第3節の承認事項
     ★締めが読む引当は3-bで触っている土台そのもの。**3-bの後に**
3. billing で lineSwitchData('2026-XX') を実行し ready を確かめる
     ready でなければ理由コードが出る（上の一覧）
4. lineRevenueShadow で旧経路と新経路を突き合わせる（★既にある仕組み）
5. 一致したら LB_CUTOVER_MONTH を設定して載せ替える
```
★第1版で書いた「D1から新しく計算を作る」は不要になった。
　4が「正式なものが出せるか」の証明そのもの。

## 第1版から残すもの（なお有効）

  実データでは **A=1件（10/10 森脇浩子様）／B=1件（10/22 野崎天平様の残骸）／C=0件**
- 検証用の会員はマスタに残す（2026-10-09 オーナー判断・単価0で会計に影響しない）
