# 設計71（下書き）：顧客名簿の検索をひらがなでも当てる

状態：**確定（2026-11-28 オーナー回答）＝A＋B**。根拠は origin/main dd16400（2026-11-28）。

## 0. 目的（1行）
トレーナー画面の「顧客名で検索…」に、ひらがな（読み）を入れても該当のお客様が残るようにする。

## 1. いまの仕組み（事実）
- 顧客の名前で探す欄は **1つだけ**：`liff/index.html` `renderCustomerList()` の `_search`（1943行）。カルテ・代行予約・管理はこの一覧から入る。
  - 他の入力欄（カルテの「種目を探す」・未紐付けの「会員を選択…」のプルダウン）は名前検索ではない。
- 一致の仕方（1952行）：`q = 入力.trim().toLowerCase()` を `name.toLowerCase().indexOf(q)` で**部分一致**。
  - 空白を詰めない（「山田 太郎」に「山田太郎」は当たらない）／全角半角・ひらがなカタカナを同一視しない／**読みを持っていない**。
- 一覧の元：`line_getTrainerReservations` の `customers`（`{customerId, name}` だけ）。経路は2本で同じ形。
  - GAS：`getTrainerReservations`→`_lbTrainerCustomers`／`_lbAllVerifiedCustomers`（`customer_line_map` の C列 NAME）
  - Worker：`compatTrainerReservations`（`worker/src/routes/compat.js`。D1 `customers.name`）
- 読みのデータ：
  - D1 `customers.kana` 列は**ある**が、押し出し（`gas/PushToEdge.js` 249行）が常に `kana: ''`＝**全員空**。
  - `customer_line_map` に読みの列は**無い**（MAP_COL A〜Q）。
  - 契約フォーム（顧客マスタ「フォームの回答 1」）を読む `_lbContractCols` は読みの列を見ていない。**フォームにフリガナの設問があるかは未確認**。
  - 会員登録の入力は「お名前（契約時のお名前）」1つだけ（`liff/index.html` 281行）。
- 既に `customers.kana` を読んでいる所（いまは空なので効いていない）：
  - `worker/src/routes/karte-ai.js` 375行：カルテの AI へ送る前に会員の名前を伏せる処理（読みも伏せる）
  - `worker/src/routes/boot.js`：一覧の並び `ORDER BY upcoming DESC, c.kana`
  → 読みを入れると**この2つの動きも変わる**（伏せる範囲が増える＝安全側／並び順が読み順になる）。

## 2. 案
| | A 画面だけで表記ゆれを畳む | B 名簿に読みの列を足して検索に使う | C 読みを名前から自動で推定 |
|---|---|---|---|
| できること | 空白・全角半角・ひらがな⇄カタカナを同一視。名前がかな書きの会員はひらがなで当たる | 読みが入っている会員はひらがなでもカタカナでも当たる | 全員に読みが付く |
| できないこと | **漢字の名前はひらがなで当たらない**（今回の要望の本体は満たさない） | 読みが空の会員は今までどおり（漢字でしか当たらない） | 人名の読みは誤りが多い（「中野」なかの/なかや 等）。辞書が数MB で LIFF が重くなる |
| 触る場所 | `liff/index.html` のみ | 名簿（`customer_line_map` に見出し `kana` の列）・GAS 2関数と押し出し・Worker compat・画面 | 画面（辞書の読み込み） |
| GAS の反映 | 不要 | **要る（1回）** | 不要 |
| 個人情報 | 増えない | 読みが新しく D1 とレスポンスに載る。読める人は**今その名前が見えている人と同じ**（担当＋担当なし／オーナーは全員）。画面には出さず照合にだけ使う | 増えない |
| 手間 | なし | 読みを入れる人の手間（既存の会員の人数ぶん・件数は要確認） | なし |

（B の補足）読みの置き場所は、トレーナーの読みと同じく**見出しが `kana` の列を探して読む**（列番号を固定しない＝MAP_COL を動かさない）。値は `_edgeTrainerKana` と同じ規則（かな・長音・中黒・空白だけ・40字まで、それ以外は空）。
（B の拡張・別案）トレーナーが画面から読みを入れる欄：書き込みの経路（GAS の新しい操作・権限の判定）が増えるので、最初は入れない。

## 5. 確定した設計
- 正本：名簿の見出し `kana` の列（R 以降だけ。A〜Q は MAP_COL の列なので見出しが kana でも読まない）。列の位置は決め打ちしない
- 値の規則：`_edgeTrainerKana`（かな・長音・中黒・空白だけ・1〜40字・NFKC）。外れたら空文字＝照合に使わない（判定できないときは今の動き）
- 書く側：`_edgeCustomers`（押し出し）の `kana` を '' から名簿の値へ。`customers` は残数の計算の入力ではない（QUOTA_INPUT_KINDS の外）＝世代は動かない
- 読む側：GAS `_lbTrainerCustomers`・`_lbAllVerifiedCustomers` と Worker `compatTrainerReservations` の `customers` に `kana`（必ず文字列）。**同じ会員に同じ値**
- 画面：`_custSearchKey`（NFKC→小文字→空白・中黒を詰める→ひらがなをカタカナへ）で、名前と読みの両方に部分一致。読みは表示しない
- 個人情報：読みの値が載るのは次の4か所。どれも見える人は今その名前が見えている人と同じ（担当＋担当なし／オーナーは全員。boot・customer は perms.js の範囲）
  1. D1 `customers.kana`（押し出し）
  2. トレーナー一覧の応答（GAS getTrainerReservations・Worker compatTrainerReservations）＝画面の検索に使う
  3. Worker `boot` のトレーナー向け customers・`customer`（顧客詳細）＝鍵は前からあり、今は全員空。値が入り始める。画面はどちらも読みを表示しない（今回は応答から落とさない＝契約を変えない）
  4. k_aiDraft：伏せる対象にだけ使う（外へは送らない）
- 副作用（読みを入れた後）：①k_aiDraft が会員の読みも伏せて送る。★ただし伏せる処理は読み全体を単語の境目なしに置き換えるので、**かなが2字以上の読みだけ**使う（`isMaskableKana`・1字の「あ」で文字起こしの「あ」が全部消えるのを防ぐ・関門① 高）②boot の一覧の並び `ORDER BY upcoming DESC, c.kana` が読み順になる（今の画面の一覧は getTrainerReservations を使うので影響なし）
- 既にある差（今回は変えない）：Worker の一覧は退会だけを外し、名簿の未照合（pending 等）の会員も出す。GAS は verified だけ。経路で一覧の人数が変わり得る（関門① 中・既存の差。読みの値は同じ会員なら一致する）
- 戻し方：名簿の kana の列を消す（または見出しを変える）＝全員空文字＝今の動き。コードを戻すなら PR を revert（GAS は次の反映で戻る）
