# ④ 予約の正本をD1へ移す（設計・第3版）

**目的**：予約の正本をスプレッドシートからD1へ移し、**「写しが古いかもしれない」という状態そのものを無くす。**

> 起草：2026-10-04／第2版：Codexの関門①で差し戻されたため全面改訂
> **第3版（2026-10-06）：決定0069でカレンダーの役割が変わったため改訂。**
> 決定0062（2026-09-30）の第3段。第1段（カレンダー→D1）と第2段（読み取りをWorkerへ）は完了済み。

> **第3版で何が変わったか**：「カレンダーは入力でもあり出力でもある」が「**B1は出力だけ**」になった。
> トレーナーにはB1の書き込み権限がすでに無い。この1点で設計の多くが単純になり、
> 代わりに「占有の2軸」と「B1を読んでいる2つ（請求・逆同期）の移行」が加わった。
> 詳細は第1節の「第2版からの変更」。

---

## 0. 第1版が差し戻された理由（ここから読む）

Codexの判定：

> ScriptLockが守っている「枠」だけを見ており、**同じLockが守っていた「残数」「変更」「振替」「全入口の直列化」を落としています。**

**私は「二重予約をどう防ぐか」ばかり考え、同じ鍵が他に何を守っていたかを見ていなかった。**

| 第1版の穴 | 何が起きるか |
|---|---|
| 重なりの検査とINSERTが原子的でない | 「空きを確かめる→書く」の間に他が入る。D1は対話型のトランザクションを持たない |
| **残数の同時予約を防げない** | 残り1回の会員が、別々の時刻に同時に2件取れる（枠は違うので一意制約に当たらない） |
| カレンダー照会が1種類だけ | いまのGASはB1・担当トレーナー・1Fの3つを見ている |
| 取消・変更・振替・固定枠・一括予約の移行が無い | 作成だけ移すと、取消が台帳だけを更新しD1は永遠に「予約あり」 |
| 後始末が「再試行」 | 予約を書いた直後にWorkerが止まると、後始末そのものが消える |
| 冪等性キーが無い | 応答が落ちて再送されると、二重になるか、顧客に区別がつかない |

**第2版の中心は「引当を行として記録する」こと。** これが残数の守りと、オーナーの「消化先を固定したい」を同時に満たす。

## 1. 結論（先に読むところ）

| # | 論点 | 結論 |
|---|---|---|
| ① | 二重予約 | **重なりの条件をINSERT文そのものに含める**（単一SQL）。**条件は2本**（施設・トレーナー）。一意制約は補助の砦 |
| ② | **残数の同時予約** | **枠を行にして、条件付きUPDATEで確保する**（`used < quota` のときだけ+1）。**ただし仮押さえは超えても作れる**（⑪） |
| ③ | **消化先** | **予約時に決めて行として記録し、以後変えない**（オーナー判断） |
| ④ | 消化先の既定 | **月額を先に使う**（オーナー判断）。顧客は選べる。**将来は自動で最適に割り当てる** |
| ⑤ | カレンダー照会 | **確定の瞬間の照会は要らなくなる**（⑫）。B1に人が書かないため |
| ⑥ | 後始末 | **予約と同じ書き込みで「やることリスト」を積む**（outbox）。再試行だけに頼らない |
| ⑦ | 冪等性 | すべての書き込みに**操作ID**を付ける。同じIDの再送には元の結果を返す |
| ⑧ | 移行の対象 | **作成だけでなく、取消・変更・振替・固定枠・一括・代行・外部取込のすべて**。**加えてB1を読んでいる2つ**（⑬） |
| ⑨ | 段階 | 3-a 二重書き（2週間）→ 3-b 読み取り切替 → 3-c 正本移行。**各段に進む条件を明文化** |
| ⑩ | 切り戻し | **受付を止める→処理中を待つ→やることリストを出し切る→戻す**。訓練で確かめる |
| ⑪ | **占有は2軸** | **施設とトレーナーは別々に埋まる**（決定0069）。オンラインはトレーナーだけ塞ぐ |
| ⑫ | **カレンダーの役割** | **B1は出力のみ・人は書かない。トレーナー個人はシフトの入力＋予約の出力。1Fは廃止**（決定0069） |
| ⑬ | **読み手の移行** | **`salonboard-sync` と `billing` もB1を読んでいる**。この2つをD1読みへ移すのも移行の対象 |

### 第2版からの変更（2026-10-06・決定0069）

**前提がひとつ変わった。「カレンダーは入力でもあり出力でもある」が、「B1は出力だけ」になった。**
トレーナーにはB1カレンダーの書き込み権限がすでに無い（権限で閉じ済み・確認済み）。

この1点で、第2版が抱えていた複雑さの多くが消える。

| 消えるもの | なぜ |
|---|---|
| 確定の瞬間のカレンダー照会（B1） | 人が書き込まないので、照会と書き込みの間に割り込む人間がいない |
| 「照会してから書く」の順序問題 | 同上。残るのはサロンボード経由のみ |
| 外部予約のループ防止 | B1が出力専用になれば循環が構造的に無い（移行期限定の仕掛けに格下げ） |
| 1Fの振り分け・同期・権限管理 | 「占有しない」は列で表せる。置き場所が要らない |
| `dailySync` による仮押さえの取り込み | D1に即記録されるので、超過が**その場で**見える（最大6時間の遅れが消える） |

逆に**増えるもの**が2つある。どちらも第2版には無かった。

- **占有の条件が2本になる**（施設・トレーナー）。オンラインはトレーナーだけ塞ぐ
- **B1を読んでいる2つの移行**（`salonboard-sync` と `billing`）。特に請求は売上に直結する

## 3. 中心の設計：引当を行として記録する

### なぜこれが要るか

いまはScriptLockが**4つのことを同時に守っている**。

| 守っているもの | D1に移すとどうなるか |
|---|---|
| 同じ枠を2人が取らない | 一意制約＋重なり条件で守れる（むしろ強くなる）。**ただし「枠」が2つに割れる**（下記） |
| **同じ人が残数を超えて取らない** | **守るものが無くなる** ← ここが第1版の穴 |
| 変更（旧を消して新を作る）が途中で止まらない | トランザクションで守る |
| すべての入口が1列に並ぶ | 行ごとの確保で置き換える。**並ぶべき入口は減る**（カレンダー直接入力と1Fの振り分けが消えるため） |

**2つ目を解くのが、引当を行にすることである。**

### 「枠」は2つある（2026-10-06・決定0069）

施設とトレーナーは**別々に埋まる**。第2版は `uses_room` ひとつで表そうとしていたが、それでは足りない。

| 種別 | 地下を占有 | トレーナーを占有 | 残数を使う |
|---|---|---|---|
| 通常・モニター | ✅ | ✅ | ✅ |
| **オンライン** | ❌ | ✅ | ✅ |
| 新規体験 | ✅ | ✅ | ❌（契約前） |
| 未登録客の仮押さえ | ✅ | ✅ | ❌（契約が無い） |
| 会員の仮押さえ（支払い前） | ✅ | ✅ | ✅ **超過になる** |

```
トレーナーの空き = 出勤 − そのトレーナーの予約（種類を問わず）
施設の空き       = 地下の定員（＝1） − occupies_facility が true の予約
```

**地下の定員は1**（`gas/LineBooking.js:4223` の `施設B1(capacity-1)` で確認）。
定員が1である限り、施設側は一意制約でも表せる。将来2以上にするなら集計を含む条件付きINSERTへ。

**オンラインかどうかは顧客（契約）の属性で決まる。** 予約ごとに選ぶのではない。
ただし**予約行に焼き込む**（契約が後で変わっても、過去の予約の占有が動かないようにするため）。

### 仮押さえは残数を超えても作れる（決定0068・0069）

第2版の確保処理は `used + 1 <= quota` で**超過を拒否**していた。これは運用と衝突する。

> 顧客から追加予約の希望がある。まだ支払いを受けていない。だから仮押さえとして枠を押さえる。

オーナーの判断は「**超過は防ぐものではなく、見せるもの**」（決定0068）。
残数チェックで止めると、この仮押さえができなくなる。

```
通常の予約（payment_status = paid）      → used + 1 <= quota のときだけ通す
仮押さえ（payment_status = unpaid）      → 枠を超えても作る。超過として記録し、画面に出す
```

超過の見え方は実装済み（「今月の残り −2回（超過2回：追加のお支払いが必要です）」）。
支払い後にチケットを足すとマイナスが消える。

**`payment_status` は将来の決済フローにそのまま繋がる。**
いまの運用（支払い前に押さえ、後でチケットを足す）と、将来の運用（顧客が先に決済する）が、
**同じ列の値の違い**になる。仕組みを作り直さずに移行できる。

### 枠を行にする

```sql
-- 月額の枠（会員×月）
CREATE TABLE monthly_quota (
  customer_id TEXT NOT NULL,
  month_key   TEXT NOT NULL,          -- '2026-10'
  quota       INTEGER NOT NULL,       -- 頻度＋繰越（契約から計算して入れる）
  used        INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (customer_id, month_key)
);

-- チケット（買った単位ごと）
CREATE TABLE ticket_packs (
  pack_id     TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL,
  kind        TEXT NOT NULL,          -- 'normal' | 'pair'
  total       INTEGER NOT NULL,
  used        INTEGER NOT NULL DEFAULT 0,
  valid_from  INTEGER NOT NULL,
  valid_to    INTEGER NOT NULL
);

-- 予約がどこから引いたか（★これが「固定」の正体）
CREATE TABLE reservation_allocations (
  reservation_id TEXT PRIMARY KEY,
  customer_id    TEXT NOT NULL,
  source         TEXT NOT NULL,       -- 'monthly' | 'ticket' | 'pair' | 'transfer'
  month_key      TEXT,                -- monthly のとき、どの月の枠か
  pack_id        TEXT,                -- ticket/pair のとき、どのパックか
  units          INTEGER NOT NULL DEFAULT 1,
  decided_at     INTEGER NOT NULL
);
```

### 確保のしかた（同時に走っても壊れない）

```sql
-- 月額から1回を確保する
UPDATE monthly_quota
   SET used = used + 1, updated_at = :now
 WHERE customer_id = :cid AND month_key = :mk
   AND used + 1 <= quota;              -- ★これが条件
-- changes = 1 なら確保できた。0 なら残りが無い
```

```sql
-- チケットから確保する（ペアは units=2）
UPDATE ticket_packs
   SET used = used + :units
 WHERE pack_id = :pid
   AND used + :units <= total
   AND valid_from <= :start_at AND valid_to >= :start_at;
```

**同時に2つのリクエストが来ても、データベースが1つずつ処理するので、`used < quota` を同時に通れない。**
ScriptLockが守っていたものを、より細かい単位（会員×月／パック）で守る。

> ★ScriptLockは**プロジェクト全体で1つ**だった。つまり無関係な会員の予約まで並べて待たせていた。
> 行ごとの確保にすると、関係する会員だけが待つ。**速くなるうえに、守りは強くなる。**

### 戻すとき（取消・変更）

```sql
UPDATE monthly_quota SET used = used - 1 WHERE customer_id = ? AND month_key = ? AND used > 0;
DELETE FROM reservation_allocations WHERE reservation_id = ?;
```

**予約の取消と、引当の返却を同じ書き込みで行う。** 片方だけ成功する状態を作らない。

## 4. 消化先の決め方（オーナー判断）

### 既定は月額

```
月額の枠が残っていれば、月額から使う
残っていなければ、チケットから使う
ペアチケットは、2名で来るときだけ
```

### 顧客は選べる（選択肢があるときだけ聞く）

```
確定の画面で
  月額もチケットも残っている → どちらから使うか選ばせる（既定＝月額）
  片方しかない               → 聞かない
```

**いまの画面は「通常」と「ペアチケット」の2択で、月額とチケットが一緒くたになっている。**
これを「月額／チケット／ペアチケット」の3つに分ける。

### 理想：自動で最適に割り当てる（将来）

**記録の構造は変えずに、決め方だけを差し替えられるようにする。**

```
いま   月額を優先（単純で説明しやすい）
将来   期限・損得を見て、顧客にいちばん有利なものを自動で選ぶ
       例：12/15で切れるチケットが3枚あり、月額は毎月付与される
           → チケットを先に使ったほうが失効しない
```

**決め方は1つの純粋関数に閉じ込める**（`chooseSource(残数の状態, 予約の日時, 顧客の指定) → source`）。
Nodeでテストでき、将来の差し替えがここだけで済む。

> ★2026-10-03 に起きた「チケットの先食い」は、**決めた後で入れ替わる**ことが原因だった。
> 固定すれば、決め方が何であれ入れ替わらない。

## 5. 予約の確定（Workerでの流れ）

```
1. 操作IDを見る（同じIDの再送なら、元の結果をそのまま返す）
2. 認証・締め切り・入力の検証          … 純粋関数（既にある）
3. （3-c以降は不要）カレンダーの照会   … 下記「照会が要らなくなる」
4. D1に1回の書き込みで、すべてを行う：
     a. 枠の確保（条件付きUPDATE。changes=0 なら残数不足）
     b. 予約の作成（重なりの条件をINSERTに含める。changes=0 なら枠が埋まった）
     c. 引当の記録
     d. やることリスト（outbox）に積む
     e. 操作IDの記録
   → どれか1つでも失敗したら、全部やり直し（原子的）
5. 応答を返す
---- 以下は別の処理が、やることリストを見て進める ----
6. Googleカレンダーに予定を作る
7. 予約台帳に書き戻す
8. LINE通知
```

### 照会が要らなくなる（2026-10-06・決定0069）

第1版は「D1に書いてからカレンダーを照会」と書いていた（図と本文が矛盾していた）。
第2版はそれを「照会してから書く」に直した。**第3版では、照会そのものが要らなくなる。**

**B1カレンダーに人が書き込まないので、照会と書き込みの間に割り込む人間がいない。**
トレーナーにはB1の書き込み権限がすでに無く、仮押さえもLIFF経由＝D1を通る。

残る外部の書き手はサロンボードだけで、それは別経路（取り込み）で入る。
**移行期（3-a・3-b）はGASが正本なので照会を残すが、3-cで落とす。**

これにより、第2版が到達点としていた「12秒→1〜2秒」は、**1秒未満に届く見込み**になる
（出勤・休憩もD1が正本になれば、確定時の外部呼び出しがゼロになるため）。

### 重なりをINSERTに含める（条件は2本）

施設とトレーナーは別々に埋まるので、重なりの条件も2本になる。

```sql
INSERT INTO reservations (
  reservation_id, customer_id, trainer_id, start_at, end_at,
  occupies_facility, occupies_trainer, consumes_quota, payment_status, status, ...)
SELECT :rid, :cid, :tid, :start, :end, :facility, :trainer, :quota, :pay, 'booked', ...
 WHERE NOT EXISTS (
   SELECT 1 FROM reservations
    WHERE status = 'booked'
      AND start_at < :end AND end_at > :start
      AND (
        -- ① 同じトレーナーが埋まっている（オンラインでも埋まる）
        (:trainer = 1 AND occupies_trainer = 1 AND trainer_id = :tid)
        -- ② 地下が埋まっている（定員1。オンラインはここに当たらない）
        OR (:facility = 1 AND occupies_facility = 1)
      )
 );
-- changes = 1 なら成立。0 なら SLOT_TAKEN
```

**「確かめてから書く」ではなく「条件つきで書く」。** 間に他が入る隙が無い。

**オンライン（`occupies_facility = 0`）は②に当たらない**ので、地下が埋まっている時間でも取れる。
いまは1Fカレンダーに置くことでこれを実現していた。列になれば置き場所が要らない。

### 一意制約は補助の砦

```sql
CREATE UNIQUE INDEX ux_resv_trainer_slot ON reservations(trainer_id, start_at)
  WHERE status = 'booked' AND occupies_trainer = 1;
CREATE UNIQUE INDEX ux_resv_facility_slot ON reservations(start_at)
  WHERE status = 'booked' AND occupies_facility = 1;
```

**`WHERE status = 'booked'` を落とすと、取り消した枠を二度と取れなくなる。**

**施設側の一意制約は「地下の定員が1」に依存している**（`gas/LineBooking.js:4223` で確認）。
定員を2以上にする日が来たら、この索引では表せない。そのときは上のINSERTの②を
`(SELECT COUNT(*) ... ) < :capacity` の形に変え、索引は落とす。**定員を変える＝索引も変える**と覚えておく。

### 列の制約もデータベースに持たせる

```sql
CHECK (end_at > start_at)
CHECK (occupies_facility IN (0,1))
CHECK (occupies_trainer  IN (0,1))
CHECK (consumes_quota    IN (0,1))
CHECK (payment_status IN ('paid','unpaid'))
CHECK (attendee_count IN (1,2))
CHECK (status IN ('booked','consumed','cancelled','changed'))
-- 施設もトレーナーも埋めない予約は存在しない（入力ミスを通さない）
CHECK (occupies_facility = 1 OR occupies_trainer = 1)
-- 残数を使うなら顧客が決まっていなければならない
CHECK (consumes_quota = 0 OR customer_id IS NOT NULL)
```

**いまのスキーマはこれらを強制していない**（Codex指摘）。正本になるなら、データベースが守る。

## 6. 後始末（outbox）

### 予約と同じ書き込みで積む

```sql
CREATE TABLE outbox (
  job_id       TEXT PRIMARY KEY,      -- 冪等性キー（reservation_id + 種別）
  kind         TEXT NOT NULL,         -- 'cal_b1' | 'cal_trainer' | 'sheet' | 'notify_customer' | 'notify_trainer'
  reservation_id TEXT NOT NULL,
  payload      TEXT NOT NULL,
  status       TEXT NOT NULL,         -- 'pending' | 'running' | 'retry' | 'done' | 'dead'
  attempts     INTEGER NOT NULL DEFAULT 0,
  next_at      INTEGER NOT NULL,
  lease_until  INTEGER,               -- 処理中に落ちたとき、他が拾えるように
  last_error   TEXT,
  external_id  TEXT                   -- 成功したときの外部ID（カレンダーの予定IDなど）
);
```

### ★トレーナー個人カレンダーへの書き戻し（2026-10-06・オーナー判断）

**トレーナーは自分の予約を個人カレンダーで見たい。** したがって `cal_trainer` は残す。

ここに危険がある。**同じカレンダーが入力（シフト）と出力（予約）を兼ねる。**

```
D1の予約 → 個人カレンダーに書く → D1がカレンダーを読む → 同じ予約をもう一度数える
```

空き枠は `出勤 − そのトレーナーの予約` で計算する。
予約をD1からもカレンダーからも引くと、**1件の予約で2枠が消える。**

**防ぎ方は、自分が書いたものに印を付けて、読むときに外すこと。**

```
書くとき  予定の説明欄に reservation_id を焼き込む
読むとき  reservation_id がある予定は無視する（自分の出力だから）
          出勤（shift）と休憩（break）だけを読む
```

既存に同じ手がある。HPB連携が `hpbReservationId` を予定に焼き込んで、
逆同期が自分の出力を拾わないようにしている（`hpb-mail-to-calendar/gas/sync.js`）。同じ作法に揃える。

**この印が抜けると、空き枠が実際の半分になる。** 移行の検査（第10節）に必ず入れる。

### B1カレンダーへの書き戻し

`cal_b1` は出力のみ。**人は書かない**ので、読み戻しの心配は無い。
ただしB1を読んでいる既存の3つ（空き枠・`salonboard-sync`・`billing`）が居る間は、
**タイトルの命名規則を変えてはならない**。読み手をD1へ移し終えてから、はじめて自由になる。

**`ctx.waitUntil()` だけに頼らない**（Codex指摘）。Workerが止まれば後始末そのものが消える。

### 冪等に書く

```
カレンダーの予定   説明欄に reservation_id を焼き込み、「予約ID＋出力先」で探してから作る
予約台帳           reservation_id で行を探してから書く（重複行を作らない）
LINE通知           outbox の状態で管理（完全な冪等は難しいので、送信済みを記録する）
```

### 遅れをどう扱うか

| 予約の開始まで | いつまでに追いつくべきか |
|---|---|
| 24時間以内 | **15分以内。** 超えたらトレーナーへ即時通知 |
| 24時間より先 | 当日中。超えたら日次の報告に載せる |

**「3回失敗したら要対応・毎日通知」では遅い**（Codex指摘）。翌日のセッションなら、最大24時間カレンダーに現れない。

**★監視の通知は、壊れている経路に載せない。** カレンダー登録の失敗を知らせる通知が、同じ仕組みで失敗したら意味がない。

## 7. 移行の対象（作成だけではない）

**第1版は予約の作成しか書いていなかった。** 正本の移行は、予約の一生すべてが対象。

| 入口 | いまの実装 | 移す段 |
|---|---|---|
| 会員の新規予約 | `makeReservationLine` | 3-c |
| 代行予約 | `makeReservationLineProxy` | 3-c |
| 繰り返し予約 | `makeRecurringReservation` | 3-c |
| まとめて予約 | `makeBatchReservation` | 3-c |
| 振替予約 | `makeTransferReservation` | 3-c |
| 取消（無料／当日消化） | `cancelReservationLine` | **3-c（同時に移す）** |
| 変更 | `changeReservationLine` | **3-c（同時に移す）** |
| 未登録客の枠確保 | `makeAdminBooking` | 3-c |
| ブロック枠 | `makeBlock` | 3-c |
| 固定枠の自動予約（毎月25日） | `autoBookRecurringPatterns` | 3-c |
| 未紐付けの後付け紐付け | `linkUnlinkedReservation` | 3-c |
| 外部（サロンボード）からの取込 | カレンダー同期 | 3-a から（下記） |

**取消を移さずに作成だけ移すと、D1の予約が永遠に `booked` のまま残る。**

### ★書き手だけでなく、読み手も移す（2026-10-06・調査で判明）

**第2版はここが抜けていた。** B1カレンダーを読んでいるのは空き枠だけではない。

| 読み手 | B1を何として読んでいるか | 移す段 | 危険度 |
|---|---|---|---|
| 空き枠（pt-gas） | 施設が埋まっている | 3-b | 中 |
| `salonboard-sync` | サロンボードへ送るブロック | 3-b | 中 |
| **`billing`（請求）** | **売上の一次ソース**（`importCalendarLog` がタイトルを解析） | **別途・慎重に** | **高** |

請求は売上に直結する。**D1読みへ移すときに数字が変われば、それは請求額が変わるということ。**
他の移行と同じ段に混ぜない。移す前後で同じ月の集計が一致することを確かめる工程を独立で持つ。

**読み手を移し終えるまで、B1のタイトルの命名規則は変えられない。**
`[RESERVED]` / `[消化]` / `HPB体験_担当_顧客` の形を保ったまま出力する。

### カレンダー直接入力という入口は存在しない（確認済み）

第2版は「カレンダーに直接書かれた予定」を入口として扱っていたが、
**トレーナーにはB1の書き込み権限が無い**（2026-10-06 確認）。この入口は移行の対象にならない。

残る「人がB1に書ける」経路はオーナーのみ。運用上ゼロとみなす。

### 1Fカレンダーの既存予定（★順序に注意）

1Fは廃止するが、**止める前にD1へ取り込まないと情報が失われる。**
1Fに置いてあること自体が「この予約はオンラインだった」という唯一の証跡になっている可能性がある。

取り込むときの判定は、契約種別の「オンライン」から引く（決定0069）。
**1Fの予定数とD1に入った `occupies_facility = 0` の件数が一致すること**を3-bへ進む条件に入れる。

### 当日キャンセルと振替権

当日キャンセルは `consumed` にして振替権を1つ与える。
**振替権もD1で管理する**（別表）。予約と同じ書き込みで増減させないと、原子性が分断される。

## 8. 外部（サロンボード）由来の予約

**D1に入れる**（オーナー判断）。入れないと二重予約の判定から漏れる。

### ループを防ぐ

```
D1の予約 → カレンダーに出力 → カレンダー同期 → D1に取り込む → また出力 …
```

**自分が作った予定を取り込まない。** カレンダーの予定の説明欄に `reservation_id` を焼き込んであるので、
それがある予定は取り込まない。

```sql
-- 外部の予定は、その出所と外部IDで一意にする
CREATE UNIQUE INDEX ux_resv_external ON reservations(source_calendar_id, external_event_id)
  WHERE external_event_id IS NOT NULL;
```

いまの `calendar_event_id` は普通の索引で、一意ではない（Codex指摘）。

### 外部予約の扱い

| | 扱い |
|---|---|
| 枠の占有 | **する**（会員が紐付いていなくても、施設とトレーナーは埋まる） |
| 残数の消費 | **しない**（紐付くまでは誰の予約か分からない）。紐付いたときに引当を作る |
| 外部で取り消された | 同期で `cancelled` にする |
| D1の予約と重なった | **先に入っていたほうを残す。** 後から来たものは「要対応」に載せ、人が判断する |

## 9. 段階（各段に進む条件を明文化する）

### 3-a：二重書き（2週間）

```
GASが予約を確定したら、いままでどおり台帳に書き、あわせてD1にも書く
読み取りは変えない。顧客から見て何も変わらない
```

**3-b へ進む条件**（すべて満たすこと）：

- [ ] 台帳とD1の突き合わせが、**14日連続で食い違い0件**
- [ ] その14日に、**25日の固定枠自動予約を1回以上含む**（月をまたぐ処理を通す）
- [ ] 取消・変更・振替・一括・代行の**すべての入口で**二重書きが動いている
- [ ] 二重書きの失敗が、永続キューで再送されている（取りこぼしが無い）
- [ ] 既存の予約の移行（下記⑩）が済み、1件ごとの内容が一致している
- [ ] **1Fカレンダーの既存予定がD1に入っている**（件数が `occupies_facility = 0` の件数と一致）
- [ ] **台帳に行が無い種別を、照合の対象から正しく外している**（下記）

#### ★「台帳に無いがD1にある」が正常な種別がある（2026-10-06）

二重書きの照合は「台帳とD1が一致すること」を見る。
ところが**台帳にそもそも書かれない種別**がある。これを食い違いとして数えると、永遠に0件にならない。

| 種別 | 台帳 | D1 | 照合 |
|---|---|---|---|
| 会員の予約（通常・オンライン） | ある | ある | **突き合わせる** |
| 未登録客の仮押さえ | **無い**（`admin_hold` は台帳に書かない仕様） | ある | 件数だけ見る |
| ブロック枠 | 無い | ある | 件数だけ見る |

**照合の対象を種別ごとに定義してから3-aを始める。** 定義せずに走らせると、
「食い違い14日連続0件」が達成不能になり、段が進まない。

### 3-b：読み取りをD1の予約へ向ける

**第1版は「1行で戻せる」と書いたが、それだけでは安全でない**（Codex指摘）。
台帳に書けてD1に書けなかった瞬間、読み取りが欠落する。

**3-b に進むには、上の条件に加えて：**

- [ ] D1側に「どこまで追いついたか」の印（watermark）がある
- [ ] 追いついていないときは、読み取りを**止めるかGASへ戻す**（黙って欠けた一覧を出さない）
- [ ] 台帳→D1の継続的な再照合と自動修復が動いている

### 3-c：書き込みをWorkerへ（正本の移行）

**3-c に進むには、上に加えて：**

- [ ] 第7節の**すべての入口**がWorkerで動く
- [ ] 切り戻し訓練を実施し、**本番のD1で戻せることを確かめた**
- [ ] outbox の遅れの監視が動いている
- [ ] Codexの関門③を通過

## 10. 既存の予約の移行

**件数が合うだけでは足りない**（Codex指摘）。最低限これらを1件ごとに確かめる。

```
予約IDの一意性 ／ session_id の一意性
同じトレーナーの時間重複が無い（occupies_trainer = 1 の中で）
地下の時間重複が無い（occupies_facility = 1 の中で）
start_at < end_at ／ 来店人数が1か2
状態の変換（confirmed→booked／consumed／cancelled／changed）
振替が残数を消費していない ／ 体験90分の終了時刻
book_type（ペア／レンタル／モニター／★オンライン）の保持
★calendar_event_id（いまの押し出しは null にしている）
会員が紐付いていない予約 ／ 変更元と変更先の関連
当日消化の取消と無料の取消の区別 ／ JSTからepoch msへの変換
```

**占有の2軸に関する検査（2026-10-06 追加）**

```
1Fカレンダーの予定数 == D1の occupies_facility = 0 の件数
  （1Fを止める前に取り込めているか。ここがずれたら1Fを止めない）
オンライン契約の会員の予約が、すべて occupies_facility = 0 になっている
地下が埋まっている時間に、オンラインの予約が入れること（入れなければ2軸が効いていない）
同じ時間・同じトレーナーで、来店とオンラインが二重に入っていないこと

★トレーナー個人カレンダーの読み戻し検査（これが抜けると空き枠が半分になる）
  D1が出力した予定（reservation_id が焼き込まれている）を、空き枠の計算が読んでいないこと
  同じ予約が「D1の予約」と「カレンダーの予定」で二重に引かれていないこと
```

**★`calendar_event_id` を落とさない。** いまの押し出しは null を入れている。
これを落とすと、後から取消・照合ができない。**台帳の15列から直接移す。**

### 移す範囲

| | 第1版 | 第2版 |
|---|---|---|
| 範囲 | 過去730日〜未来180日（いまの押し出しと同じ） | **全履歴** |

**正本にするなら、過去を切ってはいけない**（Codex指摘）。
締めや会計が過去を参照する。切るなら「切った過去は別の場所が正本」と決める必要がある。
**全部移すほうが単純で安全。**

## 11. 切り戻し（訓練で確かめる）

### 何が起きたら戻すか

| 兆候 | 判断 |
|---|---|
| 二重予約が1件でも出た | **即座に戻す** |
| 残数を超えた予約が出た | 即座に戻す |
| D1と台帳の食い違いが出た | 即座に戻す |
| 確定の失敗が増えた | 戻す |
| 遅い（2秒を超える） | 戻さない（様子を見る） |

### 戻す手順（第1版の4手順では足りない・Codex指摘）

```
1. 新しい書き込みを止める（Worker の受付を止める）
2. 処理中のものが終わるのを待つ
3. やることリスト（outbox）を出し切る、または一覧にする
4. ある時点までのD1の予約を、台帳へ反映する
5. 双方向に一致することを確かめる
6. GASの書き込みを開始する
7. 予約の受付を再開する
```

**★「Workerが失敗したら自動でGASに落ちる」を3-cではやらない。**
書き込みの結果が分からない状態でGASにも書くと、二重になる。
**落とさず、同じ操作IDでWorkerに結果を問い合わせる。**

### 訓練

**本番のD1で、予約を入れて、戻して、件数と内容が一致することを確かめる。**
手順はコマンド1つで実行できる状態にする（人の手でやると、戻す判断そのものが遅れる）。

## 13. 落とし穴

1. **一意制約から `status='booked'` を落とすと、取り消した枠を二度と取れない**
2. **重なりは一意制約では防げない**（体験90分と通常60分）。INSERTに条件を含める
3. **D1は対話型のトランザクションを持たない。** 「確かめてから書く」を分けない
4. **後始末が失敗しても予約を取り消さない**（顧客には成立の通知が届いている）
5. **やることリストをためない。** 開始が近い予約ほど早く追いつく
6. **監視の通知を、壊れている経路に載せない**
7. **外部予約のループ**（自分が作った予定を取り込まない）
8. **締め・請求は台帳を見ている。** 書き戻しは「失敗してもよい」ではなく「必ず追いつく」
9. **移行の途中は正本が2つある。** どちらが正かを常に明確にする
10. **切り戻しの訓練を「やったことにしない」**
11. **残数の引当を戻し忘れない**（取消・変更で `used` を減らす）
12. **月をまたぐ予約**（25日以降に翌月を取る）で、どの月の枠を使うかを明確にする

## 14. 検証の計画

| 何を | どう確かめるか |
|---|---|
| 二重予約 | 同じ枠に同時に2件 → 必ず片方だけ成立 |


## 16. オーナーの要望と現実のズレ

1. **「予約確定1秒未満」に、この段で届く見込みになった**（2026-10-06 改訂）。
   第2版では「確定の瞬間にB1・担当・1Fの3つを照会するので1〜2秒が限界」と書いた。
   **B1に人が書かなくなり、1Fが廃止されるので、3-cで照会そのものが消える。**

   **記録の構造は変わらないので、後から差し替えられる。**

3. **昨日塞いだものの多くが不要になるが、消すのは最後。**
   3-cが安定するまで、鮮度の判定も押し出しも残す。両方動いている状態を経ないと戻せなくなる。

4. **この段は1〜2週間では終わらない可能性が高い。**
   第1版では「作成だけ」を見て1〜2週間と見積もったが、取消・変更・振替・固定枠・一括・代行・
   外部取込のすべてが対象になった。**3-a だけで2週間、全体で3〜4週間**を見ておくべき。

5. **第3版で、減るものと増えるものが両方ある**（2026-10-06）。
   減る：確定時のカレンダー照会／1Fの振り分け・同期・権限管理／外部予約のループ防止／

   特に請求は売上に直結するので、他と同じ段に混ぜず独立した工程として扱う。
