# ④ 予約の正本をD1へ移す（設計・第2版）

**目的**：予約の正本をスプレッドシートからD1へ移し、**「写しが古いかもしれない」という状態そのものを無くす。**

> 起草：2026-10-04／**第2版：Codexの関門①で差し戻されたため全面改訂**
> 決定0062（2026-09-30）の第3段。第1段（カレンダー→D1）と第2段（読み取りをWorkerへ）は完了済み。

## 0. 第1版が差し戻された理由（ここから読む）

Codexの判定：

> ScriptLockが守っている「枠」だけを見ており、**同じLockが守っていた「残数」「変更」「振替」「全入口の直列化」を落としています。**

**私は「二重予約をどう防ぐか」ばかり考え、同じ鍵が他に何を守っていたかを見ていなかった。**

| 第1版の穴 | 何が起きるか |
|---|---|
| 重なりの検査とINSERTが原子的でない | 「空きを確かめる→書く」の間に他が入る。D1は対話型のトランザクションを持たない |
| **残数の同時予約を防げない** | 残り1回の会員が、別々の時刻に同時に2件取れる（枠は違うので一意制約に当たらない） |
| カレンダー照会が1種類だけ | いまのGASはB1・担当トレーナー・1Fの3つを見ている |
| 取消・変更・振替・固定枠・一括予約の移行が無い | 作成だけ移すと、取消が台帳だけを更新しD1は永遠に「予約あり」 |
| 後始末が「再試行」 | 予約を書いた直後にWorkerが止まると、後始末そのものが消える |
| 冪等性キーが無い | 応答が落ちて再送されると、二重になるか、顧客に区別がつかない |

**第2版の中心は「引当を行として記録する」こと。** これが残数の守りと、オーナーの「消化先を固定したい」を同時に満たす。

## 1. 結論（先に読むところ）

| # | 論点 | 結論 |
|---|---|---|
| ① | 二重予約 | **重なりの条件をINSERT文そのものに含める**（単一SQL）。一意制約は補助の砦 |
| ② | **残数の同時予約** | **枠を行にして、条件付きUPDATEで確保する**（`used < quota` のときだけ+1） |
| ③ | **消化先** | **予約時に決めて行として記録し、以後変えない**（オーナー判断） |
| ④ | 消化先の既定 | **月額を先に使う**（オーナー判断）。顧客は選べる。**将来は自動で最適に割り当てる** |
| ⑤ | カレンダー照会 | 確定の瞬間に**B1・担当トレーナー・1Fの3つ**を1回のGAS呼び出しで照会 |
| ⑥ | 後始末 | **予約と同じ書き込みで「やることリスト」を積む**（outbox）。再試行だけに頼らない |
| ⑦ | 冪等性 | すべての書き込みに**操作ID**を付ける。同じIDの再送には元の結果を返す |
| ⑧ | 移行の対象 | **作成だけでなく、取消・変更・振替・固定枠・一括・代行・外部取込のすべて** |
| ⑨ | 段階 | 3-a 二重書き（2週間）→ 3-b 読み取り切替 → 3-c 正本移行。**各段に進む条件を明文化** |
| ⑩ | 切り戻し | **受付を止める→処理中を待つ→やることリストを出し切る→戻す**。訓練で確かめる |

## 3. 中心の設計：引当を行として記録する

### なぜこれが要るか

いまはScriptLockが**4つのことを同時に守っている**。

| 守っているもの | D1に移すとどうなるか |
|---|---|
| 同じ枠を2人が取らない | 一意制約＋重なり条件で守れる（むしろ強くなる） |
| **同じ人が残数を超えて取らない** | **守るものが無くなる** ← ここが第1版の穴 |
| 変更（旧を消して新を作る）が途中で止まらない | トランザクションで守る |
| すべての入口が1列に並ぶ | 行ごとの確保で置き換える |

**2つ目を解くのが、引当を行にすることである。**

### 枠を行にする

```sql
-- 月額の枠（会員×月）
CREATE TABLE monthly_quota (
  customer_id TEXT NOT NULL,
  month_key   TEXT NOT NULL,          -- '2026-10'
  quota       INTEGER NOT NULL,       -- 頻度＋繰越（契約から計算して入れる）
  used        INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (customer_id, month_key)
);

-- チケット（買った単位ごと）
CREATE TABLE ticket_packs (
  pack_id     TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL,
  kind        TEXT NOT NULL,          -- 'normal' | 'pair'
  total       INTEGER NOT NULL,
  used        INTEGER NOT NULL DEFAULT 0,
  valid_from  INTEGER NOT NULL,
  valid_to    INTEGER NOT NULL
);

-- 予約がどこから引いたか（★これが「固定」の正体）
CREATE TABLE reservation_allocations (
  reservation_id TEXT PRIMARY KEY,
  customer_id    TEXT NOT NULL,
  source         TEXT NOT NULL,       -- 'monthly' | 'ticket' | 'pair' | 'transfer'
  month_key      TEXT,                -- monthly のとき、どの月の枠か
  pack_id        TEXT,                -- ticket/pair のとき、どのパックか
  units          INTEGER NOT NULL DEFAULT 1,
  decided_at     INTEGER NOT NULL
);
```

### 確保のしかた（同時に走っても壊れない）

```sql
-- 月額から1回を確保する
UPDATE monthly_quota
   SET used = used + 1, updated_at = :now
 WHERE customer_id = :cid AND month_key = :mk
   AND used + 1 <= quota;              -- ★これが条件
-- changes = 1 なら確保できた。0 なら残りが無い
```

```sql
-- チケットから確保する（ペアは units=2）
UPDATE ticket_packs
   SET used = used + :units
 WHERE pack_id = :pid
   AND used + :units <= total
   AND valid_from <= :start_at AND valid_to >= :start_at;
```

**同時に2つのリクエストが来ても、データベースが1つずつ処理するので、`used < quota` を同時に通れない。**
ScriptLockが守っていたものを、より細かい単位（会員×月／パック）で守る。

> ★ScriptLockは**プロジェクト全体で1つ**だった。つまり無関係な会員の予約まで並べて待たせていた。
> 行ごとの確保にすると、関係する会員だけが待つ。**速くなるうえに、守りは強くなる。**

### 戻すとき（取消・変更）

```sql
UPDATE monthly_quota SET used = used - 1 WHERE customer_id = ? AND month_key = ? AND used > 0;
DELETE FROM reservation_allocations WHERE reservation_id = ?;
```

**予約の取消と、引当の返却を同じ書き込みで行う。** 片方だけ成功する状態を作らない。

## 4. 消化先の決め方（オーナー判断）

### 既定は月額

```
月額の枠が残っていれば、月額から使う
残っていなければ、チケットから使う
ペアチケットは、2名で来るときだけ
```

### 顧客は選べる（選択肢があるときだけ聞く）

```
確定の画面で
  月額もチケットも残っている → どちらから使うか選ばせる（既定＝月額）
  片方しかない               → 聞かない
```

**いまの画面は「通常」と「ペアチケット」の2択で、月額とチケットが一緒くたになっている。**
これを「月額／チケット／ペアチケット」の3つに分ける。

### 理想：自動で最適に割り当てる（将来）

**記録の構造は変えずに、決め方だけを差し替えられるようにする。**

```
いま   月額を優先（単純で説明しやすい）
将来   期限・損得を見て、顧客にいちばん有利なものを自動で選ぶ
       例：12/15で切れるチケットが3枚あり、月額は毎月付与される
           → チケットを先に使ったほうが失効しない
```

**決め方は1つの純粋関数に閉じ込める**（`chooseSource(残数の状態, 予約の日時, 顧客の指定) → source`）。
Nodeでテストでき、将来の差し替えがここだけで済む。

> ★2026-10-03 に起きた「チケットの先食い」は、**決めた後で入れ替わる**ことが原因だった。
> 固定すれば、決め方が何であれ入れ替わらない。

## 5. 予約の確定（Workerでの流れ）

```
1. 操作IDを見る（同じIDの再送なら、元の結果をそのまま返す）
2. 認証・締め切り・入力の検証          … 純粋関数（既にある）
3. ★カレンダーを照会（B1・担当・1F）  … GAS経由・1回。失敗したら通さない
4. D1に1回の書き込みで、すべてを行う：
     a. 枠の確保（条件付きUPDATE。changes=0 なら残数不足）
     b. 予約の作成（重なりの条件をINSERTに含める。changes=0 なら枠が埋まった）
     c. 引当の記録
     d. やることリスト（outbox）に積む
     e. 操作IDの記録
   → どれか1つでも失敗したら、全部やり直し（原子的）
5. 応答を返す
---- 以下は別の処理が、やることリストを見て進める ----
6. Googleカレンダーに予定を作る
7. 予約台帳に書き戻す
8. LINE通知
```

### ①②の順序が第1版と違う

第1版は「D1に書いてからカレンダーを照会」と書いていた（図と本文が矛盾していた）。
**正しくは、照会してから書く。** 書いてから照会すると、通さない判断をしたときに取り消す必要があり、
その取り消しが失敗する経路が増える。

### 重なりをINSERTに含める

```sql
INSERT INTO reservations (reservation_id, customer_id, trainer_id, start_at, end_at, uses_room, status, ...)
SELECT :rid, :cid, :tid, :start, :end, :room, 'booked', ...
 WHERE NOT EXISTS (
   SELECT 1 FROM reservations
    WHERE status = 'booked'
      AND (trainer_id = :tid OR (uses_room = 1 AND :room = 1))
      AND start_at < :end AND end_at > :start
 );
-- changes = 1 なら成立。0 なら SLOT_TAKEN
```

**「確かめてから書く」ではなく「条件つきで書く」。** 間に他が入る隙が無い。

### 一意制約は補助の砦

```sql
CREATE UNIQUE INDEX ux_resv_trainer_slot ON reservations(trainer_id, start_at) WHERE status = 'booked';
CREATE UNIQUE INDEX ux_resv_room_slot    ON reservations(start_at)             WHERE status = 'booked' AND uses_room = 1;
```

**`WHERE status = 'booked'` を落とすと、取り消した枠を二度と取れなくなる。**

### 列の制約もデータベースに持たせる

```sql
CHECK (end_at > start_at)
CHECK (uses_room IN (0,1))
CHECK (attendee_count IN (1,2))
CHECK (status IN ('booked','consumed','cancelled','changed'))
```

**いまのスキーマはこれらを強制していない**（Codex指摘）。正本になるなら、データベースが守る。

## 6. 後始末（outbox）

### 予約と同じ書き込みで積む

```sql
CREATE TABLE outbox (
  job_id       TEXT PRIMARY KEY,      -- 冪等性キー（reservation_id + 種別）
  kind         TEXT NOT NULL,         -- 'cal_b1' | 'cal_trainer' | 'sheet' | 'notify_customer' | 'notify_trainer'
  reservation_id TEXT NOT NULL,
  payload      TEXT NOT NULL,
  status       TEXT NOT NULL,         -- 'pending' | 'running' | 'retry' | 'done' | 'dead'
  attempts     INTEGER NOT NULL DEFAULT 0,
  next_at      INTEGER NOT NULL,
  lease_until  INTEGER,               -- 処理中に落ちたとき、他が拾えるように
  last_error   TEXT,
  external_id  TEXT                   -- 成功したときの外部ID（カレンダーの予定IDなど）
);
```

**`ctx.waitUntil()` だけに頼らない**（Codex指摘）。Workerが止まれば後始末そのものが消える。

### 冪等に書く

```
カレンダーの予定   説明欄に reservation_id を焼き込み、「予約ID＋出力先」で探してから作る
予約台帳           reservation_id で行を探してから書く（重複行を作らない）
LINE通知           outbox の状態で管理（完全な冪等は難しいので、送信済みを記録する）
```

### 遅れをどう扱うか

| 予約の開始まで | いつまでに追いつくべきか |
|---|---|
| 24時間以内 | **15分以内。** 超えたらトレーナーへ即時通知 |
| 24時間より先 | 当日中。超えたら日次の報告に載せる |

**「3回失敗したら要対応・毎日通知」では遅い**（Codex指摘）。翌日のセッションなら、最大24時間カレンダーに現れない。

**★監視の通知は、壊れている経路に載せない。** カレンダー登録の失敗を知らせる通知が、同じ仕組みで失敗したら意味がない。

## 7. 移行の対象（作成だけではない）

**第1版は予約の作成しか書いていなかった。** 正本の移行は、予約の一生すべてが対象。

| 入口 | いまの実装 | 移す段 |
|---|---|---|
| 会員の新規予約 | `makeReservationLine` | 3-c |
| 代行予約 | `makeReservationLineProxy` | 3-c |
| 繰り返し予約 | `makeRecurringReservation` | 3-c |
| まとめて予約 | `makeBatchReservation` | 3-c |
| 振替予約 | `makeTransferReservation` | 3-c |
| 取消（無料／当日消化） | `cancelReservationLine` | **3-c（同時に移す）** |
| 変更 | `changeReservationLine` | **3-c（同時に移す）** |
| 未登録客の枠確保 | `makeAdminBooking` | 3-c |
| ブロック枠 | `makeBlock` | 3-c |
| 固定枠の自動予約（毎月25日） | `autoBookRecurringPatterns` | 3-c |

**取消を移さずに作成だけ移すと、D1の予約が永遠に `booked` のまま残る。**

当日キャンセルは `consumed` にして振替権を1つ与える。
**振替権もD1で管理する**（別表）。予約と同じ書き込みで増減させないと、原子性が分断される。

## 8. 外部（サロンボード）由来の予約

**D1に入れる**（オーナー判断）。入れないと二重予約の判定から漏れる。

### ループを防ぐ

```
D1の予約 → カレンダーに出力 → カレンダー同期 → D1に取り込む → また出力 …
```

**自分が作った予定を取り込まない。** カレンダーの予定の説明欄に `reservation_id` を焼き込んであるので、
それがある予定は取り込まない。

```sql
-- 外部の予定は、その出所と外部IDで一意にする
CREATE UNIQUE INDEX ux_resv_external ON reservations(source_calendar_id, external_event_id)
  WHERE external_event_id IS NOT NULL;
```

いまの `calendar_event_id` は普通の索引で、一意ではない（Codex指摘）。

### 外部予約の扱い

| | 扱い |
|---|---|
| 枠の占有 | **する**（会員が紐付いていなくても、施設とトレーナーは埋まる） |
| 残数の消費 | **しない**（紐付くまでは誰の予約か分からない）。紐付いたときに引当を作る |
| 外部で取り消された | 同期で `cancelled` にする |
| D1の予約と重なった | **先に入っていたほうを残す。** 後から来たものは「要対応」に載せ、人が判断する |

## 10. 既存の予約の移行

**件数が合うだけでは足りない**（Codex指摘）。最低限これらを1件ごとに確かめる。

```
予約IDの一意性 ／ session_id の一意性
同じトレーナーの時間重複が無い ／ B1を使う予約の時間重複が無い
start_at < end_at ／ 来店人数が1か2
状態の変換（confirmed→booked／consumed／cancelled／changed）
振替が残数を消費していない ／ 体験90分の終了時刻
book_type（ペア／レンタル／モニター）の保持
★calendar_event_id（いまの押し出しは null にしている）
会員が紐付いていない予約 ／ 変更元と変更先の関連
当日消化の取消と無料の取消の区別 ／ JSTからepoch msへの変換
```

**★`calendar_event_id` を落とさない。** いまの押し出しは null を入れている。
これを落とすと、後から取消・照合ができない。**台帳の15列から直接移す。**

### 移す範囲

| | 第1版 | 第2版 |
|---|---|---|
| 範囲 | 過去730日〜未来180日（いまの押し出しと同じ） | **全履歴** |

**正本にするなら、過去を切ってはいけない**（Codex指摘）。
締めや会計が過去を参照する。切るなら「切った過去は別の場所が正本」と決める必要がある。
**全部移すほうが単純で安全。**

## 11. 切り戻し（訓練で確かめる）

### 何が起きたら戻すか

| 兆候 | 判断 |
|---|---|
| 二重予約が1件でも出た | **即座に戻す** |
| 残数を超えた予約が出た | 即座に戻す |
| D1と台帳の食い違いが出た | 即座に戻す |
| 確定の失敗が増えた | 戻す |
| 遅い（2秒を超える） | 戻さない（様子を見る） |

### 戻す手順（第1版の4手順では足りない・Codex指摘）

```
1. 新しい書き込みを止める（Worker の受付を止める）
2. 処理中のものが終わるのを待つ
3. やることリスト（outbox）を出し切る、または一覧にする
4. ある時点までのD1の予約を、台帳へ反映する
5. 双方向に一致することを確かめる
6. GASの書き込みを開始する
7. 予約の受付を再開する
```

**★「Workerが失敗したら自動でGASに落ちる」を3-cではやらない。**
書き込みの結果が分からない状態でGASにも書くと、二重になる。
**落とさず、同じ操作IDでWorkerに結果を問い合わせる。**

### 訓練

**本番のD1で、予約を入れて、戻して、件数と内容が一致することを確かめる。**
手順はコマンド1つで実行できる状態にする（人の手でやると、戻す判断そのものが遅れる）。

## 13. 落とし穴

1. **一意制約から `status='booked'` を落とすと、取り消した枠を二度と取れない**
2. **重なりは一意制約では防げない**（体験90分と通常60分）。INSERTに条件を含める
3. **D1は対話型のトランザクションを持たない。** 「確かめてから書く」を分けない
4. **後始末が失敗しても予約を取り消さない**（顧客には成立の通知が届いている）
5. **やることリストをためない。** 開始が近い予約ほど早く追いつく
6. **監視の通知を、壊れている経路に載せない**
7. **外部予約のループ**（自分が作った予定を取り込まない）
8. **締め・請求は台帳を見ている。** 書き戻しは「失敗してもよい」ではなく「必ず追いつく」
9. **移行の途中は正本が2つある。** どちらが正かを常に明確にする
10. **切り戻しの訓練を「やったことにしない」**
11. **残数の引当を戻し忘れない**（取消・変更で `used` を減らす）
12. **月をまたぐ予約**（25日以降に翌月を取る）で、どの月の枠を使うかを明確にする

## 14. 検証の計画

| 何を | どう確かめるか |
|---|---|
| 二重予約 | 同じ枠に同時に2件 → 必ず片方だけ成立 |
| **残数の同時予約** | **残り1回の会員が別々の時刻に同時2件 → 1件だけ成立** |
| 時間の重なり | 体験90分と通常60分の重なりを止める |
| 取消→再予約 | 取り消した枠をもう一度取れる |
| 引当の返却 | 取消・変更で `used` が正しく戻る |
| 消化先の固定 | 予約時に決めた消化先が、後から変わらない |
| 後始末の失敗 | 予約は成立したまま、やることリストに残る |
| 操作IDの再送 | 同じIDで2回送っても1件だけ |
| 切り戻し | D1→台帳へ戻して、件数と内容が一致 |
| 既存の移行 | 1件ごとの内容が一致（第10節の一覧すべて） |

**わざと壊して検知するかを必ず確かめる**：

```
一意制約から status の条件を外す ／ 重なりの条件をINSERTから外す ／
枠の確保から used < quota を外す ／ 引当の返却を止める ／
後始末の失敗で予約を取り消す ／ 操作IDの検査を外す ／
外部予約のループ防止を外す ／ 切り戻しの照合を甘くする
```

## 16. オーナーの要望と現実のズレ

1. **「予約確定1秒未満」には、この段だけでは届かない。**
   確定の瞬間のカレンダー照会に1秒前後かかる（B1・担当・1Fの3つ）。
   **いまの12秒が1〜2秒になる**のがこの段の到達点。
   出勤・ブロックもD1が正になれば照会が消え、そのとき1秒未満に届く。

2. **「理想は自動で割当て」には段階がある。**
   まず「決めて固定する」（既定＝月額）。構造ができてから、決め方を自動最適化に差し替える。
   **記録の構造は変わらないので、後から差し替えられる。**

3. **昨日塞いだものの多くが不要になるが、消すのは最後。**
   3-cが安定するまで、鮮度の判定も押し出しも残す。両方動いている状態を経ないと戻せなくなる。

4. **この段は1〜2週間では終わらない可能性が高い。**
   第1版では「作成だけ」を見て1〜2週間と見積もったが、取消・変更・振替・固定枠・一括・代行・
   外部取込のすべてが対象になった。**3-a だけで2週間、全体で3〜4週間**を見ておくべき。
