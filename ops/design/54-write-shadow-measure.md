## 2. 比べた手段

### 2-1. 判定を比べる（M1）
| 手段 | 遅れ | 顧客の時間 | 正しさ | 判定 |
|---|---|---|---|---|
| A. **応答の後に GAS が「同じ入力」を Worker へ送り、Worker が D1 で判定して記録** | 数秒〜5分（一回限りトリガー／5分ごと） | 出口で1回の書き込みだけ | 比べる時刻が判定の時刻より少し後＝その差（lag）を必ず記録して分けて読む | ◎ 採用 |
| B. 確定の途中で GAS が Worker を同期で呼ぶ | 0 | **+0.5〜1秒**（UrlFetch） | 同じ瞬間で比べられる | ✗ 顧客を遅くする計測は本末転倒 |
| C. 毎晩、台帳と D1 から過去の確定を再判定 | 1日 | 0 | **判定の瞬間のカレンダーが残っていない**（calendar_events に履歴が無い） | ✗ Q1 に答えられない |
| D. 設計45 の写しの待ち（`_lbEdgePendingDrain`）に相乗りして同じ要求で送る | 同じ | 0 | 待ちの意味（I79 の covers）と失敗の扱いが混ざる | ✗ 壊れたときに写しの経路を巻き込む |

★比べる順序：一回限りトリガー `_lbCalSyncAfterWrite` の中で、**カレンダー同期（`_lbCalSyncCore`）より前**に送る。同期の後だと D1 が最新になりすぎ、S4 の Worker が実際に見る「最大5分古い D1」より甘く数えてしまう。D1 のカレンダーの古さ（cal_age_ms）は毎回記録する。

### 2-2. 直接入れた予定が D1 に届くまでの遅れ（M2）
| 手段 | 判定 |
|---|---|
| A'. **カレンダー同期の送り物に各予定の最終更新時刻（`getLastUpdated()`）を足し、Worker の同期が新しく見つけた「人が入れた予定」（休憩・ブロック・出勤）について 到着時刻 − 最終更新 を記録** | ◎ 採用。予約が無い時間の変更も数えられる＝窓の大きさそのものが分かる |
| B'. M1 の食い違いだけから推す | ✗ 確定が来なかった時間の変更は見えない＝「0回」が「起きなかった」のか「見ていない」のか分からない |

### 2-3. 契約の入力が D1 に届くまでの時間（M3）
| 手段 | 判定 |
|---|---|
| A''. **Worker の作り直しが会員を「新しい」に戻した瞬間に、新しくなかった長さ（いま − 新しくなくなった時刻）を記録**（`dirty_since`／`source_at` は既に列がある） | ◎ 採用。D1 の中だけで完結し、時刻のずれが無い |
| B''. GAS の `addTicketRefill` の時刻と突き合わせる | ✗ GAS と Worker の時計と経路をまたぐ。A'' で足りる |

## 3. 形

```
GAS（予約の要求・自動予約）
  _lbReserveCoreImpl の分岐で「どこで決まったか」を要求の中の変数に印（_lbWpMark と同じ作法・値は固定の語）
  要求の出口（ロックの外）で LB_WS_PENDING に1件積む（スイッチ LB_WS_ON が 'on' のときだけ・20件／6,000バイト・溢れは数える）
        │
        ├─ 一回限りトリガー _lbCalSyncAfterWrite の先頭（写しの待ちの次・同期より前）で送る
        └─ 5分ごとの lbCalSyncTick でも送る（一回限りが動かなかった・拒否された要求の分）
              POST /writeshadow（X-Ingest-Secret・I15）最大20件・予算10秒
Worker /writeshadow
  1件ずつ：鮮度（I31・I53）→ カレンダーの鮮度 → 施設の重なり → トレーナーの出勤と埋まり → 残数（allocate.js）
  → GAS の答えと比べて「一致／食い違い（理由）／判定しない（理由）」を write_shadow_log に1行
  → 受け取った id を返す（GAS は返った id だけ消す）
Worker の同期（calsync）
  新しく見つけた人の予定の 到着 − 最終更新 を calendar_arrival_log に1行（M2）
Worker の作り直し（/quota/rebuild・quotaBuild）
  会員が新しいに戻ったら fresh_delay_log に1行（M3）
日次点検（GAS）／作業依頼 remaining {writeShadow}
  GET /writeshadow/status：件数・理由別・p50/p95/最大・母数0・待ちの最古
```

結果の分類（write_shadow_log.verdict）：
- `match_ok`・`match_ng`（両方断った・理由の軸も同じ）
- `diff_*`（食い違い）：`diff_b1`・`diff_shift`・`diff_busy`・`diff_remain`・`diff_ng_reason`（両方断ったが軸が違う）
  - ★GAS が通して Worker が断る（**S4 なら取れたはずの予約を断る**＝安全側）と、GAS が断って Worker が通す（**S4 なら二重予約・残数超え**＝危険側）を `side` 列で必ず分ける
- `w_stale`（D1 が新しいと名乗れない＝S3/S4 は答えない側）
- `u_*`（判定できない）・`x_*`（S1a の範囲外）＝**一致にも食い違いにも数えない**（calcompare.js の規則4 と同じ。混ぜると永久に合格しないか、使えない状態を一致と数える）

### 3-3. 新しい表（migration 0036・CREATE … IF NOT EXISTS だけ・既存の表に ALTER しない＝I65 と同じ作法）
| 表 | 列 | 消える条件 |
|---|---|---|
| `write_shadow_log` | id・day（JST）・hour・op・ch・gas_ok・gas_at・verdict・side・tid・s・e・at・lag_ms・cal_age_ms・d1_ms・alloc_ms・total_ms・drain（AFTER／TICK）・build | 14日で消す（毎日の status の呼び出しで1回50行まで） |
| `calendar_arrival_log` | id・day・kind（add／change／remove）・cls（break／block／shift）・tid・s・e・delay_ms（remove は「前の同期から」の上限値）・window_hits | 30日 |
| `fresh_delay_log` | id・day・cause（dirty／source）・delay_ms | 30日 |

- **顧客ID・予約ID・予定ID・氏名・予定名の列を作らない**（検査で列の名前を固定）。tid と時刻は「その時間にそのトレーナーが埋まっていた」だけで、M2 の窓の重なりを数えるために要る。
- window_hits：その人の予定の「最終更新〜到着」の間に、write_shadow_log に同じトレーナー・重なる時間の確定が何件あったか（S4 ならその件数だけ、直接入れた予定を知らずに判定した）。
- D1 の書き込みは1件の確定につき1行＋同期の変更1件につき1行。1日数十〜数百行で、上限10万行（MODEL §7）に対して無視できる。

### 3-4. カレンダー同期の送り物の変更（M2 のため）
- `_calsyncEventsFor` と `buildCalSyncPayload` の各予定に `updatedAt`（`getLastUpdated()` のミリ秒）を足す。
- **Worker の同期の「中身が同じなら unchanged」（calsync.js の比べ方）には `updatedAt` を入れない**。入れると最終更新だけが変わった予定で毎回 patched になり、設計42（I74）の枠の押し出しが増える。検査で固定する。
- 反映の直後の1回目は、全部の予定が「新しく見つけた」に見える。**到着の記録は「前回の同期に同じ予定IDがあった」場合を除くのではなく、`updatedAt` が前回の同期の時刻より新しいものだけ数える**（反映直後の一斉の記録を出さない）。

### 3-5. 日次点検と作業依頼
- 点検（`dailyHealthCheck`）は `GET /writeshadow/status` を読み、次を出す（件数・コードだけ）：
  - `ws_danger`：`side=gas_ng_worker_ok`（危険側の食い違い）が1件でも（warn）
  - `ws_not_running`：スイッチ on で、前日に書き込み（LB_WRITE_PERF の件数）があるのに write_shadow_log が0件（warn）
  - `ws_backlog`：待ちの最古が2時間超・`dropped`／`stale` が増えた（info）
- 新しい key は **自己修理 P1 の振り分け表 `ops/booking-health-triage.md` と `LB_TRIAGE` に同じ変更で足す**（I-H10：表に無い key は B・79 key の一致を検査が見る）。3つとも B（人が見る）。
- 作業依頼 `remaining {writeShadow}`（新しい op を足さない・I-H34 と同じ作法）：日ごと・op ごとの verdict の件数・side 別・p50/p95/最大・M2 の遅れの分布と window_hits の合計・M3 の分布。**ID・時刻の生の値は返さない**。`_ejScrub` を通す（I28）。

## 5. 判定できないとき何を返すか
- 顧客：何も変わらない（GAS の答えのまま）。
- 記録：`u_*`（判定できない）・`x_*`（範囲外）・`w_stale`（D1 が新しくない）に分けて数え、**一致の率の分母に入れない**。率は「判定できた件数」を分母にし、判定できなかった件数を必ず並べて出す（倒れた回数と母数）。
- Worker が落ちた・時間切れ：GAS は項目を消さない（返った id だけ消す）。2時間で `stale` に数えて捨てる。

## 7. 止まったら誰が気づくか
- 比べる経路が止まる（スイッチ on なのに0件）→ 翌朝の点検 `ws_not_running`（母数は writePerf の書き込み件数＝別の記録から取る）。
- 送れずに溜まる → `ws_backlog`（最古の年齢・dropped・stale）。
- 危険側の食い違い → `ws_danger`（1件でも）。
- M2 の到着の記録が止まる（同期は動いているのに0件が7日続く）→ status に「最後に記録した時刻」を出し、作業依頼で CEO が読む（人が予定を入れない週もありうるので warn にはしない）。
