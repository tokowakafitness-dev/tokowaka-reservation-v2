### 顧客への影響：**値は変わらない。顧客の出口に新しい書き込み・ロックを足さない**
- 変えないのは**値**：GAS の判定・応答の中身・カレンダー・台帳・通知・写しの中身は1文字も変えない（不変条件 案 I83）。

- 例外は全部握りつぶし、6列目が作れなければ今と同じ5列の行を書く（I83）。

## 3. 形

```
GAS（予約の要求・自動予約）
  _lbReserveCore（:7357）は今も1回につき必ず _lbLogOutcome で booking_metrics に1行 appendRow している
  → その行の6列目に材料の文字列 'ws1' + JSON を足す（新しい書き込み・ロック・Script Property は0）
        │
        ├─ 一回限りトリガー _lbCalSyncAfterWrite の最後（成功した枠を変える操作のときだけ作られる）
        └─ 5分ごとの lbCalSyncTick の最後（断られた要求・一回限りが動かなかった分）
              カーソル LB_WS_CURSOR から先の行を読む（UserLock はカーソルの読み書きの間だけ）
              POST /writeshadow（X-Ingest-Secret・I15）最大50行・その実行の残り時間が足りるときだけ
              Worker が記録したと返した行は、6列目から顧客IDを消す（記録の文字列だけ残す）
Worker /writeshadow
  1件ずつ：鮮度（I31・I53）→ カレンダーの鮮度（readCalendar）→ 施設の重なり → トレーナーの出勤と埋まり → 残数（allocate.js）
  → GAS の答えと比べて「一致／食い違い（理由）／判定しない（理由）」を write_shadow_log に1行（行の鍵 n で二重に入れない）
Worker の同期（calsync）
  新しく見つけた人の予定の 到着 − 最終更新 を calendar_arrival_log に1行（M2）
Worker の作り直し（/quota/rebuild・quotaBuild）
  会員が新しいに戻ったら fresh_delay_log に1行（M3）
日次点検（GAS）／作業依頼 remaining {writeShadow}
  booking_metrics の 6列目つきの行数（母数）と Worker の記録の数を突き合わせる
```

### 3-1. outcome の記録の6列目（`booking_metrics`・`'ws1'` ＋ JSON）
| 鍵 | 値 | 個人情報 |
|---|---|---|
| n | 行の鍵（8桁の乱数・`Utilities.getUuid` の先頭）＝Worker が二重に入れない鍵 | — |
| op | 固定の語（reserve／proxy／batch／transfer／change／autobook／recurring） | — |
| ok・code | 成否・予約の返り値の code（許可リストに完全一致・外は OTHER）。3列目の outcome と同じ値 | — |
| at | どこで決まったか（gate／bad／deadline／horizon／remain／cap／b1／trainer／f1／consec／ok） | — |
| cid | 顧客ID（`C`+数字） | ★ID。**Worker が記録したと返したら、送る側がこの鍵だけを消す**（§6） |
| tid | トレーナーID | — |
| s・e・ex | 開始・終了・変更前の開始（ミリ秒） | — |
| att・pk | 人数・パック種別（固定の語） | — |
| cm | 連続ルールのモード（off／dry／on）と、その要求に効くか | — |
| t | 判定した時刻（ミリ秒） | — |
| cal | その時点の `LB_CALSYNC_LAST_OK`（読めなければ入れない。★これを読むために Script Property を新しく読まない＝既に読んでいる値があれば使う・無ければ空。Worker は D1 の公開世代の時刻を使う） | — |

- **予定ID・予約IDは載せない**（改訂1 の evs・rid を廃止）。Worker は「自分の予定」を **同じトレーナー・同じ開始・同じ終了の予約の予定を、カレンダーごとに1件だけ外す**ことで除く（本当に二重に入っていれば2件目が残るので食い違いとして見える）。残数も「同じ会員・同じ開始の確定の行を1件だけ外す」。
- 氏名・LINE の ID・電話・予定名は載せない。
- **既存の読み手**：`booking_metrics` を全幅で読む関数が4つある（LineBooking.js:5396・5412・7169・11472。`getLastColumn()` まで読む）。どれも0〜4列目しか使わないが、**6列目を報告やメールに出さないことを検査で固定する**。`getBookingMetrics`（:11491）は4列だけ読む。
- 容量：セルが1行に1つ増える。スプレッドシートのセルの上限（1,000万）に対する今の使用量は未確認（§13）。1日の行数は数十〜百程度。
- スイッチ：顧客の要求の中では Script Property を読まない（読むだけでも1回の呼び出しになる）。**6列目は常に書き、送るかどうかだけを `LB_WS_ON`（切替関数 `lbWriteShadowSetOn()／Off()`・画面で足さない＝決定0192）で決める**。6列目を書くことそのものを止めるのは GAS の差し戻し（または SETTINGS の定数）。

### 3-1-a. 何を母数に入れるか（関門① 中4・改訂2）
材料は `_lbReserveCore` が outcome を書く1行そのもの。**母数＝対象の channel・BUSY と perf_test を除いた outcome の行、材料＝その行の6列目**なので、母数と材料が別々に失われることはない（行が書けなければ両方無い＝今と同じく outcome の記録の欠け）。

| 経路 | 母数（比べる対象）に入れるか | 理由 |
|---|---|---|
| 認証の失敗（`handleLineGet` の `!auth.ok` の直接の return） | 入らない | `_lbReserveCore` まで行かない＝行が無い |
| 認証・振り分けの例外（投げ直す出口） | 入らない | 同上（`_lbReserveCoreImpl` の中の例外も outcome を書かずに外へ出る） |
| 通常の出口・成功／断り（SLOT_TAKEN・NO_REMAINING・TOO_SOON 等） | 入る | 断りは一回限りトリガーが作られない（PushToEdge.js:1381-1390・確認済み）＝5分ごとの同期で送る |
| BUSY（I81） | 入れない（行はあるが code=BUSY で外す） | 何も判定していない |
| SLOT_CHECK_UNAVAILABLE（1F・連続ルールが読めない） | 送るが比べない（`x_f1`／`x_consec`） | 範囲外 |
| 連続ルールで断った分（`_skipOutcome`・outcome を書かない） | 入らない | 連続ルールは off（10/26〜）。on に戻すと決めたら別に扱う |
| 変更：core が例外（補償） | 入らない | 行が無い |
| 変更：core が断った（補償）・成功 | 入る | `ex`（旧の開始）で Worker も旧行を外す |
| 自動予約（`channel='line'`） | 入る | op=autobook |
| `perf_test` | 入れない | — |
| ★**変更（中央27.1秒）** | **全部入る**（改訂1 の期限による欠けは無くなった） | 出口で積まないので時間に関係なく材料がある |

### 3-1-b. 送る側の排他（関門① 再審 重1）
- 送る側（トリガーの中）だけがカーソル `LB_WS_CURSOR`（{row, n}）を読み書きする。**顧客の要求は触らない**。
- 排他は **UserLock**（`tryLock(1000)`）。顧客の要求は UserLock を使わない（使っているのは `_lbCalSyncCore`・`_lbCalSlotsWithRecord` だけ・どちらもトリガーの中）。送る段はそれらの後に動くので、同じ実行の中でぶつからない。
- **保持はカーソルの読みと書きの2回の Script Property の操作の間だけ**。シートの読み・UrlFetch・6列目の消去はロックの外で行う。二つの送る側が同じ行を送っても Worker は行の鍵 `n` で二重に入れない（INSERT OR IGNORE）。カーソルは大きい方へしか進めない（MAX）。
- ロックが取れなければその回は送らない（`send_lock_miss` を Worker へ次回の送信で一緒に報告。数えるのは Worker の status＝ロックの外で数えて消えることが無い）。
- ScriptLock（書き込み・押し出し・I81/I82）は**一切使わない**。

### 3-1-c. 送る側の残り時間（関門① 中5）
- 一回限りトリガー：今ある段を全部済ませた後、その実行の経過が **4分未満**なら1回だけ送る（最大50行・UrlFetch 1回）。
- 5分ごとの同期：最後に、経過が **3分未満**なら1回だけ。カーソルの先が空ならシートの最終行を1回読むだけ。
- シートの読みはカーソルの行から最大200行（6列目の無い行は飛ばす）。カーソルの行の `n` が一致しなければ（誰かが行を消した・並べ替えた）直近200行を読み直す（Worker は `n` で重複を捨てる）。
- UrlFetch には時間切れを指定できないので、Worker は50行で10秒を超えたら残りを受け取らずに返す（GAS は返った行までカーソルを進める）。

## 10. 合格の線（S1 の観測の後に読む・S1b の結果と合わせて S2/S3 へ）
合否を**2つに分けて**出す（関門① 再審 中2）。片方だけ通っても、通った方の結論しか使わない。

### 10-A. 判定の同値性（M1）＝「同じ材料なら Worker は GAS と同じ答えを出すか」
★M1 は送る段を最後にしたので、D1 は判定の瞬間より新しい。**ここで言えるのは判定の論理が同じかどうかだけ**で、「古い D1 で確定してよいか」は 10-B で決める。
- **危険側の食い違い（GAS 断り・Worker 通し）0件**。安全側は理由ごとに件数と原因を確かめる。
- **有効な標本の下限**（関門① 再審 重2）：判定できた件数（`match_*`＋`diff_*`）が
  - 全体で **100件以上**
  - op ごとに：会員の予約（reserve）**40件以上**・**変更（change）15件以上**・代行（proxy）10件以上・自動予約（autobook）は25日の1回を含む
  - 断り（gasOk=false）を **20件以上** 含む（危険側は断りの中にしか現れない）
  - 足りなければ観測を延ばす（1週で足りなければ2週）。標本が足りないまま合格にしない
- **欠けの偏り**：op×時間帯ごとに、Worker の記録 ÷ 母数 が **95%以上**（`ws_partial` が鳴っていない）。6列目の無い対象の行は0件
- **判定できないことに逃げて合格しない**（関門① 重3）：
  - `u_cal_stale` が母数の **2%以下**、かつ1日 **3件以下**
  - D1 のカレンダーが7分を超えて古かった**連続時間の最長が15分以下**
  - `u_*` 全体が母数の **5%以下**
  - `x_*`（範囲外）は分母に入れないが、op ごとの件数を並べ、**`x_*` を除いた後の判定できた件数で上の下限を満たす**こと
- どれかを満たさなければ合格にせず、原因を潰して観測をやり直す。

### 10-B. 古い D1 で確定してよいか（M2）＝Q1 の「5分の窓」
- 危険な窓の当たり（`window_hits` のうち、**人が入れた「休憩・ブロックの追加」または「出勤の削除・短縮」が D1 に届く前に、同じトレーナー・重なる時間で GAS が通した確定**）が観測期間（最短2週）で **0件**。
  - 1件でもあれば合格にしない。件数と種類（休憩／ブロック／出勤）をオーナーに出し、計画書 §2-4 の「後から確かめる」（S4）だけで足りるかを決める。
  - 危険でない当たり（休憩・ブロックの削除・出勤の追加＝古い D1 では断るだけ）は件数だけ出す。
- 直接入れた予定の到着の遅れ：**p95 が6分以下・最大が12分以下**（5分ごとの同期＋処理）。超えたら同期の止まりを先に直す。
- 人が直接入れた予定の件数が観測期間で **10件未満**なら「標本不足」として結論を出さず、観測を延ばす（0件の窓は「起きなかった」ではなく「見ていない」かもしれない）。

### 10-C. ほかに読む数（合否ではなく置き直しに使う）
