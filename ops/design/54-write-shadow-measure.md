### 顧客への影響：**値は変わらない。顧客の出口に新しい書き込み・ロックを足さない**
- 変えないのは**値**：GAS の判定・応答の中身・カレンダー・台帳・通知・写しの中身は1文字も変えない（不変条件 案 I83）。
- 顧客の要求の中で増えるのは、**既に毎回書いている outcome の記録の1行（`_lbLogOutcome` の `appendRow`）に、6列目のセルを1つ足すこと**と、その文字列を作る計算だけ（改訂2）。新しい Script Property・新しいロック・新しい書き込みの回数は0。期限で積まないこと（skipped_budget）も起きない。
- 送るのは一回限りトリガーと5分ごとの同期の**最後**（§3-1-c）。前の段の開始時刻は変えない。送る側の排他は UserLock（顧客の経路が使わない鍵）で、送る段の1回分だけ・取れなければ次回に再試行。
- 1日の GAS の実行時間の増分の見積り：§3-1-d（約1〜2分/日・上限90分/日に対して）。
- 例外は全部握りつぶし、6列目が作れなければ今と同じ5列の行を書く（I83）。
- だから S1a は「計測だけの段」。顧客影響の関門は計画書どおり①（設計）と②（実装）を通す。③は不要（顧客に出すものが無い）。

## 3. 形

```
GAS（予約の要求・自動予約）
  _lbReserveCore（:7357）は今も1回につき必ず _lbLogOutcome で booking_metrics に1行 appendRow している
  → その行の6列目に材料の文字列 'ws1' + JSON を足す（新しい書き込み・ロック・Script Property は0）
        │
        ├─ 一回限りトリガー _lbCalSyncAfterWrite の最後（成功した枠を変える操作のときだけ作られる）

              前回どこまで見たか（行番号＋時刻・LB_WS_CURSOR）の続きを読み、6列目の印が「送った」でない行を送る（シートは保護で持ち主だけ編集可）
              POST /writeshadow（X-Ingest-Secret・I15）最大50行・その実行の残り時間が足りるときだけ
              Worker が記録した（または既に記録済み＝n が重複）と返した行は、そのセルの n を読み直して
              一致したときだけ、顧客IDを消して「送った」の印に書き換える

  1件ずつ：鮮度（I31・I53）→ カレンダーの鮮度（readCalendar）→ 施設の重なり → トレーナーの出勤と埋まり → 残数（allocate.js）

Worker の同期（calsync）
  新しく見つけた人の予定の 到着 − 最終更新 を calendar_arrival_log に1行（M2）

  会員が新しいに戻ったら fresh_delay_log に1行（M3）
```

- **既存の読み手**：`booking_metrics` を全幅で読む関数が4つある（LineBooking.js:5396・5412・7169・11472。`getLastColumn()` まで読む）。どれも0〜4列目しか使わないが、**6列目を報告やメールに出さないことを検査で固定する**。`getBookingMetrics`（:11491）は4列だけ読む。
- 容量（関門① 再々審 中3）：スプレッドシートのセルの上限（1,000万）は**値の入ったセルではなくグリッド（各シートの最大行数×最大列数）の合計**で数える。

  - 行は今も appendRow のたびに1行（×最大列数のセル）増えている。6列目はこの増え方を変えない。
  - **実装の前提条件**：作業依頼で、台帳のスプレッドシートの全シートの「最大行数×最大列数」の合計と、`booking_metrics` の最大行数・最大列数を実測する（値は返さず数だけ）。合計が上限の80%を超えていたら、6列目の前に行の整理を別に決める。
- スイッチ：顧客の要求の中では Script Property を読まない（読むだけでも1回の呼び出しになる）。**6列目は常に書き、送るかどうかだけを `LB_WS_ON`（切替関数 `lbWriteShadowSetOn()／Off()`・画面で足さない＝決定0192）で決める**。6列目を書くことそのものを止めるのは GAS の差し戻し（または SETTINGS の定数）。

- **1セルの長さ（改訂5・関門① 5回目 中3）**：上限1,000文字に届かないことを ID の長さから示す。

  | n | 8 |
  | op・at・pk・cm | 10・8・6・8 程度 |

  | cid | 15（`C`＋14桁） |
  | rid・xr | 各 約40（`'L'`＋14桁＋`_`＋トレーナーID＋`_`＋8・LineBooking.js:8165） |

  | s・e・ex・t・cal | 各13（ミリ秒） |
  | ok・att・sent | 1〜5 |
  | 鍵の名前・記号（20鍵×約6） | 約120 |
  | 合計（最大） | **約560文字**（eb・et が上限120でも約720文字）＝1,000文字に届かない |
  - それでも超えたら（作り方の不具合）、6列目に `ws1` と `{"n":…,"too_long":1}` だけを書き、母数に入れたまま `ws_too_long` として**欠けに数える**（合格の条件は0件・§10-A）。改訂4 の「5列の行にする」は母数から消えて欠けの分類と矛盾するのでやめた。

### 3-1-a. 何を母数に入れるか（関門① 中4・改訂2）
材料は `_lbReserveCore` が outcome を書く1行そのもの。**母数＝対象の channel・BUSY と perf_test を除いた outcome の行、材料＝その行の6列目**なので、母数と材料が別々に失われることはない（行が書けなければ両方無い＝今と同じく outcome の記録の欠け）。

| 経路 | 母数（比べる対象）に入れるか | 理由 |
|---|---|---|
| 認証の失敗（`handleLineGet` の `!auth.ok` の直接の return） | 入らない | `_lbReserveCore` まで行かない＝行が無い |
| 認証・振り分けの例外（投げ直す出口） | 入らない | 同上（`_lbReserveCoreImpl` の中の例外も outcome を書かずに外へ出る） |
| 通常の出口・成功／断り（SLOT_TAKEN・NO_REMAINING・TOO_SOON 等） | 入る | 断りは一回限りトリガーが作られない（PushToEdge.js:1381-1390・確認済み）＝5分ごとの同期で送る |
| BUSY（I81） | 入れない（行はあるが code=BUSY で外す） | 何も判定していない |
| SLOT_CHECK_UNAVAILABLE（1F・連続ルールが読めない） | 送るが比べない（`x_f1`／`x_consec`） | 範囲外 |
| 連続ルールで断った分（`_skipOutcome`・outcome を書かない） | 入らない | 連続ルールは off（10/26〜）。on に戻すと決めたら別に扱う |
| 変更：core が例外（補償） | 入らない | 行が無い |
| 変更：core が断った（補償）・成功 | 入る | `ex`（旧の開始）で Worker も旧行を外す |
| 自動予約（`channel='line'`） | 入る | op=autobook |
| `perf_test` | 入れない | — |
| ★**変更（中央27.1秒）** | **全部入る**（改訂1 の期限による欠けは無くなった） | 出口で積まないので時間に関係なく材料がある |

### 3-1-b. 送る側の読み方と排他（改訂5・シートの保護が前提）
- **前提**：`booking_metrics` はシートの保護でスクリプトの持ち主だけが編集できる（§3-1-e）。スクリプトは行を足す（appendRow）だけで、消す・並べ替える・刈り込むコードは無い（e94ff52 を grep で確認：`deleteRow`・`deleteRows`・`sort`・`clear`・`clearContents` の対象に `booking_metrics` は無い）。**だから行の位置は動かない**。
- **続きから読む**：送る側だけが `LB_WS_CURSOR`（{row, t}＝前回どこまで見たかの行番号と、その行の1列目の時刻）を持つ。毎回 `row+1` から最終行まで（1回最大500行）を読み、6列目が `ws1` で `sent` の無い行を送る（1回50件まで）。読み切れなかった分は次の回にその続きから読む＝**上限で打ち切っても押し出されない**（改訂4 の「3時間の窓の端まで読む」の判定は不要になった・関門① 5回目 中1）。
  - カーソルを進めるのは「読んだ行のうち、送り終えた（または送らなくてよい）行が連続している所まで」。送れなかった行があればそこで止める＝次回またそこから。
  - 起動のたびに、`row` の行の1列目の時刻が `t` と一致するかを確かめる。一致しなければ（保護が外れて誰かが行を動かした）カーソルを使わず、**保護の点検と同じ warn（`metrics_unprotected`・下）を出し、その回は送らない**（位置の前提が崩れたまま書き換えない）。
- **顧客IDの期限の消去**（改訂6・関門① 6回目 中2）：同じ読みの中で、`t`（判定の時刻）から2時間を超えた未送の行は、**6列目を「顧客IDを消し `stale:1` を足した文字列」に書き換えてから**カーソルを進める。分岐を固定する（改訂7・関門① 7回目 中2）：①書く前の照合（1〜5列目と `n`）が合わない → 書かずに**カーソルをその行で止める** ②書いた後に読み直して「顧客IDが無く `stale:1` がある・1〜5列目が同じ」を確かめられない → **カーソルをその行で止める**（`write_conflict` に数える） ③確かめられたときだけ進める＝**確かめられないまま進めない**。止まり続けたら（カーソルの先の未送が増える・同じ行で3回止まった）`ws_backlog`（info）、保護の崩れなら `metrics_unprotected`（warn）で翌朝に出る。件数は Worker への報告に頼らず、**この耐久的な印から数える**：日次点検が前日の `booking_metrics` の行を読むとき（母数を数えるのと同じ読み）に `stale:1` の行を数える。送る側は余裕があれば `stale` の行も判定なし（verdict `u_stale_unsent`・`n` で冪等）で Worker に送るが、届かなくても数は失われない。カーソルの手前に未送の行は残らない（送れない行でカーソルが止まっている間に2時間を過ぎれば、この規則でその行が片づき前へ進む）。
- **書き換えの照合（念のため残す）**：書く直前に、その行の1〜6列目を取り直して、1〜5列目が読んだときと同じで6列目の `n` が一致するときだけ6列目を書く。書いた後にもう一度読み、違っていれば `write_conflict` を数える。**競合したときは `sent` を付けない**＝次の回にもう一度送られる（Worker は `n` で重複を捨てる）。永久に送れない行は作らない（関門① 5回目 中2）。
- **排他**：送る段の1回分を UserLock（`tryLock(1000)`）の中で行う（顧客の要求は UserLock を使わない）。取れなければその回は何もせず、次の一回限りトリガーか5分ごとの同期で再試行して吸収する。ScriptLock は使わない。

### 3-1-e. `booking_metrics` の保護（改訂5・CEO 判断＝締める方向なので CEO の裁量）
- **業務の確認（COO の観点）**：コードにも業務の規則の文書（`30_projects/personal-training/ops/OPS-RULES.md`・予約リポジトリの設計書と MODEL）にも、`booking_metrics` を人が手で編集する手順は無い。シートは点検と計測の読み手が読むだけの記録。**ただし、オーナーが画面から行を消したり並べ替えたりしたことが無いかは未確認**＝「手で編集する運用は無い」の前提で進めるかは CEO が最終判断する（オーナーに1問で聞ける形：「booking_metrics のシートを手で触ることはありますか」）。
- **保護の前に確かめられる範囲（改訂7・関門① 7回目 中1）**：`booking_metrics` に行を足すのは、Web アプリの実行（`executeAs: USER_DEPLOYING`＝デプロイした人として動く）と、インストール型トリガー（作った人として動く）。保護の編集者に入っていないアカウントで動く実行は appendRow を断られる。メールアドレスで比べる案（`Session.getEffectiveUser`）は権限（userinfo.email）の追加が要るので採らない（`appsscript.json` は変えない）。確かめられるのは次だけ：
  1. Web アプリの実行者＝5分ごとの同期（`lbCalSyncTick`）のトリガーを作った人：設計42 の既存の印（Web アプリの実行から `lbCalSyncTick` のトリガーが見える＝`_lbCalSlotsSameUser` が same・`TICK_NOT_VISIBLE` が出ていない）。
  2. 作業依頼を動かしているアカウントから、`lbCalSyncTick`・`dailyHealthCheck`（LineBooking.js:5163 で作る）・自動予約・作業依頼のトリガーが**見える**（`getProjectTriggers()` は今のアカウントのトリガーだけを返す＝見えたものは同じアカウント）。見えたら、それらと Web アプリの実行と保護を置く `setupMetricsProtection()`（作業依頼から呼ぶ）は**同じアカウント**で動くと言える。日次点検もこのアカウントで動く（＝保護の編集者なので、保護を外せる）。
  - **これで証明できないこと**：見えないトリガー（別のアカウントが作ったのか、存在しないのか、名前が違うのか区別できない）。後から別のアカウントがトリガーを作った場合も、日次点検（同じアカウントで動く）からは見えない。→ **推論で塞がず、断られた事実を直接数えて戻す**（下）。
  - 1 か 2 が偽か不明（印が無い・見えない）なら、保護を置かずに止める（`metrics_protect_blocked`・warn）。保護が無い間は送る側も動かない（S1a は始まらない）。
- **断られた事実を数える**：`booking_metrics` に書く経路は `_lbLogOutcome` の appendRow（LineBooking.js:11458）1か所と、送る側の6列目の書き換えだけ（grep で確認）。
  - `_lbLogOutcome` の appendRow を try で包み、**失敗したときだけ** Script Property `LB_METRICS_WRITE_FAIL`（{n, last, type}＝件数・最後の時刻・例外の型名 `_lbErrType`・例外の文は残さない）を足してから、今と同じく例外を投げ直す（呼び出し元が握る＝予約の結果は変わらない）。**失敗の記録は別の try/catch の中で行い、記録（Property の読み書き）が例外になっても握りつぶして、元の appendRow の例外を必ずそのまま投げ直す**（改訂8・関門① 8回目 ①）。**成功したときは何もしない**＝顧客の経路の通常の手間は増えない。ロックを取らずに足す（同時の2件で1件落ちうる下限値。判定は「0より大きいか」だけなので足りる）。
  - 送る側の書き換えの失敗も同じ Property に足す（type に `ws_rewrite`）。
  - 日次点検（上の2で、保護を置いたのと同じアカウントで動くと確かめたもの）が `n > 0` を見たら `metrics_write_fail`（warn）を出し、**保護を外す**（`setupMetricsProtection()` が置いた説明の印つきの保護だけ）。保護を外すのは S1a の前の状態に戻すだけなので、自己修理のモード（practice／on）に関係なく日次点検が行う。外したら `metrics_unprotected` も出て送る側は止まる＝S1a は止まる。`incidents` には振り分け A（直せる・元に戻すだけ）として記録する（振り分け表・`LB_TRIAGE`・I-H12 の「A は2つだけ」の記述を同じ変更で直す）。
  - 日次点検は数えた分を引いて0に戻す（読んだ後に増えた分は残す）。
  - **失敗の記録に依らない独立の検知**（改訂8・関門① 8回目 ②）：失敗の記録そのもの（Property）が落ちると上の経路は気づけない。そこで日次点検は、**保護が置かれているときだけ**、前日について次の2つを比べる：
    - 台帳 `line_reservations` の作成日時（11列目・`recordReservationLine` が書く・LineBooking.js:8179・分まで）が**前日 00:00〜23:49**で、channel（10列目）が `_lbReserveCore` の channel の集合（S1a の対象と同じ表）に入る行の数＝`L`
    - `booking_metrics` の行のうち、時刻（1列目・秒まで）が**前日 00:00:00〜当日 00:10:00**で、同じ channel の集合で outcome が `success` の行の数＝`M`
    - **窓を非対称にする理由**（改訂9・関門① 9回目）：成功の予約は台帳を先に書き（`recordReservationLine`・LineBooking.js:7519）、outcome はその後（`_lbReserveCore` の `_lbLogOutcome`・:7360）。間は数秒、最悪でも GAS の1回の実行の上限6分。同じ「前日」で切ると、台帳 23:59・outcome 翌 00:00 の1件で `L=1・M=0` になり毎朝誤って保護を外しうる。`L` の終わりを23:49に、`M` の終わりを当日00:10にすると、`L` に数えた予約の outcome は必ず `M` の窓に入る（23:49＋6分＜00:10）＝**正常なら必ず `M ≥ L`**。逆に前日の頭に前々日分の outcome が混ざっても `M` が増えるだけで、誤検知の向き（`M` が足りない）にはならない。
    - ★**時刻を落とさない変換規則を固定する**（改訂10・関門① 10回目。日付しか返さない `_lbDateKey`（LineBooking.js:6166-6171）は使わない）：
      - セルが Date 値なら、そのまま epoch ミリ秒（`getTime()`）にする
      - セルが文字列なら、`SETTINGS.TIMEZONE` の `yyyy/MM/dd HH:mm` または `yyyy/MM/dd HH:mm:ss` として解釈して epoch ミリ秒にする（形に合わなければその行は数えず、`unparsed` の件数として出す）
      - 窓の両端も同じ `SETTINGS.TIMEZONE` から epoch ミリ秒に直す：L は「前日 00:00:00.000 ≤ t < 前日 23:50:00.000」（台帳は分までなので、23:49 はその分全体＝23:49:59 まで含む・23:50 は含まない）、M は「前日 00:00:00.000 ≤ t ≤ 当日 00:10:00.000」（00:10:00 は含む・00:10:01 は含まない）
      - **比べるのは当日 00:10:00 より後に動いた日次点検だけ**（いつもの7時の実行）。それより前の実行（手動の実行・作業依頼の dry-run など）は比べない（M の窓がまだ閉じていない）
    - **`L ≥ 1` で `M = 0`、または `L ≥ 5` で `M / L < 0.8`**（正常なら `M ≥ L` なので、線は欠けだけを拾う）なら、`metrics_write_fail` と同じ扱い（warn・保護を外す）。理由の語は `independent`。成功の予約は必ず台帳に1行・outcome に1行を書く（`_lbReserveCore` の成功＝`recordReservationLine` の後に `_lbLogOutcome('success')`）ので、ふだんは `M ≈ L`。差が出るのは outcome の行が断られたときか、台帳だけを書く別の経路（取込・保守の関数）が同じ channel を使ったとき＝後者は channel の集合から外す（実装の最初に台帳の channel の実際の値を数えて固定する）。
    - 保護が置かれていないときは比べない（S1a の前と同じく、outcome の記録の欠けは今までどおり見ていない）。
  - これで「最大約1日分」は2つの経路で成り立つ：①失敗の記録が書ければ翌朝それで外す ②失敗の記録も落ちたら、翌朝の台帳との比較で外す。どちらも日次点検（保護を置いたのと同じアカウント）が動く前提。日次点検そのものが止まったら、既存の点検の見張り（I-H16・点検の完走の印を lbNudgeDaily が確かめる）で気づく。
- 保護の関数 `setupMetricsProtection()`（冪等）：上の1・2が通ったときだけ、`booking_metrics` にシートの保護を1つだけ置き（説明の欄に印）、編集者を「この関数を動かしたアカウント」だけにする（スプレッドシートの持ち主は保護の下でも常に編集できる）。閲覧は今のまま。既に同じ保護があれば何もしない。ほかの編集者が付いていれば外す。
- 初回は GAS の反映の後、作業依頼から1回呼ぶ。新しいトリガーは作らない。
- **日次点検**：保護が無い・ほかの編集者がいる・警告だけの保護（`setWarningOnly`）→ `metrics_unprotected`（warn）。`LB_METRICS_WRITE_FAIL` が0より大きい → `metrics_write_fail`（warn・保護を外す）。自己修理 P1 の振り分け表と `LB_TRIAGE` に同じ変更で足す（I-H10）。送る側もカーソルの照合で崩れを見つけたら `metrics_unprotected` を出し、送るのを止める。
- 権限：シートの保護はスプレッドシートの今の権限の範囲（`appsscript.json` の変更は要らない見込み・実装の最初に確かめる）。

### 残りのリスク（保護が外れたとき・書き手が変わったとき・正直に）
- **別のアカウントが作ったトリガーから `_lbLogOutcome` が呼ばれると、保護で appendRow が断られる**。呼び出し元は例外を握りつぶすので**予約そのものは失敗しない**が、outcome の記録の行が欠ける＝S1a の母数だけでなく、既存の予約の成否の集計（`getBookingMetrics`）・通知の失敗の記録も欠ける。保護の前に確かめられる範囲（上の1・2）ではこれを証明できない。断られたら `LB_METRICS_WRITE_FAIL` に数え、翌朝の日次点検が保護を外して元に戻す＝**欠けるのは最大で約1日分（日次点検の間隔）の、そのアカウントの実行の outcome 行**（失敗の記録・台帳との比較の2つの経路で翌朝に外す。日次点検が止まった場合は I-H16 の見張りで気づく）。
- 人が行を消す・並べ替える・挿入すると、カーソルの行番号がずれる。送る側は時刻の照合で気づいて止まるが、**止まっている間に足された行の顧客IDは2時間で消えず、保護を戻してカーソルを直すまで残る**。翌朝の点検（`metrics_unprotected`）で気づく。
- 照合の間（数十ミリ秒）に行が動けば、別の記録の6列目を1件上書きしうる（顧客IDを消した文字列で上書きするので顧客IDは増えない・`write_conflict` で数える・`sent` は付けないので自分の行は次回送られる。上書きされた側の記録は1件の標本として失われ `ws_partial` に出る）。
- 保護を外せるのはスプレッドシートの持ち主だけ。外したら点検が翌朝に鳴る。

### 3-1-c. 送る側の残り時間（関門① 中5）
- 一回限りトリガー：今ある段を全部済ませた後、その実行の経過が **4分未満**なら1回だけ送る（最大50行・UrlFetch 1回）。
- 5分ごとの同期：最後に、経過が **3分未満**なら1回だけ。未送が無ければ窓を読むだけ。
- シートの読みはカーソルの続きから1回最大500行（§3-1-b）。
- UrlFetch には時間切れを指定できないので、Worker は50行で10秒を超えたら残りを受け取らずに返す（返った `n` の行だけ印を書く・残りは次の走査で送る）。

### 3-4. カレンダー同期の送り物の変更（M2 のため）
- `_calsyncEventsFor` と `buildCalSyncPayload` の各予定に `updatedAt`（`getLastUpdated()` のミリ秒）を足す。
- **Worker の同期の「中身が同じなら unchanged」（calsync.js の比べ方）には `updatedAt` を入れない**。入れると最終更新だけが変わった予定で毎回 patched になり、設計42（I74）の枠の押し出しが増える。検査で固定する。

### 3-5. 日次点検と作業依頼
- 点検（`dailyHealthCheck`）は `GET /writeshadow/status` と `booking_metrics` を読み、次を出す（件数・コードだけ）：

  - `ws_not_running`：`LB_WS_ON` が on で、前日に対象の行（母数）があるのに Worker の記録が0件（warn）
  - `ws_partial`：前日の **op×時間帯（hour）ごと**に、母数（6列目つきの対象の行）と Worker の記録の数を突き合わせ、どこかで記録が母数の95%未満（warn・欠けた op と時間帯を固定の語で出す）。6列目の無い対象の行（6列目を作る処理が例外で落ちた）も数える
  - `ws_backlog`：2時間を超えて未送のまま顧客IDを消した行（stale）が出た・送る側のロックが続けて取れない・カーソルの先の未送が500行を超えた（info）
  - `metrics_unprotected`・`metrics_protect_blocked`・`metrics_write_fail`：§3-1-e（warn。write_fail は保護を外す）
- 新しい key は **自己修理 P1 の振り分け表 `ops/booking-health-triage.md` と `LB_TRIAGE` に同じ変更で足す**（I-H10：表に無い key は B・79 key の一致を検査が見る）。7つ（ws_danger・ws_not_running・ws_partial・ws_backlog・metrics_unprotected・metrics_protect_blocked は B（人が見る）／metrics_write_fail は A（日次点検が保護を外して元に戻す））。
- ★改訂2で母数の内訳は単純になった（関門① 再審 中1）：母数＝対象の行・材料＝同じ行の6列目。欠けうるのは「送れなかった（未送のまま2時間＝stale）」と「Worker が記録できなかった」だけで、どちらも数える場所がロックの外の消えうる数ではない（未送はシートの `sent` の無い行、Worker の失敗は Worker の status）。
- 作業依頼 `remaining {writeShadow}`（新しい op を足さない・I-H34 と同じ作法）：日ごと・op ごと・時間帯ごとの母数と verdict の件数・side 別・p50/p95/最大・M2 の遅れの分布と window_hits・M3 の分布。**ID・時刻の生の値は返さない**。`_ejScrub` を通す（I28）。

## 5. 判定できないとき何を返すか
- 顧客：何も変わらない（GAS の答えのまま）。
- 記録：`u_*`（判定できない）・`x_*`（範囲外）・`w_stale`（D1 が新しくない）に分けて数え、**一致の率の分母に入れない**。率は「判定できた件数」を分母にし、判定できなかった件数を必ず並べて出す（倒れた回数と母数）。
- Worker が落ちた・時間切れ：印を書かずカーソルも進めない（次の回に同じ行を送る・Worker は `n` で重複を捨てる）。2時間を超えて未送の行は顧客IDを消し、`stale` として Worker へ件数だけ報告する（カーソルの所で片づけて進むので残らない・保護が前提）。

## 7. 止まったら誰が気づくか
- 比べる経路が止まる・一部だけ止まる → 翌朝の点検 `ws_not_running`／`ws_partial`（母数は outcome の記録＝write-shadow と別の記録から、同じ対象の集合で取る・§3-5）。

## 8. 戻し方
1. `lbWriteShadowSetOff()`（GAS・反映不要・即時）：送るのをやめる。6列目は書き続ける（顧客IDは2時間で消す処理も止まるので、止めている間は送る側の「消すだけ」の段を動かす＝送らずに顧客IDだけ消す）。6列目を書くこと自体を止めるのは GAS の差し戻し。

## 10. 合格の線（S1 の観測の後に読む・S1b の結果と合わせて S2/S3 へ）

### 10-A. 判定の同値性（M1）＝「同じ材料なら Worker は GAS と同じ答えを出すか」
★M1 は送る段を最後にしたので、D1 は判定の瞬間より新しい。**ここで言えるのは判定の論理が同じかどうかだけ**で、「古い D1 で確定してよいか」は 10-B で決める。
- **危険側の食い違い（GAS 断り・Worker 通し）0件**。安全側は理由ごとに件数と原因を確かめる。
- **有効な標本の下限**（関門① 再審 重2）：判定できた件数（`match_*`＋`diff_*`）が
  - 全体で **100件以上**
  - op ごとに：会員の予約（reserve）**40件以上**・**変更（change）15件以上**・代行（proxy）10件以上・自動予約（autobook）は25日の1回を含む
  - 断り（gasOk=false）を **20件以上** 含む（危険側は断りの中にしか現れない）
  - 足りなければ観測を延ばす（1週で足りなければ2週）。標本が足りないまま合格にしない
- **欠けの偏り**：op×時間帯ごとに、Worker の記録 ÷ 母数 が **95%以上**（`ws_partial` が鳴っていない）。6列目の無い対象の行は0件
- **判定できないことに逃げて合格しない**（関門① 重3）：
  - `u_cal_stale` が母数の **2%以下**、かつ1日 **3件以下**
  - D1 のカレンダーが7分を超えて古かった**連続時間の最長が15分以下**
  - `u_*` 全体が母数の **5%以下**。うち **`u_self_id` と `ws_too_long` は0件**（どちらも材料の作り方の不具合＝直してから観測をやり直す）
  - `metrics_unprotected` と `write_conflict` が観測期間で0件（保護の前提が保たれていた）
  - `x_*`（範囲外）は分母に入れないが、op ごとの件数を並べ、**`x_*` を除いた後の判定できた件数で上の下限を満たす**こと
- どれかを満たさなければ合格にせず、原因を潰して観測をやり直す。

### 10-B. 古い D1 で確定してよいか（M2）＝Q1 の「5分の窓」
