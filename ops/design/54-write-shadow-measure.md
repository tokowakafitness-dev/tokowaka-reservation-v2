### 顧客への影響：**値は変わらない。実行時刻は少し動く（上限を決めて守る）**
- 変えないのは**値**：GAS の判定・応答の中身・カレンダー・台帳・通知・写しの中身は1文字も変えない（不変条件 案 I83）。比べるのは応答の後。
- 動くのは**実行時刻**（関門① 中5）：
  - 要求の出口で、比べる材料を Script Property に1回積む（§3-1-b）。**受付からの経過時間で期限を切り、間に合わなければ積まない**（関門① 重1）。積むときの上限はロックの待ち 300ms＋書き込み1回（数十ミリ秒の見込み）＝**1要求あたり最大で約0.4秒、ただし受付から15秒を超える要求には一切足さない**。段 `ws` として writePerf（I77）に出して実測する。
  - 一回限りトリガーと5分ごとの同期の**最後**に送る（§3-1-c・関門① 中5）。前の段（写しの待ち・通知の待ち・同期・二重書き・枠の押し出し）の開始時刻は変えない。送る段は残り時間を見て、足りなければ送らない。
  - 1日の GAS の実行時間の増分の見積り：§3-1-d（約1〜2分/日・上限90分/日に対して）。
- 例外は全部握りつぶし、予約は成立のまま（I83）。既定オフ。
- だから S1a は「計測だけの段」。顧客影響の関門は計画書どおり①（設計）と②（実装）を通す。③は不要（顧客に出すものが無い）。

### 2-1. 判定を比べる（M1）

### 3-1-a. 何を母数に入れるか（関門① 中4）
材料を取るのは `_lbReserveCore` の返り値の直前（1要求でまとめて予約なら複数件）。積むのは `handleLineGet` の**通常の出口**と、自動予約（`autoBookRecurringPatterns`）の終わりだけ。

| 経路 | 比べる母数に入れるか | 数え方 |
|---|---|---|
| 認証の失敗（`handleLineGet` の `!auth.ok` の直接の return） | **入れない**（判定まで行っていない） | 数えない（writePerf の UNAUTHORIZED が既にある） |
| 認証・振り分けの例外（catch して投げ直す出口） | **入れない**（積まない。例外の経路に仕事を足さない） | 材料は捨てる。件数は writePerf の THROW と、日次の突き合わせの「残差」に出る |
| 通常の出口・成功 | 入れる | — |
| 通常の出口・断り（SLOT_TAKEN・NO_REMAINING・TOO_SOON 等） | 入れる（GAS 断り＝`gasOk=false`） | 一回限りトリガーは作られないので **5分ごとの同期で送る**（確認済み：`edgeAfterWrite` は `res.success !== true` で戻り、`_lbScheduleCalSync` はその後ろ・PushToEdge.js:1381-1390） |

### 3-1-b. 出口で積むときの期限と排他（関門① 重1・重2）
- **期限**：`handleLineGet` の入口の時刻（`_lbWpStart` の t0。write-shadow の対象 op は LB_WP.OPS の部分集合にして必ず t0 がある＝検査で固定）から
  - **15秒以内**：積む。ロックの待ちは `min(300ms, 15秒 − 経過)`。
  - **15秒を超えたら積まない**（`skipped_budget`）。画面の待ちの上限は20秒（liff/index.html:1096）。変更は中央27.1秒なので**変更の多くは skipped_budget になる**＝変更の比較は S1a では標本が少ない（自動予約・代行・会員の予約で見る。変更の比較を厚くするのは S1b で決める）。
  - ★「20秒を過ぎた要求は画面がもう待っていないので積んでもよい」という案は採らない（LIFF は通信の失敗で1回だけ自動で送り直す＝同じ時間に2本目の書き込みがロックを待っている可能性がある）。
- **排他**：`LB_EDGE_PENDING` と同じ **`_lbDwLocked`（ScriptLock）** に揃える。理由：
  - 読んで足して書く形なので、同時の2要求が互いの1件を消す（ロック無しだと黙って消える）。
  - 別のロック（UserLock）は、カレンダー同期（`_lbCalSyncCore`）が数秒握る同じ鍵で、出口がそれを待つことになる。DocumentLock は Web アプリの実行に文書が無い。
  - 1件ずつ別の Script Property に置く案（ロック不要）は、プロパティの数が最大20個増えて画面の一覧を埋め、取り出しで全件を読むので採らない。
- **待ちの上限**：出口は `_lbDwLocked(fn, min(300, 残り))`（既定の 15,000ms は使わない）。送る側（トリガーの中）は 300ms×3回まで。
- **I82 との競合**：押し出し（`_edgeLocked`）は同じ ScriptLock を所有権方式で長く持つことがある。その間は出口のロックが取れず `lock_miss` になる＝**押し出しが動いている時間の要求が標本から欠ける（偏り）**。`lock_miss` の件数と時刻の時（hour）を数えて偏りの大きさを出す。逆向き（出口が握る数十ミリ秒の間、押し出し・書き込みが待つ）は、書き込みの `_lbTakeWriteLock` の待ちより十分短いので BUSY を増やさない見込み。設計47 の `LB_WRITE_LOCK_COUNT` で反映前後を比べて確かめる。
- **数え方**（関門① 中6）：
  - ロックの中で書けたもの（`LB_WS_PENDING` の同じ JSON の `count[日]`）：`enq`（積めた）・`overflow`（20件・6,000バイトで古い方を捨てた）・`stale`（2時間で捨てた）・`sent`（送った）・`acked`（Worker が記録したと返した）・`lost`（送った後に消そうとして見つからない＝競合で消えた）
  - ロックが取れなかった・書けなかったもの（ロックの外の別の Script Property `LB_WS_MISS`・設計47 の `_lbWlFlush` と同じくロックを取らずに足す＝同時の2件で1件落ちうる下限値）：`lock_miss`・`set_fail`（setProperty の例外）
  - `skipped_budget` は時間が無いので何も書かない。**writePerf の行（I77）に `ws` の結果のコード（enq／skip／miss／fail）を1つ足して**残す（直近60件のリング）。日次は残差として出す（下）。

### 3-1-c. 送る側の残り時間（関門① 中5）
- 一回限りトリガー：今ある段を全部済ませた後、その実行の経過が **4分未満**なら1回だけ送る（最大20件・UrlFetch 1回）。4分以上なら送らず次の5分ごとへ回す（GAS の1回の上限6分）。
- 5分ごとの同期：最後に、経過が **3分未満**なら1回だけ。待ちが空なら Script Property を1回読むだけ。
- UrlFetch には時間切れを指定できないので、Worker 側は1件あたりの処理を軽くし（D1 の読み4〜6回・割当器1回）、20件で10秒を超えたら残りを受け取らずに返す（GAS は返った id だけ消す）。

### 3-4. カレンダー同期の送り物の変更（M2 のため）
- `_calsyncEventsFor` と `buildCalSyncPayload` の各予定に `updatedAt`（`getLastUpdated()` のミリ秒）を足す。
- **Worker の同期の「中身が同じなら unchanged」（calsync.js の比べ方）には `updatedAt` を入れない**。入れると最終更新だけが変わった予定で毎回 patched になり、設計42（I74）の枠の押し出しが増える。検査で固定する。
- 反映の直後の1回目は、全部の予定が「新しく見つけた」に見える。**到着の記録は「前回の同期に同じ予定IDがあった」場合を除くのではなく、`updatedAt` が前回の同期の時刻より新しいものだけ数える**（反映直後の一斉の記録を出さない）。

### 3-5. 日次点検と作業依頼
- 点検（`dailyHealthCheck`）は `GET /writeshadow/status` を読み、次を出す（件数・コードだけ）：
  - `ws_danger`：`side=gas_ng_worker_ok`（危険側の食い違い）が1件でも（warn）
  - `ws_not_running`・`ws_partial`：下の突き合わせ（warn）
  - `ws_backlog`：待ちの最古が2時間超・`overflow`／`stale` が増えた（info）
- 新しい key は **自己修理 P1 の振り分け表 `ops/booking-health-triage.md` と `LB_TRIAGE` に同じ変更で足す**（I-H10：表に無い key は B・79 key の一致を検査が見る）。4つ（ws_danger・ws_not_running・ws_partial・ws_backlog）とも B（人が見る）。
- ★`ws_not_running` を「部分停止」まで拾える形にする（関門① 中6）。母数は **write-shadow の対象と同じ集合**：outcome の記録（`_lbLogOutcome`・`_lbReserveCore` 1回につき1行・日付と channel つき）のうち、対象の channel（op の許可リストと同じ表から作る）で BUSY と perf_test を除いた件数＝`target`。日ごとに次を突き合わせる：
  - `target` ＝ `enq` ＋ `lock_miss` ＋ `set_fail` ＋ 残差（`skipped_budget`・例外の出口・変更の core 例外）
  - `enq` → `sent`（＋待ちに残った分・`overflow`・`stale`）→ `acked` → Worker の `write_shadow_log` の行数（Worker の記録の失敗も Worker の status に数える）・`lost`
  - 鳴らし方：`target>0` なのに `enq=0` → `ws_not_running`（warn）／`enq/target` が50%未満、または `sent>0` で `acked/sent` が90%未満、または `lost>0` → `ws_partial`（warn・どの段で欠けたかを固定の語で出す）／残差の率は writePerf の15秒超の件数の率と比べて大きく外れたら `ws_partial` に `residual` を付ける
- 作業依頼 `remaining {writeShadow}`（新しい op を足さない・I-H34 と同じ作法）：日ごと・op ごとの verdict の件数・side 別・p50/p95/最大・M2 の遅れの分布と window_hits の合計・M3 の分布。**ID・時刻の生の値は返さない**。`_ejScrub` を通す（I28）。
