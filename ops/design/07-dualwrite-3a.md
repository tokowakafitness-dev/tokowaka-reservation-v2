## 2. 設計の芯：入口ごとに引当を書かない

| | やり方 | 評価 |
|---|---|---|
| A | 入口ごとに引当を INSERT／DELETE する | ❌ **同じ計算を2通り書くことになる** |
| **B** | **書き込みのあと、その会員ぶんを作り直す** | ✅ 既に全員一致で検証済みの処理をそのまま使う |

**Bを採る。** 理由：

- 作り直しの処理（`buildQuotaForCustomer` / `buildAllocationsForCustomer`）は、
  39名の実データで計算と一致することを確認済み。**新しいロジックを持ち込まない**
- 入口は11（取消・変更・振替・一括・代行・固定枠…）。入口ごとに差分を書けば、
  **11通りの「引当の増減の書き方」が生まれる**。1つ間違えれば残数が狂う
- 消化先が変わる変更（月額→チケット）は、差分では表せない。作り直しなら自然に入る

既に `GET /quota/build?customer=<cid>&alloc=1&dry=0` で1名だけ作り直せる。

### コスト
1名 × 数か月。`loadCalcInput` 5クエリ＋書き込み数件。サブリクエスト上限50に対して十分小さい。

## 3. ★計算入力の「会員単位の置き換え」が要る（これが無いと取消が消えない）

いちばん重要な穴。

```
_edgeCalcReservations() は confirmed / consumed の行だけを出す
→ 予約が取り消されると、その行は**payloadから消える**
→ いまの partial 押し出しは「含まれなかった行」を消さない
   （deleteStale は scope:'all' のときだけ＝全件を走査し終えたときだけ）
→ D1の calc_reservation_rows に取消済みの行が残り続ける
→ 作り直しても、その予約を「生きている」として引当を作る
```

**＝取消が永遠にD1へ伝わらない。** 朝に見た食い違いが、放置すれば積み上がる形。

### 足すもの：`scope: 'customer'`（世代方式・2026-10-08 Codex関門①で修正）

```
POST /ingest { kind:'calcReservations', scope:'customer', customerId:'C123', rows:[…] }

  ① rows を**1行残らず** UPSERT する（synced_at = batchId）
  ② その会員の、**この世代より古い行**を削除する
     DELETE FROM calc_reservation_rows WHERE customer_id = ? AND (synced_at IS NULL OR synced_at < ?)
  ③ ①と②を**同じ env.DB.batch() に入れる**（途中で切れたら全部戻る）
  ④ sync_state は**押さない**
```

#### ★`NOT IN (…)` にしてはいけない（最初はそう書いていた）
取り込みは1回500行まで受ける（`MAX_ROWS`）。`NOT IN` にすると会員1人で最大501個の
バインド変数になる。**同じリポジトリの引当側は、D1の差し込み数の上限を理由に80件で
分割している**（`alloc-build.js` の `CHUNK = 80`）。自分で引いた線を別の場所で越えることになる。

#### ★`scope:'customer'` では「中身が同じ行を飛ばす」をしてはいけない
いまの差分モードは、中身が変わっていない行を書かない（D1の書き込み枠の節約・2026-09-29）。
**世代で消す方式と組み合わせると、変わっていない正常な行が古い世代のまま残り、削除される。**
→ `scope:'customer'` のときは `same()` の判定を通さず全行書く。
   対象は1人ぶん（多くても数十行）なので、書き込み枠への影響は無い。

#### なぜ既存の `partial` + `deleteStale` を使わないか
`deleteStale` は表全体から消す。1人ぶんの押し出しで使えば**他の会員の行が全部消える。**
いまは `scope:'all'` を要求して弾いてあるが、ここで緩めてはいけない。
**別の名前の、削除範囲が会員に閉じた指定**を足す。

#### 守り（実装時に必ず入れる）
```
scope:'customer' は customerId が無ければ 400
削除の WHERE から customer_id を外せないようにする（テストで固定）
rows の中に別の customer_id が混ざっていたら 400（他人の行を書かせない）
rows が空でも成立させる（＝その会員の予約が全部消えた、は正常な状態）
  ★ただし「読めなかった」と取り違えない（下記）
sync_state を押さないことをテストで固定（全体の鮮度は full sync が持つ）
```

#### ★「0件」と「読めなかった」を取り違えない（Codex関門①）
```
_edgeCalcReservations()  シートが読めない → null ／ ヘッダだけ → null
                         読めて confirmed/consumed が0件 → []
```
**`(_edgeCalcReservations() || []).filter(...)` と書いてはいけない。**
読めなかった `null` が正常な空配列に化け、**その会員の生きている予約を全部消す。**
```js
var all = _edgeCalcReservations();
if (all == null) return false;            // 読めなかった＝送らない
var mine = all.filter(…);                 // [] は正常として送る
```

### なぜ `sync_state` を押してはいけないか
`loadCalcInput` は3つの同期時刻が2時間以内であることを要求する。
1人ぶんの押し出しで時刻を押すと、**他の会員の古い行が「新しい」ことになる。**
2026-09-29 に別の表で起きた穴と同じ形（`ingest.js` のコメントに記録あり）。

## 4. 顧客を待たせない（遅らせてよい理由がある）

書き込みの直後に作り直しを同期で呼ぶと、予約確定が2呼び出しぶん遅くなる。
軽量化で 5,836ms → 1,703ms まで削った経路なので、ここに足したくない。

**3-a では、顧客の予約可否・残数表示に枠と引当を使う経路が0件。** だから遅れは顧客に見えない。
（★「読む処理が1つも無い」は誤り・Codex関門①で訂正。
  読んでいるのは照合 `quota-verify` と、合言葉で守られた運用確認 `quota/status` だけ。
  どちらも私が回すもので、顧客の画面には出ない。）

```
やること      既にあるトリガーに相乗りして、あとで処理する
やらないこと  予約確定の応答を待たせる／★新しいトリガーを作る
```

### ★新しいトリガーを作らない（2026-10-08・測って決めた）

コード上のトリガーは**21ハンドラ分**。GASの上限は1プロジェクト20本。**余裕がない。**
また「掃除してから作る」には並行実行の競合がある（Codex関門①）。
→ **既にある2つに相乗りする。作成の競合も上限の問題も、まとめて消える。**

| | 相乗り先 | 間隔 | 役割 |
|---|---|---|---|
| 速い道 | `_lbCalSyncAfterWrite`（`LB_CALSYNC.AFTER_HANDLER`） | 書き込みの**1秒後** | 予約のあと、ほぼすぐ追いつく |
| 心拍 | `pushToEdgeLight` | **15分ごと** | 速い道が働かなかったぶんを拾う |
| 網 | `pushToEdgeFullSync` | 1日1回（深夜4時） | 計算入力を全件入れ直す |

速い道は `EDGE_CALSYNC_AFTER` に載る操作のときだけ働く（カレンダーが変わる操作＝予約系）。
載らない操作（チケット追加など）は心拍が拾う。**どちらも働かなくても、網が翌日に揃える。**

★3-b（読み取りをD1へ向ける）に進む前に、ここは**同期呼び出しへ戻す**。
そのときは「古い残数を見せない」ほうが優先になる。**この判断は3-aに限る。**

**ただし「同期に戻す」だけでは足りない**（Codex関門①）。3-b では
「Workerへの書き込みが失敗したとき、予約をどう返すか」を決める必要がある。
3-a は正本がGASなので失敗しても予約は成立する。3-b は残数の判断にD1を使うので、
失敗は「残数が分からない」を意味する。**その場合の答え方は3-bの設計で決める。**

### トリガーの数を増やさない
同じハンドラの待機中トリガーを消してから1本作る（既存の `_lbCleanCalSyncAfterTriggers` と同じ）。
同時刻に複数の予約が入っても1本にまとめる。

ただし**作り直しは会員ごと**なので、1本のトリガーで複数の会員を処理する必要がある。
→ 待ち行列（第5節）に会員IDを積み、トリガーはその全員を処理する。

## 5. 失敗を落とさない（永続キュー）

3-b へ進む条件に「二重書きの失敗が、永続キューで再送されている」がある。

```
置き場所   Script Properties の 'LB_DUALWRITE_QUEUE'
形         { "C123": { "version": 17, "queuedAt": 1791420000000 }, … }   ★会員IDの配列ではない
積むとき   書き込みの直後。既に居ても version を上げる
外すとき   作り直しが成功し、**かつ version が処理開始時と同じとき**だけ
再送       トリガーが残りを処理する。残っていれば次のトリガーでも処理する
上限       200名。超えたら queuedAt の古い順に捨て、'LB_DUALWRITE_OVERFLOW' に件数を加算
           （黙って捨てない。溢れたこと自体を照合で見つける）
```

#### ★会員IDの配列にしてはいけない（Codex関門①）
```
1. トリガーが C123 を取り出して処理を始める
2. 処理中に C123 へ新しい予約が入る
3. 積もうとするが「既に居る」ので何もしない
4. 処理が成功し、C123 を外す
5. **2の予約が永遠に反映されない**
```
version を持たせ、**外すときに version が変わっていないことを確かめる。**
変わっていれば残す（次のトリガーで処理される）。

処理中ずっとロックを握るのは不可。**Workerとの通信中に予約の書き込みまで止まる。**

**二重の網**：全体同期（1日1回・`pushToEdgeFullSync`）が計算入力を全件入れ直す。
キューが壊れても、翌日には計算入力が揃う。ただし**枠と引当の作り直しは別**なので、
日次の作り直し＋照合を自動で回す（第7節）。

#### ★ロックを掛ける範囲（Codex関門①）
Script Properties の `getProperty` / `setProperty` は個々には原子的だが、
**「読む→直す→書く」の全体は原子的ではない。** 囲わないと並行予約で会員IDが失われる。

```
同一の ScriptLock 区間に入れるもの
  積むとき   キューを読む／会員を足す（versionを上げる）／上限とoverflowの処理／保存
  外すとき   キューを読む／versionを照合／同じなら外す／保存
```

**処理そのもの（Workerとの通信）はロックの外。** 中で握ると予約の書き込みまで止まる。

トリガーを作らない設計にしたので（第4節）、**「掃除してから作る」の競合は無くなった。**

### なぜシートではなく Script Properties か
`nudge_log` の行番号がずれて未達を送信済みにした事故（2026-10-07）と同じ理由。
**行番号に依存する置き場所を、並行して書かれるキューに使わない。**
Script Properties は読み書きが原子的で、ロックで囲めば十分。

## 6. 抜けている入口（4つ・Codex関門①で判明）

**「16の入口に配線済み」という私の理解は不正確だった。**
`edgeAfterWrite` の呼び出しは**1箇所だけ**（`handleLineGet`・`LineBooking.js:247`）。
16というのは、その1箇所が通す action の許可リスト（`EDGE_AFTER_WRITE`）の数。

生きている経路は `doGet` → `handleLineGet` → `_lbDispatch` → `edgeAfterWrite`。
**その中央出口を通らずに予約台帳を書く経路が4つある。**

| | 経路 | 何が起きるか | 対処 |
|---|---|---|---|
| A | `doPost`（`LineBooking.js:170,175`） | 旧経路。`makeReservationLine` を直接呼ぶ。**公開Web Appなので到達可能** | 中央出口へ通す |
| B | `liffApi`（同:198,211） | 旧経路（HtmlService用・いまは未使用）。同じく直接呼ぶ | 中央出口へ通す／閉じる |
| C | `dailySync`（6時間ごと・同:4496 で `setValues`） | **カレンダー取込が予約を台帳に足す。** D1には翌日の全体同期まで入らない | 足した行の `customer_id` を重複除去してキューへ |
| D | `autoBookRecurringPatterns`（毎月25日・同:6699 で `_lbReserveCore` 直呼び） | 固定枠の自動予約がD1へ伝わらない | **1件でも成功した会員だけ**キューへ |

★Dは「対象会員全員」ではなく**成功した会員だけ**積む。`order` には予約できなかった会員も入る。

### 揃っているかを機械で検査する（文字列検索だけでは足りない）
中央出口が1箇所なので、「呼び出し箇所を数える」検査では意味が無い。別々に固定する：

```
① EDGE_AFTER_WRITE の16キー ⊆ _lbDispatch の case
② 予約・契約・紐付けを書き換える case ⊆ EDGE_AFTER_WRITE
③ _lbReserveCore を直接呼んでいる場所の一覧（増えたら気づく）
④ line_reservations へ appendRow / setValues している場所の一覧（同）
⑤ doPost / liffApi が中央出口を通ること
```

許可リストが3箇所にあって1つだけ直し忘れた事故（2026-10-07）の再発防止。

## 7. 3-b へ進む条件（14日待たない形に置き換える）

## 8. この設計で壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 作り直しの範囲外の引当が取り残される | **`from` を記録開始月にするだけでは足りない**（下記★） |
| ② | トリガーが動かない時間帯に書き込みが集中すると、キューが伸びる | 上限200＋溢れを記録。日次の作り直しが追いつかせる |
| ③ | 作り直しの最中にもう1件予約が入る | 作り直しは会員単位で原子的（期間の引当を全削除→全挿入）。後から来たぶんは次のトリガーで入る |
| ④ | `scope:'customer'` の削除が広がる | WHERE に customer_id を必ず入れる。テストで固定。rows に他人が混ざったら400 |
| ⑤ | 3-a のあいだ、D1の引当が数秒〜1分古い | **読む処理が無いので無害。** 3-bの前に同期呼び出しへ戻す（第4節） |
| ⑥ | 未登録客の仮押さえ・ブロック枠は会員が無い | 引当も要らない（`consumes_quota = 0`）。キューに積まない |
| ⑦ | 旧経路（`doPost`）から予約が入ると写しが直らない | 中央出口へ通す（第6節A） |

### ★①の詳細：記録開始月より前の引当は、いまの削除では消えない（Codex関門①）

```sql
-- いまの削除（alloc-build.js）
DELETE FROM reservation_allocations
 WHERE customer_id = ? AND resv_month >= ? AND resv_month <= ?   -- 期間の中だけ
-- ＋ 今回入れ直す予約IDで直接消す（80件ずつ）
```

したがって次の行は**どちらにも引っかからず残る**：
```
customer_id = C123
resv_month < 新しい recordsFrom
かつ 今回作る引当には含まれない
```

`recordsFrom` は固定ではなく動く：
```
棚卸しが承認されたら   そのcutover月（LineBooking.js:3445）
棚卸しが無ければ       その会員の登録月（同:3475）
selfRegister 等が      LINKED_AT を書く（同:583）
```
つまり**あとから棚卸しが承認された／登録情報を作り直した／以前に広い範囲で
手作業 build した**とき、旧い引当が取り残される。

→ 会員ぶんの作り直しの同じバッチに足す：
```sql
DELETE FROM reservation_allocations WHERE customer_id = ? AND resv_month < ?   -- recordsFrom より前
```
記録開始月より前は「完全な予約履歴として扱わない領域」なので、
**引当が存在すること自体が不整合。**

### ★`to` も固定にしない（Codex関門①）
「当月+2」と決め打つと、それより先の予約の引当が取り残される。
→ `to` は **その会員の confirmed/consumed 予約の最大月**（ただし最低でも当月+2）。
   予約を取れる地平が将来広がっても壊れない。

## 9. 実装の順序

```
0. いまのトリガー本数をハンドラ別に数える（20本の上限に対する余裕を確かめる）
1. 引当の削除範囲を直す（recordsFrom より前を消す・to を予約の最大月まで）
2. ingest に scope:'customer' を足す（世代方式・same-skip無効・同一batch）
3. GAS：その会員の計算入力を押す _edgePushCalcResvFor(cid)（null と [] を区別）
4. GAS：世代付きの待ち行列（enqueue／トリガー作成を同一ロック）
5. GAS：作り直しを行うトリガーのハンドラ（version を確かめて外す）
6. GAS：中央出口（edgeAfterWrite）からキューへ積む
7. GAS：抜けている4つの入口を繋ぐ（doPost・liffApi・dailySync・autoBook）
8. 入口の網羅を5つの検査で固定
9. 日次の照合＋通知＋キューの作り直し
10. 入口を1回ずつ実際に通す（③）＋固定枠の自動予約（④）
```
