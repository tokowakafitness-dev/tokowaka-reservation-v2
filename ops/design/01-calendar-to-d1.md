# ① カレンダー → D1（設計・第4版）

**目的**：空き枠の判定に必要な材料をD1に持ち、スプレッドシート（`slots_*`）を経由しない状態にする。

**この段の性質**：**読み取りのみ。カレンダーには一切書かない。**
画面はこれまでどおりGASの答えを表示する。Workerの答えは**比較のためだけ**に取る。

---

## 第3版で何を変えたか（最も重要な判断）

第2版は「増分同期（syncToken）＋地平の作り直し」の二本立てだった。
これに対する敵対的レビューで、**設計の土台を壊す事実**が出た。

> **Google Calendar API は、`syncToken` と `timeMin` / `timeMax` を同時に指定できない。**

つまり「地平を区切って増分同期する」は**そもそも実装できない**。
さらに、二本立てにしたことで以下が芋づる式に必要になっていた。

- 作り直しと増分同期の排他（フェンシング付きロック）
- 両者が同時に走ったときの取りこぼし対策
- `410 Gone` でのトークン破棄と再構築
- カレンダーごとに世代がずれる問題（公開の単位）

**これらは全部、増分同期を採ったことから生まれた複雑さである。**

### 規模を見直した

| | 実際の数 |
|---|---|
| カレンダー | 4つ（トレーナー3＋B1） |
| 予定の総数 | 地平2ヶ月で数百件 |
| 変更の頻度 | 1日に数件 |

**この規模で増分同期を使う理由がない。** 毎回まるごと取り直しても、
4回のAPI呼び出しで1〜2秒である。

### だから、増分同期をやめる

```
毎回、地平の全範囲を4カレンダーぶん取り直す（singleEvents=true）
  ↓
中身が前回と同じなら、何も書かない（確認時刻だけ更新）
  ↓
違えば、新しい世代として書き、検査してから公開する
```

**これで上に挙げた複雑さが全部消える。**
同期の経路が1つになり、世代も4カレンダーまとめて1つになる。

## 1. 対象カレンダー

空き枠の判定に**実際に使われているもの**を、コードで確認して確定した。

| カレンダー | 空き枠に効くか | 根拠 |
|---|---|---|
| トレーナーA/B/C（各自） | **必須** | シフト・休憩・ブロック・予約を保持 |
| **B1（部屋）** | **必須** | `buildAvailableSlots` が `calB1.getEvents()` で部屋の埋まりを見ている |
| 1F（部屋） | **いまは使わない** | 「通常予約はB1のみ」（コード.js）。`LB_1F_TRAINER_BLOCK=on` のときだけ効く。**既定OFF** |

> ★第1版の誤り：B1を「後回しでよい」とした。**B1を欠くと、部屋が埋まっている時間を
> 「空いています」と3人分まとめて誤表示する。**

**①で同期するのは4つ。** 1Fは実装しない。
ただし **`LB_1F_TRAINER_BLOCK` が `on` になっていたら、D1の空き枠を使わない**（後述の可否判定）。
設定が変わったのに実装が追いついていない状態を、黙って通さない。

## 2. 地平（取得する範囲）

運用で決まっている。

```
当月末まで ／ 毎月25日以降は翌月末まで
（20日シフト提出 → 25日翌月解禁）
```

**具体値（Asia/Tokyo・半開区間 `[start, end)`）**

```
horizon_start = 当日の 00:00
horizon_end   = 24日まで → 翌月1日の 00:00
                25日以降 → 翌々月1日の 00:00
```

> `horizon_start` を「同期した時刻」にしてはいけない。毎分値が変わり、
> 中身が同じでも必ず新しい世代が作られる。**当日00:00に丸める。**

**毎回この範囲を丸ごと取る。** `singleEvents=true` で繰り返し予定を展開して受け取る。

> ★第2版の誤り：増分同期だけでは「変わっていない未来の予定」が取れないため、
> 25日に地平が伸びた瞬間に翌月のシフトが丸ごと欠ける、という問題があった。
> **毎回丸ごと取るので、この問題自体が存在しない。**

## 3. 分類の仕様

分類は**カレンダーの役割ごとに意味が変わる。** 仕様として確定させる。

### トレーナーのカレンダー

| タイトル | 効果 | 判定 |
|---|---|---|
| `isShiftEvent()` が真 | **shift**（この中でだけ予約できる） | 部分一致 |
| `[RESERVED]` で始まる | busy | 先頭一致 |
| `✅` で始まる | busy | 先頭一致 |
| `休憩` を含む | busy | 部分一致 |
| `ブロック` を含む | busy | 部分一致 |
| それ以外 | ignore | — |

**優先順位**：上から順に見て、最初に当たったものを採る。
（例：「シフト」と「ブロック」を両方含むタイトルは **shift** になる）
既存GASと同じ評価順になっていることを、タイトルと期待結果の対応表で固定する。

### B1（部屋）

| タイトル | 効果 |
|---|---|
| `[消化]` で**始まる** | **ignore**（席は空いている） |
| それ以外すべて | **room_busy**（全トレーナーに効く） |

> ★第1版の誤り：「種類と時間だけ持つ」とした。B1の `[消化]` は
> 「予定はあるが席は空いている」という特別扱いで、これを取りこぼすと
> **消化済みの時間が永久に予約不可になる。**

### 既存の実装が3箇所で食い違っている

| 場所 | 休憩・ブロックを busy 扱いにするか |
|---|---|
| 空き枠の生成（コード.js） | する |
| 体験予約の空き確認（コード.js） | **しない**（`[RESERVED]` と `✅` のみ） |
| LINE予約の空き確認（LineBooking.js） | する |

**「既存を踏襲する」では、どれに合わせたか決まらない。**
①は上の表（空き枠の生成＝LINE予約と同じ）に合わせる。
体験予約との差は**仕様の差として残し**、揃えるかは別途判断する。

分類は**タイトルと期待結果の対応表**をテストとして持つ。

## 4. D1に持つ形

```sql
-- 世代（4カレンダーまとめて1つ）
calendar_snapshot(
  generation      INTEGER PRIMARY KEY,
  status          TEXT NOT NULL,     -- building / ready / rejected
  horizon_start   INTEGER NOT NULL,  -- 取得した範囲
  horizon_end     INTEGER NOT NULL,
  calendars       TEXT NOT NULL,     -- idと役割の対応（JSON）
                                     -- [{"calendar_id":"...","role":"trainer","trainer_id":"B"}, ...]
                                     -- ★idの配列ではなく対応を持つ。短絡判定と可否判定の両方で
                                     --   「いまの構成と同じか」を比べるため
  rule_version    INTEGER NOT NULL,  -- 分類規則の版
  flag_1f         TEXT NOT NULL,     -- 取得時の LB_1F_TRAINER_BLOCK
  content_hash    TEXT NOT NULL,     -- 中身が変わったかの判定に使う
  built_at        INTEGER NOT NULL,  -- この世代を作り終えた時刻
  created_at      INTEGER NOT NULL
)

-- 公開中の世代（1行だけ）
calendar_active(id INTEGER PRIMARY KEY CHECK (id = 1), generation INTEGER, checked_at INTEGER)

-- 予定
calendar_events(
  generation   INTEGER NOT NULL,
  calendar_id  TEXT NOT NULL,
  event_id     TEXT NOT NULL,
  role         TEXT NOT NULL,   -- trainer / capacity_b1
  trainer_id   TEXT,            -- role=trainer のとき
  effect       TEXT NOT NULL,   -- shift / busy / room_busy / ignore
  reason       TEXT NOT NULL,   -- shift / reserved / break / block / consumed / room / other
  start_at     INTEGER NOT NULL,
  end_at       INTEGER NOT NULL,
  all_day      INTEGER NOT NULL,
  PRIMARY KEY (generation, calendar_id, event_id)
)
```

**★タイトルそのものは持たない。** 予約の予定には会員の氏名が入る。
分類は同期のときにメモリ上で行い、**結果だけを残す。**
（第1版の `title_hash` は削除。氏名は総当たりで復元できるため意味がない）

### 2つの時刻を分ける

> ★第2版の誤り：`completed_at` 1つで「最後に書いた時刻」と「鮮度」を兼ねようとして矛盾した。
> 変更がない間は書かない設計なのに、鮮度をその時刻で見ると、
> **2分変更がないだけで必ずD1が使えなくなる。**

| | 意味 | 更新のタイミング |
|---|---|---|
| `calendar_active.checked_at` | Googleに聞いて正常に確認できた時刻 | **変更がなくても毎回**（1行だけ） |
| `calendar_snapshot.built_at` | その世代を作り終えた時刻 | 世代を作ったときだけ |

**鮮度は `checked_at` で見る。**

## 5. 同期の手順

> **第4版での訂正（2026-10-02・実装時に判明）**
>
> この節は「Workerが自分でカレンダーを読む」前提で書かれている。第4版でGASが読む形に
> 変えたため、以下は当てはまらない。実装は `gas/PushToEdge.js` の `buildCalSyncPayload` と
> `worker/src/routes/calsync.js` にある。
>
> | 記述 | 実際 |
> |---|---|
> | `maxResults` / `nextPageToken` / 20ページ | **ページングは無い**。GASの `getEvents` が一括で返す |
> | 「ページを取り終えていない」の検査 | 該当しない。代わりに**構成の検査**（B1が1つ・トレーナー3人以上）で揃っているかを見る |
> | 中身の印（ハッシュ）にメタデータを含める | GASは**予定だけ**をハッシュする。地平・規則の版・1Fフラグ・カレンダー構成は<br>Workerが**別に比べる**ので穴は無い |
> | `calendar_lock` / `owner_token` | **作らない**。Workerが同期しなくなったのでロックの対象が無い。<br>巻き戻しは公開の瞬間の条件付き更新（active.generation の比較）で防ぐ |
> | 「`ignore` の割合が急に増えた」の検査 | **観測できない**。GASは `ignore` を送らないため。<br>見たければGASが件数だけ送る必要がある |



```
1. 地平を計算する（当月末／25日以降は翌月末）
2. 4カレンダーを全部取る（`singleEvents=true`）
   - `maxResults = 250`。`nextPageToken` が無くなるまで取る（**1カレンダーあたり上限20ページ**）
   - 429 / 5xx は短い指数バックオフ＋ゆらぎで再試行
   - **同期全体の期限は20秒**（読み取り時の同期は5秒）。超えたら中止し、公開中の世代をそのまま使う
   - 再試行は**1リクエストあたり2回まで**（0.5秒・1.5秒＋ゆらぎ）
   - ページ数・件数・所要時間を記録する。**1カレンダー5,000件**を超えたら公開しない
   - 1つでも失敗したら中止。公開中の世代はそのまま

   > 「4回のAPI呼び出しで1〜2秒」は**前提ではなく、初期の実測値と監視の対象**である。
   > 1カレンダーが1ページに収まる保証はない。
3. 分類して、中身のハッシュを作る（**正規形を固定する**）

   APIの応答をそのままハッシュしてはいけない。並び順やキーの順が変わるだけで
   毎回「変わった」ことになる。逆に、空き判定に使う項目を落とすと
   **本当に変わっているのに「同じ」**と判定される。

   ```
   各予定を次のタプルにする
     calendar_id / role / trainer_id / event_id / effect / reason
     / start_at / end_at / all_day
   → calendar_id, event_id, start_at, end_at の順に並べ替える
   → 世代のメタデータを頭に付ける
     hash_format_version / horizon_start / horizon_end / rule_version
     / flag_1f / カレンダーidと役割の対応 / タイムゾーン(Asia/Tokyo)
   → **固定順のJSON配列にして UTF-8 でバイト列にする**
      （区切りは JSON の仕様どおり。`null` は `null` と書く。数値は整数のまま）
   → SHA-256（16進の小文字）
   ```

   **既知の入力に対する期待ハッシュをテストに置く。** 直列化の仕方が変わったら落ちるようにする。

   **event_id をハッシュに含める。** 含めないと、Google側で予定が作り直されて
   idが変わっても「同じ」と判定される。
4. **「同じ取得仕様で、同じ中身だったか」**を見る
   ├ 次が**全部**一致 → checked_at だけ更新して終わり（D1の書き込み1行）
   │    content_hash ／ horizon_start ／ horizon_end
   │    ／ カレンダーidと役割の対応 ／ rule_version ／ flag_1f
   └ 1つでも違う → 5へ

   > ★ここを `content_hash` だけで判定してはいけない。
   >   毎月25日に地平が翌月末まで伸びても、**その範囲にまだ予定が1件も無ければ
   >   中身のハッシュは前と同じ**になる。すると新しい世代が作られず、
   >   `horizon_end` が古いままなのに `checked_at` だけ新しくなり、
   >   **翌月の要求が永久にGASへ落ち続ける。**
   >   昨日（2026-09-29）踏んだ「古いものが新しく見える」のと同じ種類の罠。
5. 新しい世代として calendar_events に書く（status=building）
6. 検査する（後述）。落ちたら status=rejected にして公開しない
7. **公開する。** 次の3つを **1回のまとまり（D1のbatch）で全部成功か全部失敗か**にする
   - snapshot を status=ready
   - calendar_active の generation を切り替え
   - checked_at を更新

   **その際、次の条件を満たすときだけ成功させる（条件付き更新）。**
   - 自分がまだロックの所有者であること（`owner_token` が一致）
   - `calendar_active.generation` が、同期を始めたときに読んだ値のままであること

   > ★ロックがあるだけでは足りない。同期に数秒かかる以上、
   >   「Aが止まる → ロック期限切れ → Bが公開 → Aが復帰して古い結果を公開」
   >   という巻き戻しが起きる。**公開の瞬間に条件を確かめる**ことでしか防げない。

   条件が変わっていたら公開せず、次の同期に任せる。
   世代の番号は、並行しても衝突しない採り方にする（`MAX+1` は使わない）。
8. 古い世代は、しばらく置いてから消す（後述）
```

**同期の経路はこれ1つだけ。** 作り直しと増分の競合という問題が存在しない。

### 同時に走らせない

```sql
calendar_lock(
  id INTEGER PRIMARY KEY CHECK (id = 1),
  owner_token TEXT,      -- 取った人を表す使い捨ての文字列
  expires_at  INTEGER    -- 期限（例：同期の期限＋30秒）
)
```

取り方：`UPDATE calendar_lock SET owner_token=?, expires_at=? WHERE id=1 AND (owner_token IS NULL OR expires_at < ?)`
→ **更新された行数が0なら取れていない。** 取れなければ同期せず、公開中の世代をそのまま使う。

**世代の番号は `MAX+1` で採らない。** `calendar_snapshot.generation` を
`INTEGER PRIMARY KEY AUTOINCREMENT` にして、挿入時に採番させる。

### ★D1では「まとまり」だけでは守れない

D1のbatchは、**条件に合わず0行更新でも「成功」**として扱われる。
「batchにしたから全部成功か全部失敗」にはならない。

だから公開のときは：

- 公開に関わる**すべての更新に同じ条件を付ける**
  （`owner_token` が自分／`active.generation` が同期開始時に読んだ値）
- **更新された行数を数え、0なら公開失敗として扱う**（世代は `building` のまま残す）

**変更が無くて `checked_at` だけ更新するときも、同じ条件を付ける。**
古い同期が、新しい同期の結果を上書きしないようにするため。

### 誰が呼ぶか（第4版で変更・2026-10-02）

```
GASの時間主導トリガー … 1分ごと（カレンダー全量を読んでD1へ押し出す）
予約の確定・変更・取消 … その場で押し出す（既存の edgeAfterWrite に相乗り）
```

**Workerはカレンダーを読まない。** 読み取り時にその場で同期することもしない
（Workerからカレンダーに届かないため）。

**「常に1分以内」とは言えない。** トリガーが詰まることはある。
正しくは「**正常時の目標が1分、上限2分**」。上限を超えたらD1を使わずGASへ落とす。
顧客から見れば「遅くなる」だけで、誤った空き枠は出ない。

## 6. 公開前の検査

**止める条件**（1つでも当たれば公開しない・`status=rejected`）

| | 内容 |
|---|---|
| 取得 | 4つのカレンダーのどれかが取れなかった |
| 取得 | ページを取り終えていない |
| 中身 | `end_at <= start_at` の予定がある |
| 中身 | 日時が読めない／必須項目が欠けている |
| 中身 | 同じ `(calendar_id, event_id)` が重複している |
| 中身 | 地平と**まったく重ならない**予定がある（`start_at < horizon_end AND end_at > horizon_start` を満たさない） |
| 運用 | **トレーナー3人全員**の出勤が0件 |

**警告にとどめる条件**（公開はするが記録して知らせる）

| | 内容 |
|---|---|
| 運用 | 1人または2人の出勤が0件（休業・休職がありうる） |
| 傾向 | 前の公開世代から件数が半分以下 |
| 傾向 | ページ数・処理時間が急に増えた |
| 傾向 | `ignore` の割合が急に増えた |

> ★第3版の初稿は「1つでも落ちたら公開しない」と書きながら、
>   出勤0件は警告としており矛盾していた。また対象は3人なのに「4人中3人以上」と書いていた。

**落ちた世代も残す**（原因を追えるようにするため）。

## 7. D1を使ってよいかの判定（1箇所にまとめる）

**すべての読み取りが必ずこの関数を通る。**

```
D1を使ってよい ＝
  calendar_active.generation がある
  かつ その世代の status = ready
  かつ checked_at が2分以内
  かつ 世代の rule_version が今のコードと一致
  かつ 世代の calendars に必要な4つが全部入っている
  かつ 要求された日時が [horizon_start, horizon_end) に完全に入っている
  かつ 世代の flag_1f が現在の設定と一致（＝1Fが on なら使わない）
```

> **地平を持っているかを必ず見る。** 25日に地平が伸びたのに作り直しが失敗していると、
> `checked_at` は新しいのに翌月のデータが無い、という状態になりうる。

判定に落ちたらGASへ落とす。**GASも失敗したら、空の配列（＝空きなし）を返さず、明示的にエラーを返す。**
「空きなし」と「分からない」を同じ見た目にしない。

### 読み取りは1回のSQLでまとめて取る

可否判定と予定の取得を別々のSQLにすると、**その間に世代が消される**おそれがある。
`calendar_active` との結合で一度に取る。

**ただし「使えるが予定が0件」と「そもそも使えない」を区別できる形にする。**
単純な内部結合だと、どちらも0行になって見分けがつかない。

```
返すもの： usable = 1 / 0
           reason = stale / horizon / rule / flag / missing（使えないとき）
           events = 予定の配列（使えるとき。0件もありうる）
```

重なりの判定は統一する：`event.start_at < 要求の終わり AND event.end_at > 要求の始まり`

## 8. 古い世代の削除

- 残すもの：**公開中の世代 ＋ 過去に公開された ready な世代 2つ**
- `building` のまま長く残ったものは、ロックの期限切れを確かめてから `rejected` にして消す
- `rejected` は24時間残す（原因を追うため）
- 予定の削除と世代の削除は**同じまとまり**で行う
- **SQLの条件で、公開中の世代を必ず除外する**
- 削除に失敗しても、同期や公開は失敗させない

## 9. 終日予定と日またぎ

- `start.dateTime`（時刻あり）と `start.date`（終日）を別に扱う。
- 終日は **Asia/Tokyo** で `[当日00:00, 翌日00:00)` に変換する。
  **UTCの00:00として扱うと、日本時間では前日9時からになり、前日の枠を誤って塞ぐ。**
- ミリ秒への変換は1箇所に集約する。
- 日をまたぐシフト・ブロックはそのまま区間として持つ（日で切らない）。

## 10. 認証（第4版で全面的に変えた・2026-10-02）

### 結論：Workerはカレンダーを読まない。GASが読んでD1へ押し出す。

**当初の設計は「Workerがサービスアカウントで直接カレンダーを読む」だった。
これをやめる。** 理由は2つ。

**① 組織ポリシーがサービスアカウントの鍵の作成を禁止している**

```
iam.disableServiceAccountKeyCreation
```

実際にオーナーがサービスアカウントを作って鍵を発行しようとして止まった。
**このポリシーは緩めない。** 鍵は「置き場所」「漏洩」「期限切れ」の3つの事故を
生むので、持たないのが正しい。組織がそれを強制しているのは良い設定である。

鍵を使わない方法（Workload Identity 連携）も検討したが、Cloudflare Workers は
OIDCトークンを発行しないため、**自前でJWTを署名することになり結局は鍵を持つ。**
仕組みだけ複雑になって目的を達成しない。

**② ①は移行期間だけの仕組みである**

```
①  カレンダー → D1   （いまここ。移行のため）
③  予約の正本をD1へ
    ↓
③が終わると向きが逆になる： D1 → カレンダー（書き出し）
    ↓
★①の「カレンダー → D1」は役目を終えて消える
```

**捨てるものに認証の仕組みを作り込むのは投資の誤りである。**
①でGASを外しても、③でまた作り直すことになる。

### 顧客の速度は落ちない（ここを取り違えない）

速度を決めるのは**顧客が読むときの経路**であって、D1に入れる側ではない。

```
裏側（顧客は待たない）              表側（顧客が待つ）
GAS → カレンダー読む → D1  ／  顧客 → Worker → D1 → 250ms
     1分ごと・数秒
```

**D1に誰が書くかは、顧客の待ち時間に影響しない。**

### 鮮度

| きっかけ | 遅れ |
|---|---|
| 定期（1分ごとのトリガー） | 最大1分 |
| **予約・変更・取消が入った瞬間** | **ほぼゼロ**（既存の `edgeAfterWrite` が押し出す） |
| オーナーがカレンダーを直接編集 | 最大1分 |

当初の設計は「30秒を目標・上限2分」だった。**予約直後が即時反映される分、
GAS経由の方が速い場面がある。**

### GASが読む権限

**いまGASが持っている権限をそのまま使う**（`auth/calendar`）。新しい認証を増やさない。
サービスアカウントは作らない。

### この変更で不要になったもの

- サービスアカウントの作成・鍵の管理・90日ごとのローテーション
- Cloudflare Secret への鍵の登録
- 鍵の台帳（`90_ops/`）
- JWT・アクセストークンをログに出さない規則（そもそも扱わない）

### 残る注意点

- **GASの実行時間（6分）に収まること。** 4カレンダー・地平2ヶ月・数百件なら数秒。
  収まらなくなったら分割する（カレンダーごと・期間ごと）
- **GASが止まるとD1が更新されない。** 鮮度の判定（§7）が効いて、古ければGASへ落ちる。
  つまり「遅くなる」だけで「誤った空き枠を出す」ことにはならない
- **GASの1日あたりの実行時間の上限。** 1分ごと×数秒なら余裕がある。
  日次の点検（`dailyHealthCheck`）で実行時間を見る

## 10'. （廃止）サービスアカウントによる認証

> **この節は実施しない。** 上の §10 のとおりGAS経由に変えた。
> 判断の経緯を残すために記述は消さずに置く。

**専用のGoogleプロジェクト＋専用のサービスアカウントを作る。**
オーナー個人アカウントのトークンは使わない。

| | 設定 |
|---|---|
| スコープ | `https://www.googleapis.com/auth/calendar.readonly`（①は読み取りのみ） |
| 共有 | 対象4カレンダーに**個別に**「**すべての予定の詳細を表示**」 |
| ドメイン全体の委任 | **使わない** |
| 有効にするAPI | Calendar API のみ |
| 鍵の置き場所 | Cloudflare の Secret。CEOは値を見ない。オーナーが登録する |
| 鍵の更新 | 90日ごと。鍵ID・作成日・失効日を `90_ops/` の台帳で管理 |

> **「予定の表示（時間だけ）」では足りない。** `[消化]` や `[RESERVED]` の区別にタイトルが要る。
> **サービスアカウントは予定に含まれる会員の氏名を読める。** オーナーに明示して承認を得る。

> 現在GASが持つ `auth/calendar` との比較：スコープは操作の種類を、共有は対象を絞る。
> サービスアカウントは自分のカレンダーを持たず、共有された4つしか見えないため、**対象の面で確実に狭い。**

**②（書き込み）に進むときは、読み取り用を昇格させず、書き込み用の別アカウントを作る。**

**ログの禁止事項**：JWT・アクセストークン・Google APIの応答本文をログに出さない。

## 11. 「読み取りのみだから影響しない」の検証

| 影響 | 見積もり・対策 |
|---|---|
| Google APIの呼び出し | 4カレンダー×1,440回/日＝**5,760回**（上限100万回/日）。専用プロジェクトで既存GASと分ける |
| D1の書き込み | **変更がない回は1行**（`checked_at` のみ）＝1,440行/日。<br>変更があった回だけ数百行。1日数件の変更なら**合計3,000行未満**（上限10万行/日） |
| 比較処理が画面を遅くする | **比較は画面の応答から完全に切り離す。** 失敗しても表示に影響させない |
| 費用 | Worker・D1・Google API それぞれに上限と警告を設定する |

切り替えるのは③（読み取りの切り替え）であって、①ではない。
