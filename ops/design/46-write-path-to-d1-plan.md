## 2. Worker＋D1 で確定し、カレンダー・シート・通知は後から GAS が反映する形にしたとき

### 2-1. 形

```
LIFF ──(予約・取消・変更)──▶ Worker
   1 ID トークンの確認（Worker に既にある auth.js）
   2 操作ID（再送なら元の結果を返す）
   3 判定の材料を D1 から読む：会員・契約の入力・その会員の予約・トレーナーの出勤と埋まり（calendar_events）・その時間の予約
   4 判定：締め切り・予約できる最終日・受付の関門・連続ルール・残数（allocate.js をそのまま回す）・重なり
   5 D1 に1回の batch：予約の行／その会員の引当の入れ替え（I30 と同じ形）／後始末の行（outbox）／操作ID
        ＋見張り（会員ごとの版の比較・重なり）が外れたら batch 全体を巻き戻す
   6 応答（ここまで約1秒未満）
   ── 応答の後 ──
   7 Worker が GAS を1回呼ぶ（ctx.waitUntil・速い道）→ GAS が outbox を取り出して
        B1・トレーナー個人カレンダーに予定（予定ID は予約IDから決める＝二重に作らない・設計04 §6）
        台帳に行／振替権・cancel_notes の書き出し／LINE 通知
   8 速い道が落ちても、5分ごとの既存のトリガー（lbCalSyncTick）に相乗りして取り出す（安全網）
```

★設計04 §5 からの変更点（関門①で問う）：**残数の条件を SQL の1文に書かない。** 設計04 は `used + 1 <= quota` の条件つき INSERT を想定していたが、いまの割当器（alloc-3）は FEFO・前借り（lent）・未来月の繰越・ペアの人数を扱う。SQL の1文に写すと GAS の答えとずれる（MODEL §8「値を別の場所から作り直すとき」）。代わりに**その会員ぶんを Worker が割当器で計算し直し、会員ごとの版を比べてから書く**（楽観的な排他）。`/quota/rebuild`（I30）がいま1名を1つの batch で入れ替えているのと同じ形で、I1（used はトリガーだけ）・I4（期間を消して入れ直す）・I3（枠と引当は同じ batch）をそのまま守れる。

### 2-4. トレーナー・オーナーが Google カレンダーに直接入れた予定との衝突

事実（コード）：
- トレーナー個人カレンダーで「埋まり」になるのは `[RESERVED]`・`✅`・「休憩」・「ブロック」を含む予定だけ（コード.js:294）。それ以外の私用の予定（例：通院）は**今も予約を止めない**。出勤は「出勤」「シフト」等を含む予定（:315）。
- いまは確定の瞬間に GAS がカレンダーを直接読むので、直接入れた休憩・ブロック・シフトの削除は**即座に**効く。
- D1 の `calendar_events` は5分ごと（＋予約の直後）の同期。S4 の後は、直接入れた変更が**最大約5分**予約に効かない。

塞ぎ方（推奨の順）：
1. **数える（S1）。** write-shadow（§4 S1）で「GAS がカレンダーを直接読んだ答え」と「D1 の calendar_events で出した答え」が食い違った回数と母数を毎日数える。食い違いの理由（出勤なし・休憩・ブロック・B1）別に。**ここが0か、ほぼ0なら5分の窓を受け入れる根拠になる。**
2. **後から反映するときに確かめる（S4）。** outbox の取り出しでカレンダーを書く直前に、GAS がその時間のトレーナー個人カレンダーと B1 を読み直す。直接入れた予定と重なっていたら、**予約は生かしたまま**「要対応」に積み、担当とオーナーへ知らせる（自動では取り消さない＝顧客にはもう完了と出ている・設計04 §13-4）。§6 Q2。
3. **画面から入れる道を勧める（運用）。** 休憩・ブロックはトレーナー画面（`makeBlock`）から入れれば D1 に即入る。直接入力を禁止はしない（わざと通している例外を止めない）。
4. 出勤の削除で既存の予約が出勤の外に出る形は今もある（直接入力が後から来る場合）。この計画で悪くならない。

## 5. いまの GAS の重複読みを削る中間策は推奨しない

- 対象：名簿を最大4回・台帳を3回・残数の計算を4回（CEO の数え。`getCustomerByLine`・`getBookableRemaining`（:4592 契約の全履歴・:4595 台帳）・`edgeAfterWrite` の名簿の引き直し・変更のトレーナー宛の残数の文 等）。
- 見込み：pre 2.9秒と remain 1.7秒の一部、2〜3秒。
- **捨てる仕事になる。** 会員の3操作は S4 で GAS を通らなくなる。S3 の時点で remain（残数の判定）は Worker に移る。残る GAS の読みも S5 で消える。効果がある期間は「実装の後〜S4」のおよそ4〜5週間だけ。
- 費用：実装1〜2日＋関門②＋GAS 反映（ほかとまとめても関門の手間は増える）。読みを共有にすると「ロックの外で読んだ値をロックの中で使う」古さの穴を新しく作りうる（取消は I-C7 でロックの外の名簿読みを意図して1回にしている）。
- **推奨しない。** 同じ手間は S1〜S4 を早める方に使う。

## 7. 不変条件（S2 以降の設計で MODEL §3 に足す予定・検査はその設計で紐付ける）
- 予約の確定を書くのは Worker だけ（S3 以降）。GAS は予約の正本を書かない（outbox の反映だけ）。
- 台帳→D1 の予約の押し出しは、切り替えた範囲では止める（向きは D1→台帳だけ）。
- 確定の batch は「予約・引当の入れ替え・outbox・操作ID・見張り」を全部か無か。残数の判定は allocate.js（単一ソース）の答えで、会員ごとの版が一致したときだけ書く。
- 自分が書いたカレンダーの予定（拡張プロパティ reservationId）を、空き枠・埋まりの材料に読み戻さない。
- 後始末の失敗で予約を取り消さない。
