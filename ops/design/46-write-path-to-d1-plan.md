## 2. Worker＋D1 で確定し、カレンダー・シート・通知は後から GAS が反映する形にしたとき

### 2-1. 形

```
LIFF ──(予約・取消・変更)──▶ Worker
   1 ID トークンの確認（Worker に既にある auth.js）
   2 操作ID（再送なら元の結果を返す）
   3 判定の材料を D1 から読む：会員・契約の入力・その会員の予約・トレーナーの出勤と埋まり（calendar_events）・その時間の予約
   4 判定：締め切り・予約できる最終日・受付の関門・連続ルール・残数（allocate.js をそのまま回す）・重なり
   5 D1 に1回の batch：予約の行／その会員の引当の入れ替え（I30 と同じ形）／後始末の行（outbox）／操作ID
        ＋見張り（会員ごとの版の比較・重なり）が外れたら batch 全体を巻き戻す
   6 応答（ここまで約1秒未満）
   ── 応答の後 ──
   7 Worker が GAS の反映役を起こす（確定の直後・ctx.waitUntil・速い道・通常 数秒〜数十秒＝Q4 訂正）→ GAS が outbox を取り出して
        B1・トレーナー個人カレンダーに予定（予定ID は予約IDから決める＝二重に作らない・設計04 §6）
        台帳に行／振替権・cancel_notes の書き出し／LINE 通知
   8 速い道が落ちても、1分ごとの拾い役が起こし直す（§4-3・Q4 訂正）。さらに5分ごとの既存のトリガー（lbCalSyncTick）にも相乗りして取り出す（最後の安全網・起こす経路そのものが壊れたとき）
```

★設計04 §5 からの変更点（関門①で問う）：**残数の条件を SQL の1文に書かない。** 設計04 は `used + 1 <= quota` の条件つき INSERT を想定していたが、いまの割当器（alloc-3）は FEFO・前借り（lent）・未来月の繰越・ペアの人数を扱う。SQL の1文に写すと GAS の答えとずれる（MODEL §8「値を別の場所から作り直すとき」）。代わりに**その会員ぶんを Worker が割当器で計算し直し、会員ごとの版を比べてから書く**（楽観的な排他）。I1（used はトリガーだけ）・I4（期間を消して入れ直す）・I3（枠と引当は同じ batch）はそのまま守れる。

★**`/quota/rebuild` はこの排他の実例ではない**（関門 Codex 指摘1・quota-rebuild.js:14-17・140-155）。あちらは入れ替えを先に書き、最後の印（markBuilt）だけを版で条件づける＝競合しても「新しいと名乗らない」だけで、書いた引当は残る。確定の batch では次を**SQL のエラー（名前つき CHECK 違反）に変えて batch 全体を巻き戻す**（実例は karte_guard・karte.js:188-227・0025_karte.sql:232-241）。`changes = 0` は失敗にならない（設計04 §5）ので、条件つき文だけに頼らない。
- 会員の版：batch の頭で `UPDATE … SET rev = rev + 1 WHERE customer_id = ? AND rev = ?`、続けて「いまの rev が期待＋1でなければ見張りの表へ違反の行を入れる」文。
- 重なり：予約を入れた**後で**、同じ batch の中で「施設を占有する生きた予約どうしの時間の重なり」「同じトレーナーで占有する生きた予約どうしの時間の重なり」が1件でもあれば見張りへ違反の行（区間の重なりは一意制約では防げない＝60分と体験90分・設計04 §13-2）。
- 取消・変更・外部予定の取込も**同じ見張りを通す**（取込が衝突したら取込の側を「要対応」に原子的に記録・設計04 §8「先に入っていたほうを残す」）。
- 具体の SQL は S2 の設計（関門①）で書き、「見張りを1行外すと二重予約の検査が落ちる」ことを本物の SQLite で確かめる（MODEL §8・D1 の身代わりは制約を再現しない）。

### 2-4. トレーナー・オーナーが Google カレンダーに直接入れた予定との衝突

事実（コード）：
- トレーナー個人カレンダーで「埋まり」になるのは `[RESERVED]`・`✅`・「休憩」・「ブロック」を含む予定だけ（コード.js:296）。それ以外の私用の予定（例：通院）は**今も予約を止めない**。出勤は「出勤」「シフト」等を含む予定（:317）。
- いまは確定の瞬間に GAS がカレンダーを直接読むので、直接入れた休憩・ブロック・シフトの削除は**即座に**効く。
- D1 の `calendar_events` は5分ごと（＋予約の直後）の同期。S4 の後は、直接入れた変更が**最大約5分**予約に効かない。

塞ぎ方（推奨の順）：
0. ★**1F は重なりの条件に入れない**（Q5：使っていない。10月の8件は古い残り）。オンラインの予約の「トレーナーだけを塞ぐ占有」は別に設計する（この計画の外・§4 の「後で」）。
1. **数える（S1・設計54）。** write-shadow（§4 S1）で「GAS がカレンダーを直接読んだ答え」と「D1 の calendar_events で出した答え」が食い違った回数と母数を毎日数える。食い違いの理由（出勤なし・休憩・ブロック・B1）別に。**ここが0か、ほぼ0なら5分の窓を受け入れる根拠になる。**
2. **後から反映するときに確かめる（S4）。** outbox の取り出しでカレンダーを書く直前に、GAS がその時間のトレーナー個人カレンダーと B1 を読み直す。直接入れた予定と重なっていたら、**予約は生かしたまま**「要対応」に積み、担当とオーナーへ知らせる（自動では取り消さない＝顧客にはもう完了と出ている・設計04 §13-4）。§6 Q2＝**オーナー回答どおり**。
3. **画面から入れる道を勧める（運用・S3 の後）。** S3 の後は、トレーナー画面のブロック（`makeBlock`）が Worker の確定を通るので D1 に即入る。**いまの makeBlock はカレンダーに書くだけで、D1 へは予約直後のカレンダー同期で入る**（LineBooking.js:7977〜・PushToEdge.js:2473 の `EDGE_CALSYNC_AFTER`）。直接入力を禁止はしない（わざと通している例外を止めない）。
5. 外部予定（HPB・直接入力）の取込と outbox の反映がぶつかる順序（D1 で確定 → 反映の前に外部の予定がカレンダーに入る → 同期が取り込む → outbox が同じ時間に書く）は、取込も §2-1 の重なりの見張りを通すことで決める：**D1 に先に入った方が残り、後から来た取込は「要対応」に原子的に記録**される。outbox はそのまま予定を書き、担当とオーナーに知らせる（2 の確かめと同じ通知）。
4. 出勤の削除で既存の予約が出勤の外に出る形は今もある（直接入力が後から来る場合）。この計画で悪くならない。

### 4-0. 個人情報がどこに出て誰が読めるか（各段の受け入れ条件・関門 Codex 指摘12〜14）
- **outbox の payload は ID と時刻と種別だけ**（予約ID・顧客ID・トレーナーID・開始・種別）。氏名・LINE の送り先・電話は入れず、GAS が取り出したときに名簿から引く。取消の理由・ひとことは outbox に複製しない（cancel_notes の行を GAS が後から書くときは、その行から読む）。
- 終わった行（done・dead）は30日で payload を空にする（`notify_retry` の本文と同じ扱い・MODEL §2-3c）。行は消さない。例外の文・応答本文は記録しない（固定のコードだけ）。
- 見張りの窓口と作業依頼 `remaining` が返すのは**件数・最古の年齢・固定のコードだけ**。予約ID・顧客ID・日時・payload を返さない。作業依頼の結果は今と同じく読み取りの鍵が要り、`_ejScrub` を通す（I28・MODEL §8-2）。
- S1 の比べた記録は「一致／食い違いの理由のコード・入口・時刻の時」だけ。氏名・顧客IDを持たない（下4桁も持たない）。
- 全履歴の移行（S2）と照合の差分は、本番の値を公開リポジトリ（テストの固定値・設計書・PR・コミット）に貼らない。CI に出すのは種類と件数だけ。push 前の検査（I75）を通す。
- D1 の新しい表を読めるのは今の D1 と同じ（Cloudflare の管理者と Worker）。新しく人が読める場所は作らない。

### 4-3. 反映役の起こし方と5分の見張り（Q4 訂正 2026-11-24・S4 で入る）
オーナーの訂正：開始24時間以内の予約は、カレンダーへの反映が**5分**を超えたら知らせる。前提＝確定の瞬間に Worker から GAS の反映役を起こす（通常 数秒〜数十秒）、1分ごとの定期処理は取りこぼしの拾い役。

**事実（e94ff52 のコード）**
- いまの Worker は GAS を一度も呼ばない（`worker/src` に GAS の URL への送信が無い）。Worker の定期実行（cron）も `wrangler.toml` に無い。向きは常に GAS→Worker（合言葉 `EDGE_SECRET`＝ヘッダ `X-Ingest-Secret`・I15）。
- GAS の入口は `doGet`（`handleLineGet`・LINE の ID トークン）と `doPost`（LIFF・ID トークン。管理の1操作だけ `ADMIN_TOKEN`）。**鍵つきで外から GAS を起こす入口は今は無い。**
- GAS のトリガーは上限20本・本番は18本（MODEL §7）。自己修理 P1 は「足した後18本以下」を不変条件にしている（I-H5）。

**形（推奨）**
1. **起こす**：確定の batch が通ったら、Worker が `ctx.waitUntil` で GAS の Web アプリへ「起きて」だけを送る（**中身は空**＝予約ID・顧客ID・氏名を送らない）。GAS は起きたら、今までどおり GAS→Worker の向き（`EDGE_SECRET`）で outbox を取り出す。起こす要求は何も書き換えないので、誰かに URL を知られても起きる回数が増えるだけ（GAS 側で1分あたりの回数に上限を置き、超えたら黙って捨てる）。
2. **1分ごとの拾い役**：GAS の時間主導トリガーは使わない（19本目になる・自己修理の I-H5 の18本と衝突・1日1,440回の実行で無料アカウントの実行枠 90分/日を圧迫）。代わりに **Worker の cron（1分ごと）**が outbox の最古の未処理を数え、30秒より古いものがあれば上の「起こす」を送り直す。GAS の実行は「残りがあるときだけ」増える。
3. **最後の安全網**：起こす経路そのもの（GAS の Web アプリ・鍵）が壊れたときのため、5分ごとの `lbCalSyncTick` に outbox の取り出しを相乗りさせる（今の設計45・45b と同じ作法・新しいトリガーなし）。
4. **5分の見張り**：開始24時間以内の予約の未処理が5分を超えたら、担当とオーナーへ知らせる。数えるのは Worker（壊れている経路に見張りを載せない）。LINE を送れるのは GAS だけなので、知らせるのは GAS の5分ごとの相乗り（`lbCalSyncTick`）が Worker の「5分超の件数」を読んで送る＝起こす経路が壊れていても届く。**GAS そのものが止まった（実行枠の使い切り等）ときは LINE では知らせられない**（日次点検と作業依頼で読む。Worker に LINE の鍵を置くかは §4 の「後で」と同じ判断）。
5. 数：起こした回数・起こして取り出せた回数・cron が起こし直した回数・5分ごとの相乗りが拾った回数・5分超の件数を Worker で数え、日次点検へ（倒れた回数と母数）。

**未確定（CEO の守りの判断が要る）**
- **起こす要求の鍵**：GAS は要求のヘッダを読めない（今の Webhook も URL のクエリの合言葉で検証している）。①既存の `EDGE_SECRET` を逆向きにも使う（鍵は増えないが、用途が「GAS が Worker に名乗る」から「Worker が GAS を起こす」へ広がる）②起こす専用の合言葉を新しく置く（Worker の Secrets と GAS の Script Property に1つずつ・Script Property は画面から足せない＝50個の天井・切替関数で入れる）③鍵なし（中身が空で何も書かないことに頼り、回数の上限だけで守る）。CTO の推奨は②（漏れても起きる回数が増えるだけで、取り出しの鍵とは分ける）。**どれも Worker に GAS の Web アプリの URL を持たせる**（今は持っていない）。
- **Worker の cron**：`wrangler.toml` に `[triggers] crons` を足す（D1/KV の結びつけではないので作業ルール §4 の禁止には当たらないが、Worker が自分から外へ送り始める初めての変更）。無料の枠で1分ごとの cron が使えるかは未確認。
- GAS の Web アプリの起動1回あたりの実行時間（数秒）×1日の確定の件数が実行枠に収まるか（§8 の未確認と同じ・S1 で GAS の一回限りトリガーの起動の遅れと所要時間を数える＝設計54）。

## 5. いまの GAS の重複読みを削る中間策は推奨しない

## 7. 不変条件（S2 以降の設計で MODEL §3 に足す予定・検査はその設計で紐付ける）
- 予約の確定を書くのは Worker だけ（S3 以降）。GAS は予約の正本を書かない（outbox の反映だけ）。
- 台帳→D1 の予約の押し出しは、切り替えた範囲では止める（向きは D1→台帳だけ）。
- 確定の batch は「予約・引当の入れ替え・outbox・操作ID・見張り」を全部か無か。残数の判定は allocate.js（単一ソース）の答えで、会員ごとの版が一致したときだけ書く。
- 自分が書いたカレンダーの予定（拡張プロパティ reservationId）を、空き枠・埋まりの材料に読み戻さない。
- 後始末の失敗で予約を取り消さない。
