# 設計57　翌月の空き枠の見張り（日次点検）

2026-11-25・CTO（CEO 決定・オーナー「12月の予約が問題なく開放されているか」）
改訂：関門② 再審2で数え始める条件を経過3分未満に・かかった秒数を残す（版 2026-11-25d）。関門② 1回目（書き直し中の公開シート・読めないカレンダー）→ 再審で CEO 判断「書き直しの途中が見えるシートを読まない」＝読み方を枠の計算そのものに変えた（版 2026-11-25c）

## 目的（1行）
毎月25日以降、翌月の空き枠が開いていない（翌月の出勤の入れ忘れ・出勤はあるのに枠ができない）ことに、日次点検で翌朝気づけるようにする。

## 事実（読んだもの）
- 予約できる最終日は GAS `_lbBookingHorizonEnd`（gas/LineBooking.js）と Worker `slotsRange`（worker/src/routes/slots.js）。25日0時から翌月末。
- 空き枠の計算は `buildAvailableSlots(excludeStartMs, nowMsOpt)`（gas/コード.js）＝出勤（`isShiftEvent`）−予約・休憩・ブロック・B1（・1F）。
  **カレンダーと Script Properties を読んで枠を返すだけで、書き込みはしない**（キャッシュ・公開シート・`LB_SLOTS_BUILT_AT` を書くのは呼び出し側 `buildAndCacheSlots`）。
  `nowMsOpt` は「いま」を指定する突き合わせ用の引数（既存）。
- 公開シート（`writeToSpreadsheet`）は原子的に差し替えられない（slots の全消去→見出し→全行→トレーナー別タブ→meta!A1）。
  途中に読むと空・部分なのに meta は前回の時刻のまま。正常に枠が全体0のときも行が無い（関門② 1回目・再審の指摘）。
- 日次点検 `dailyHealthCheck`（7時）の段「翌月の解放」は**契約**の見張り（nudge_open_miss）で、**枠**は誰も見ていなかった。

## 比べた手段
| 手段 | 判断 |
|---|---|
| A. 公開シートの2列＋meta を読む（初版） | ✕ 書き直しの途中・正常な0枠を取り違える（関門②）。前後で meta を読んでも getLastRow と getValues の間の消去は塞げない |
| B. **日次点検の中で `buildAvailableSlots` を翌月だけで呼ぶ** | ◎ 採用（CEO 判断）。書き直しとの競合も、正常な0枠の取り違えも構造的に無い。顧客に出す枠と同じ計算 |
| C. 枠を作るたびに月ごとの日数を Property に残す | ✕ 顧客の経路（10分ごとの作り直し）に書き込みを足す |
| D. Worker の slots_cache を読む新しい窓口 | ✕ 新しい op を足さない |

## 何をするか
段「翌月の解放」の最後に `lbNextMonthOpenCheck(now, 点検の経過時間)` を呼ぶ。
1. `_lbNextMonthRange(now)`：`_lbBookingHorizonEnd(now)` が今月末なら **null＝何も読まない**（24日まで）。翌月なら翌月1日0時〜末日23:59:59。
2. `_lbNextMonthOpenRead`：`buildAvailableSlots(null, 翌月1日0時 − 3時間)` を呼ぶ。
   - 「いま」を翌月1日の3時間前に置く理由：地平がちょうど翌月末になる（その日は25日以降）・翌月1日の午前枠（前日22時締め）も締め切り前で数えられる。前夜3時間ぶんの枠は月の範囲で捨てる。
   - 読むカレンダーは翌月＋3時間だけ（施設 B1・トレーナー3本・1F の切替が on なら 1F）。
   - 出勤は**同じ呼び出しの読みを使い回す**：`buildAvailableSlots` がトレーナーの出勤と読めなかったトレーナーを
     `LB_SLOTS_READ_LOCAL`（その実行の中だけの変数・コード.js）に置く。枠の計算そのものは1文字も変えていない。
3. 判定
   - 顧客向け（`hidden` でない）トレーナーの翌月の枠のある日が **0日 → `next_month_slots_none`**（warn・件数1）。
     詳細＝出勤のある日数（記号ごと：`A(非表示):n・B:n・C:n`）・枠のある日（全体／顧客向け）。
     facts＝`no_shift`（出勤も0日＝入れ忘れの見込み）／`not_covered`（出勤はあるのに枠0＝予定名か予約・ブロックで埋まっている）。
   - 1日以上 → `next_month_open`（info・件数＝顧客向けの日数）。案件にしない。
   - **判定できない → `next_month_slots_unknown`**（warn・0日とは言わない）：顧客向けトレーナーのカレンダーが1本でも読めない（読んだ記録が無いも同じ）＝`cal_unreadable`（原因を確定できない）／日次点検の経過が3分以上＝`no_time`（数え始めない）。非表示（オーナー）だけ読めないなら判定する。
   - 点検そのものが例外（施設のカレンダーが読めない等）→ `next_month_check_fail`（AB・例外の文は出さない・段に完走の印を付けない）。

★全体ではなく**顧客向け**で数える理由：オーナー（hidden）の枠は曜日×時間帯で固定客にだけ出る。オーナーの出勤が入っていると、
　スタッフの出勤が丸ごと抜けても「全体」は0日にならず、見張りが黙る。詳細には全体の日数も並べる（CEO 承認済み）。

件数を1に固定するので、悪化のメールは**最初の日だけ**。台帳（incidents）には B で開き、直った次の点検で閉じる。

★変わること：初版は「本番の作り直しが翌月を覆っているか」も見ていたが、今の形は「出勤から翌月の枠ができるか」を見る。
　本番の作り直しは同じ `_lbBookingHorizonEnd` を使うので、地平の食い違いは起きない作り。作り直しそのものの停止は既存の見張り（枠のすぐ押し出し・定期処理の鮮度）が見る。

## 重さの見積り（★未計測）
25日〜末日だけ（月に最大7回）。24日までは0。
- カレンダー4本（施設＋トレーナー3。1F の切替が on なら＋1）×約1か月の `getEvents`：1本1〜3秒＝4〜15秒
- 枠の計算（メモリの中・連続ルールが on なら施設のタイトルも使う）：1〜数秒
- 公開シート・キャッシュ・Property への書き込みは無い
- 合計の見込み **5〜20秒**（本番の作り直し＋キャッシュ＋公開シート＋送信の合計が約43秒・約5週ぶん、の実績から上に寄せても30秒以内）。
- 打ち切り：カレンダーの読みは同期で途中で止められない。だから**数え始めるのは点検の経過が3分未満のときだけ**（3分ちょうど以上は `no_time`）。見込み5〜30秒に対し、6分の制限まで3分の余裕（関門② 再審2）。
- かかった秒数を詳細に「数えるのに n秒」で残す（none・open とも）。
- 実測は次の25日の `LB_HEALTH_STEP`（段の経過 ms：`翌月の解放=…` と次の段 `二重書き=…` の差）で確かめる。
