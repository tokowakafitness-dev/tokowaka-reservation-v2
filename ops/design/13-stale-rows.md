# 枠とチケットの古い行をどうするか（切り替え前の必須条件）

> 2026-10-09・CEO玄／前提：`11-sync-version.md`（会員ごとの世代）・`12-shadow-compare.md`
> **第2版。** 第1版は関門①で差し戻された（指摘6件・却下0）。方針そのものは支持された。
> 差し戻しの内容は第9節に残す。

---

## 1. 何が起きているか（事実）

枠（`monthly_quota`）とチケット（`ticket_packs`）は **UPSERT だけ**で書いている。
**いまの計算に無くなった行を消していない。**

```
worker/src/lib/quota-build.js   quotaUpsertStatements … INSERT … ON CONFLICT DO UPDATE のみ
worker/src/lib/alloc-build.js   引当は「消してから入れる」になっている（対照的）
```

契約を変えてチケットの行が消えると、**古いパックがD1に残る。**
読み取りをD1へ向けると、次が全部誤る。
```
hasTicket / ticketTotal / ticketExpireMs / ticketRemaining / type
```
★`type` が誤ると、月額だけの会員に**チケットの案内が出る**。顧客に見える。

---

## 2. ★「消す」のは危険（なぜ独立工程にしたか）

| | 理由 |
|---|---|
| ① | `used` は**トリガーだけが触る**（0009 の不変条件）。パックを消して入れ直すと `used` が0に戻り、引当の再挿入で積み直される。順序を1つ間違えると残数が狂う |
| ② | 引当から**外部キーで参照されている**（`FOREIGN KEY (pack_id) REFERENCES ticket_packs`）。参照が残っている行を消すと**その会員ぶんの書き込みが丸ごと落ちる** |
| ③ | 引当の削除範囲は `recordsFrom` より前と `fromMonth..maxResvMonth`。**その間（recordsFrom〜fromMonth）の引当は残る**。そこが参照しているパックは消せない |

①②③のどれかを外すと、**残数が静かに狂う**か、作り直しが止まる。

---

## 3. ★採る案：消すのではなく「読まない」

枠とチケットの行に**作った世代**を持たせ、**読む側がいまの世代の行だけを読む。**

```sql
ALTER TABLE monthly_quota ADD COLUMN built_version INTEGER;
ALTER TABLE ticket_packs  ADD COLUMN built_version INTEGER;
```
```
枠を作り直すとき   その作り直しが読んだ source_version を built_version に入れる
                   （customer_sync_version.built_version に書くのと同じ値）
読むとき           customer_sync_version.built_version と**同じ行だけ**を読む
古い行             残る。しかし**読まれない**
```

### なぜこれが良いか

| | 「消す」案 | 「読まない」案 |
|---|---|---|
| `used` のトリガー | 触る（危険） | **触らない** |
| 外部キー | 参照を気にして順序を組む | **関係ない** |
| 範囲外の引当 | 消せない行が出る | **関係ない** |
| 間違えたとき | 残数が狂う／書き込みが落ちる | **古い行が読まれないだけ**（＝答えない側に倒れる） |
| 行の増え方 | 増えない | 増える（40名×数か月＝小さい） |

**危険な操作を一度も行わずに、目的（古い値を顧客に出さない）を達する。**
行の掃除は、読まれなくなった**あとで**、落ち着いてやればよい。

---

## 4. 読む側の変更（1か所）

`worker/src/lib/remain-from-d1.js` の `readRemainDiag`。
```
いま   SELECT … FROM monthly_quota WHERE customer_id = ? AND month_key IN (?, ?)
あと   ＋ AND built_version = ?      （その会員の built_version）
いま   SELECT … FROM ticket_packs WHERE customer_id = ?
あと   ＋ AND built_version = ?
```
`built_version` は既に `readSyncVersionForRemain` が読んでいる。**新しい読み取りは増えない。**

★`built_version` が NULL の行は読まれない。
　＝**いま入っている行は全部読まれない**（まだこの列が無いので）。
　だから **全会員を作り直してから** 読み取りを切り替える。順序は第6節。

---

## 4-2. ★「読まれない」だけでは安全側に倒れない（第1版の重大な誤り）

第1版は「世代を書き忘れた行は読まれない＝写しへ落ちる」と書いた。**成立しない。**

`readRemainDiag` は、世代が追いついていれば行を読み、
**枠0行・パック0行でも「契約が無い会員」として正常に答える**（`{ type: null }`）。

```
もし枠の行に built_version を書き忘れたら
  世代は追いついている（customer_sync_version は更新されている）
  行は絞られて0行になる
  → 「契約なし」を顧客に出す。★月額会員の画面から残数が消える
```
**答えない側ではなく、間違った側に倒れる。** いちばん避けたい形。

### 直し方：行数を世代と一緒に持つ
```sql
ALTER TABLE customer_sync_version ADD COLUMN built_rows INTEGER;
```
```
作り直すとき   その会員について書いた「枠の行数 ＋ パックの行数」を入れる
読むとき       読めた行数が built_rows と**一致しないときは答えない**
```
★これは「書き忘れ」も「取り落ち」も同じ1つの検査で捕まえる。
　一致しなければ写しへ落ちる＝**本当に安全側へ倒れる。**
★`built_rows` が NULL（まだ作り直していない）のときも答えない。

## 5. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 作り直しが途中で止まり、一部の月だけ新しい世代になる | 枠・引当・`customer_sync_version` は**同じ batch**。途中で止まれば全部無かったことになる（既にそうなっている） |
| ② | `built_version` を書き忘れた行が読まれない | ★それが安全側。読まれなければ写しへ落ちる。`quotaStatus` に「世代の入っていない行」の数を出す |
| ③ | 古い行が増え続ける | 40名×数か月。`quotaStatus` に総数と「読まれない行」の数を出し、増え方を見てから掃除する |
| ④ | `used` は世代ごとに分かれるのか | **分かれない。** `used` は**物理的な行**（主キー）に入る。`monthly_quota` は `(customer_id, month_key)` が主キーなので、同じ会員・同じ月は**常に同じ行**で、作り直しても `used` はその行の値を保つ（UPSERT は `used` を更新しない＝トリガーの不変条件）。`ticket_packs` は `pack_id` が変われば別の行になる → ⑧ |
| ⑤ | 同じ `pack_id` が世代をまたいで同じとき | UPSERT で `built_version` が更新される＝新しい世代として読まれる。正しい |
| ⑥ | `quota-verify`（照合）が古い行も見てしまう | 照合も同じ条件で絞る。絞らないと「消えた契約のパック」で食い違いが出続ける |
| ⑦ | 読む側を先に切り替えると shadow が汚れる | 世代の無い行が除外され、D1が「契約なし」を返すか答えられなくなる。shadow が**通常の鍵の食い違い**（`type` など）か `_one_sided` で埋まり、何も読めない。★第6節の順序で作り直しを先に |
| ⑧ | ★`pack_id` が同じ契約で別のIDになる | `pack_id` 列が無い互換経路では、**開始日・終了日・シートの行番号から合成している**（`worker/src/allocate.js`）。日付を直す／行を挿入する／列を新設する、で**IDが変わる**。変わると古い行が残り、新しい行が増える。→ 第6節の合格条件に「`pack_id` 列が存在し、全チケット行が採番済み」を入れる |

## 6. 順序（★書く側と読む側を分ける）

```
1. 列を足す（migration）
     monthly_quota.built_version / ticket_packs.built_version
     customer_sync_version.built_rows
2. ★書く側だけ直す（quota-build が行にも世代と行数を書く）。読む側はまだ絞らない
3. 全会員を作り直す（★withAlloc=1 で。枠だけでは世代が更新されない）
4. ★合格条件を確かめる（下）
5. 読む側を直す（readRemainDiag と quota-verify を世代で絞る＋行数を照合）
6. shadow を on にしてベースラインを採る
7. 食い違いが0で続いたら、1人だけ on（★オーナー承認）
```

### ★4の合格条件（第1版は成立しない条件を書いていた）
第1版は「表全体で `built_version IS NULL` が0件」とした。**達成できない。**
UPSERT は**いまの計算に出た主キーしか更新しない**ので、
まさに問題になっている「計算から消えた行」は NULL のまま残る。

正しい合格条件：
```
① 各会員について、いまの計算が作るべき**全部の主キー**が、
   その会員の built_version と同じ世代で存在する
   → `built_rows` と、同世代で読めた行数が一致すること（第4-2節）
② NULL・別世代の行は「古い行」として**別に数える**。0件を条件にしない
③ ★pack_id 列が本番に存在し、全チケット行が採番済みであること
   （合成IDのまま切り替えると、日付や行番号の変更でIDが変わり、
     古い行が増え続け、どの行がいまのものか分からなくなる）
```

★5を先にやると、作り直す前の全会員でD1が「契約なし」を返し、
　shadow の食い違いが通常の鍵で埋まって何も分からない。

## 7. 捨てた案

| | 案 | なぜ捨てたか |
|---|---|---|
| A | 消してから入れ直す | 第2節の①②③。`used` のトリガーと外部キーに触る |
| B | 削除だけを別の工程で（引当を消さずに） | 外部キー違反で落ちる |
| C | 行に「最後に見た時刻」を持たせ、古ければ読まない | 時刻では判定できない（設計11 第1節と同じ理由） |

## 9. 第1版からの変更（関門①・指摘6件・却下0）

```
① ★重大：「世代を書き忘れた行は読まれない＝写しへ落ちる」は成立しない
   readRemainDiag は 0行でも「契約なし」を正常に答える
   ＝**月額会員の画面から残数が消える**。答えない側ではなく間違った側に倒れる
   → customer_sync_version.built_rows を足し、読めた行数と一致しなければ答えない
② ★「表全体で built_version IS NULL が0件」は達成できない
   UPSERT はいまの計算に出た主キーしか更新しない＝消えた行は NULL のまま残る
   → 合格条件を「いまの計算が作るべき全主キーが同世代で存在する」に変えた
③ shadow が「全部 _one_sided になる」は不正確
   世代で絞って0行になると、D1は「契約なし」を正常に返す
   ＝通常の鍵（type など）の食い違いになる
④ used は「世代別」ではなく「物理的な行（主キー）別」
⑤ ★合成 pack_id が別IDになる経路がある
   （開始日・終了日・シートの行番号から作っている。日付を直すとIDが変わる）
   → 合格条件に「pack_id 列が存在し全行採番済み」を入れた
⑥ quota-verify も世代の追いつきを確認し、前後で世代を見直す。
   途中で世代が変わった会員は「不一致」ではなく「飛ばした（version_changed）」にする
   全表の検査は役割を分ける：
     いまの世代の行 → 表示の値と合うか
     全部の行       → used と引当の合計など、物理的な不変条件
     古い行         → 件数と増え方の監視
```

★方針（消すのではなく読まない）は**支持された**。
　削除は「不可能」ではないが、顧客の表示を切り替える前提としては過剰で危険。

### 索引
`ticket_packs` の索引はいま `(customer_id, valid_to)` だけ。
世代で絞るので `(customer_id, built_version)` を足す。
