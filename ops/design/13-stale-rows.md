# 枠とチケットの古い行をどうするか（切り替え前の必須条件）

> 2026-10-09・CEO玄／前提：`11-sync-version.md`（会員ごとの世代）・`12-shadow-compare.md`
> **第4版（関門①通過）。** 3回差し戻された（指摘 6 → 5 → 1件・却下0・累計12件）。
> 差し戻しの内容は第9節に残す。

---

## 1. 何が起きているか（事実）

枠（`monthly_quota`）とチケット（`ticket_packs`）は **UPSERT だけ**で書いている。
**いまの計算に無くなった行を消していない。**

```
worker/src/lib/quota-build.js   quotaUpsertStatements … INSERT … ON CONFLICT DO UPDATE のみ
worker/src/lib/alloc-build.js   引当は「消してから入れる」になっている（対照的）
```

契約を変えてチケットの行が消えると、**古いパックがD1に残る。**
読み取りをD1へ向けると、次が全部誤る。
```
hasTicket / ticketTotal / ticketExpireMs / ticketRemaining / type
```
★`type` が誤ると、月額だけの会員に**チケットの案内が出る**。顧客に見える。

---

## 2. ★「消す」のは危険（なぜ独立工程にしたか）

| | 理由 |
|---|---|
| ① | `used` は**トリガーだけが触る**（0009 の不変条件）。パックを消して入れ直すと `used` が0に戻り、引当の再挿入で積み直される。順序を1つ間違えると残数が狂う |
| ② | 引当から**外部キーで参照されている**（`FOREIGN KEY (pack_id) REFERENCES ticket_packs`）。参照が残っている行を消すと**その会員ぶんの書き込みが丸ごと落ちる** |
| ③ | 引当の削除範囲は `recordsFrom` より前と `fromMonth..maxResvMonth`。**その間（recordsFrom〜fromMonth）の引当は残る**。そこが参照しているパックは消せない |

①②③のどれかを外すと、**残数が静かに狂う**か、作り直しが止まる。

---

## 3. ★採る案：消すのではなく「読まない」

枠とチケットの行に**作った世代**を持たせ、**読む側がいまの世代の行だけを読む。**

```sql
ALTER TABLE monthly_quota ADD COLUMN built_version INTEGER;
ALTER TABLE ticket_packs  ADD COLUMN built_version INTEGER;
```
```
枠を作り直すとき   その作り直しが読んだ source_version を built_version に入れる
                   （customer_sync_version.built_version に書くのと同じ値）
読むとき           customer_sync_version.built_version と**同じ行だけ**を読む
古い行             残る。しかし**読まれない**
```

### なぜこれが良いか

| | 「消す」案 | 「読まない」案 |
|---|---|---|
| `used` のトリガー | 触る（危険） | **触らない** |
| 外部キー | 参照を気にして順序を組む | **関係ない** |
| 範囲外の引当 | 消せない行が出る | **関係ない** |
| 間違えたとき | 残数が狂う／書き込みが落ちる | **古い行が読まれないだけ**（＝答えない側に倒れる） |
| 行の増え方 | 増えない | 増える（40名×数か月＝小さい） |

**危険な操作を一度も行わずに、目的（古い値を顧客に出さない）を達する。**
行の掃除は、読まれなくなった**あとで**、落ち着いてやればよい。

## 4. 読む側の変更（1か所）

`worker/src/lib/remain-from-d1.js` の `readRemainDiag`。
```
いま   SELECT … FROM monthly_quota WHERE customer_id = ? AND month_key IN (?, ?)
あと   ＋ AND built_version = ?      （その会員の built_version）
いま   SELECT … FROM ticket_packs WHERE customer_id = ?
あと   ＋ AND built_version = ?
```
`built_version` は既に `readSyncVersionForRemain` が読んでいる。**新しい読み取りは増えない。**

★`built_version` が NULL の行は読まれない。
　＝**いま入っている行は全部読まれない**（まだこの列が無いので）。
　だから **全会員を作り直してから** 読み取りを切り替える。順序は第6節。

## 4-2. ★「読まれない」だけでは安全側に倒れない（第1版の重大な誤り）

第1版は「世代を書き忘れた行は読まれない＝写しへ落ちる」と書いた。**成立しない。**

`readRemainDiag` は、世代が追いついていれば行を読み、
**枠0行・パック0行でも「契約が無い会員」として正常に答える**（`{ type: null }`）。

```
もし枠の行に built_version を書き忘れたら
  世代は追いついている（customer_sync_version は更新されている）
  行は絞られて0行になる
  → 「契約なし」を顧客に出す。★月額会員の画面から残数が消える
```
**答えない側ではなく、間違った側に倒れる。** いちばん避けたい形。

### 直し方：行数を世代と一緒に持つ（★2つに分けて数える）
```sql
ALTER TABLE customer_sync_version ADD COLUMN built_quota_rows INTEGER;
ALTER TABLE customer_sync_version ADD COLUMN built_pack_rows  INTEGER;
```
```
作り直すとき   枠の行数（built.monthly.length）とパックの行数（built.packs.length）を
               **別々に**入れる
読むとき       いまの世代で読めた行数が、両方とも一致しないときは答えない
NULL のとき    答えない（まだ作り直していない）
```
★**1つの合計にしない。** 「枠が1行足りず、パックが1行多い」が打ち消し合って通る。
　分けても同じ表の中の相殺は残るが、守りたい事故
　（片方のUPSERTだけ世代を書き忘れた／片方の表を丸ごと取り落とした）は確実に捕まる。
　主キーの集合そのものの一致は、照合（`quota-verify`）側で見る。

### ★読む範囲と書く範囲をそろえる（第2版の穴）
書く側は `fromMonth..toMonth` の**全部の月**を作る。
読む側（`readRemainDiag`）は**当月と翌月だけ**を読んでいた。**件数が一致するはずがない。**

```
対処   読むときは「いまの世代の月額の行を**全部**」読む
         SELECT … FROM monthly_quota WHERE customer_id = ? AND built_version = ?
       件数を照合したうえで、**表示に使うのは当月と翌月の行だけ**
```
数か月×40名なので、全部読む負荷は無視できる。COUNT を別に撃つより単純。

### ★同じ世代で作り直すと行が溜まる（関門①の2周目で見つかった）
`built_version` には `source_version` をそのまま使う。
**入力が変わらないまま作り直すと、同じ世代番号を使い回す。**

```
世代10で 9〜12月を作る
入力は変わらない
世代10のまま 10月〜翌1月を作る
→ 9月の行は**世代10のまま残る**
   いまの計算が作るのは4行。しかし世代10の行は5行
   ＝件数の検査が**永久に通らない**
```

```
対処   各会員のbatchの**冒頭**で、その会員の世代印だけを外す
         UPDATE monthly_quota SET built_version = NULL WHERE customer_id = ?;
         UPDATE ticket_packs  SET built_version = NULL WHERE customer_id = ?;
       そのあと、今回の計算に出た行だけをUPSERTして新しい印を付ける
```
★行を**消していない**。`used` に触れない。外部キーにも影響しない。
　同じbatchなので、途中で失敗すれば印を外したことも無かったことになる。
★作り直しが同時に2本走っても、**最後に書き終わったbatchの集合と件数が対応する**。
　古い入力のビルドなら、既にある競合の処理で `built_version = 0` に倒れる。

### ★枠だけ作り直した状態を「いまの世代」にしない（関門①の3周目）
いまのコードは `withAlloc=1`（引当も作る）のときだけ世代の印を書く。理由は
**枠だけ作り直すと `used` が古いまま**で、それを「新しい」と記録すると誤った残数を答えるから。

新しく行にも印を付けるので、`withAlloc=0` でも印が付くと**同じ穴が開く**。

```
決め   dry=0 かつ alloc=0 は**書き込ませない**（400 で弾く）
       ＝顧客に出せる作り直しは必ず引当も作る
```
★`alloc` の既定は false（`gas/PushToEdge.js`）。
　うっかり `write:true` だけ投げたときに弾かれる＝安全側。
　「枠だけ書く」用途は dry-run（確かめるだけ）で足りる。

### ★競合で倒すときは件数も落とす
`markBuiltStatement` が「古い作り直しだった」と判定して `built_version = 0` にするとき、
件数も NULL に落とす。でないと「世代0・件数あり」というちぐはぐな行が残る。
```sql
built_quota_rows = CASE
  WHEN source_version = excluded.built_version THEN excluded.built_quota_rows
  ELSE NULL
END
```

## 5. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 作り直しが途中で止まり、一部の月だけ新しい世代になる | 枠・引当・`customer_sync_version` は**同じ batch**。途中で止まれば全部無かったことになる（既にそうなっている） |
| ② | `built_version` を書き忘れた行が読まれない | ★「読まれない」だけでは安全側に倒れない（第4-2節）。**件数の照合**で捕まえ、一致しなければ答えない。`quotaStatus` には「世代の入っていない行」「別世代の行」の数を出し、増え方を見る |
| ③ | 古い行が増え続ける | 40名×数か月。`quotaStatus` に総数と「読まれない行」の数を出し、増え方を見てから掃除する |
| ④ | `used` は世代ごとに分かれるのか | **分かれない。** `used` は**物理的な行**（主キー）に入る。`monthly_quota` は `(customer_id, month_key)` が主キーなので、同じ会員・同じ月は**常に同じ行**で、作り直しても `used` はその行の値を保つ（UPSERT は `used` を更新しない＝トリガーの不変条件）。`ticket_packs` は `pack_id` が変われば別の行になる → ⑧ |
| ⑤ | 同じ `pack_id` が世代をまたいで同じとき | UPSERT で `built_version` が更新される＝新しい世代として読まれる。正しい |
| ⑥ | `quota-verify`（照合）が古い行も見てしまう | 照合も同じ条件で絞る。絞らないと「消えた契約のパック」で食い違いが出続ける |
| ⑦ | 読む側を先に切り替えると shadow が汚れる | 世代の無い行が除外され、D1が「契約なし」を返すか答えられなくなる。shadow が**通常の鍵の食い違い**（`type` など）か `_one_sided` で埋まり、何も読めない。★第6節の順序で作り直しを先に |
| ⑧ | ★`pack_id` が同じ契約で別のIDになる | `pack_id` 列が無い互換経路では、**開始日・終了日・シートの行番号から合成している**（`worker/src/allocate.js`）。日付を直す／行を挿入する／列を新設する、で**IDが変わる**。変わると古い行が残り、新しい行が増える。→ 第6節の合格条件に「`pack_id` 列が存在し、全チケット行が採番済み」を入れる |

## 6. 順序（★書く側と読む側を分ける）

```
1. 列を足す（migration）
     monthly_quota.built_version / ticket_packs.built_version
     customer_sync_version.built_quota_rows / built_pack_rows
2. ★書く側だけ直す。読む側はまだ絞らない
     batchの冒頭でその会員の世代印を外す → 今回の行をUPSERTして印を付ける
     → 枠の行数とパックの行数を customer_sync_version に書く（同じbatchの最後）
3. 全会員を作り直す（★withAlloc=1 で。枠だけでは世代が更新されない）
4. ★合格条件を確かめる（下）
5. 読む側を直す（readRemainDiag と quota-verify を世代で絞る＋行数を照合）
6. shadow を on にしてベースラインを採る
7. 食い違いが0で続いたら、1人だけ on（★オーナー承認）
```

### ★4の合格条件（第1版は成立しない条件を書いていた）
第1版は「表全体で `built_version IS NULL` が0件」とした。**達成できない。**
UPSERT は**いまの計算に出た主キーしか更新しない**ので、
まさに問題になっている「計算から消えた行」は NULL のまま残る。

正しい合格条件：
```
① 各会員について、いまの計算が作るべき**全部の主キー**が、
   その会員の built_version と同じ世代で存在する
   ★2つに分けて考える（厳密には同値ではない）
     件数の一致      → 顧客の読み取り経路で毎回見る（オンラインの完全性の検査）
     主キーの集合の一致 → 照合（quota-verify）で見る。**切り替えの合格条件はこちら**
② NULL・別世代の行は「古い行」として**別に数える**。0件を条件にしない
③ ★pack_id 列が本番に存在し、全チケット行が採番済みであること
   （合成IDのまま切り替えると、日付や行番号の変更でIDが変わり、
     古い行が増え続け、どの行がいまのものか分からなくなる）
```

★5を先にやると、作り直す前の全会員でD1が「契約なし」を返し、
　shadow の食い違いが通常の鍵で埋まって何も分からない。

## 10. 実装で見つかったもの（関門②・3周・却下0）

### 1周目（2件）
```
① ★主キーの集合の照合を設計に書いたのに実装していなかった
   顧客の読み取り経路で見るのは件数だけ。それでは
     当月以外の月額行の欠け／余り・期限切れパックの主キー違い・
     同じ枚数の別パックへの入れ替わり
   が通る（当月の残数はたまたま一致する）
② quotaStatus の「いまの世代」が、読まれない行も数えていた
   （source > built の会員は世代が一致しても読み取りの対象外）
```

### 2周目（3件）
```
③ ★作った**主キー集合の照合が運用経路で一度も走らない**
   Workerは from/to を渡されたときだけ照合し、GASは渡していなかった。
   しかもGASは keyMismatch を集計も表示もせず、合否にも入れていなかった
   ＝**不一致があっても「✅ 全員で一致しました」と出る**
④ ★作った範囲を保存していないので、正しい from/to を後から確定できない
   範囲は会員ごと・実行ごとに違う
     全員ぶん     当月〜翌月
     二重書き1人  recordsFrom 〜 当月+2か月（または最も先の予約月）
   → customer_sync_version に built_from_month / built_to_month を保存し、
     照合は**保存された範囲**を使う（URLでは受け取らない）
⑤ 計算に問題がある会員で、途中までの集合を「作るべき集合」として比べていた
   → KEY_EXPECTATION_NOT_OK として飛ばし、合格にもしない
```

### 3周目（1件）
```
⑥ keyChecked を一致したときだけ数えていた
   ＝全員が不一致なら0になり、「合わない」と「1人も走っていない」が同時に出て読めない
   → D1の主キーを読み終えた時点で数える
```

★③は「検査を足したのに、運用では一度も走らない」形。
　**設計に書いただけでは走らない。呼ぶ側と合否の両方を直すまで、検査は存在しないのと同じ。**

### 合格の条件（GAS側の `allGood`）
```
食い違い0 ／ 比べられない人0 ／ 使いすぎ0 ／ 覆い方の未設定0
主キーの集合が合わない人0 ／ 範囲が無くて照合できない人0
★照合が1人以上走っている（keyChecked > 0）
D1にだけ残った行0 ／ 最後のページまで到達
```
★本番はいま `built_from_month` が NULL なので、**作り直すまで合格しない**。意図どおり。

### 検査

## 11. ★切り替えの合格条件は「採番済み」ではなかった（2026-10-09・訂正）

関門①で Codex は「本番では `pack_id` 列が存在し、全チケット行が採番済み」を
切り替えの合格条件にすべき、と指摘した。これを受けて条件に入れた。

**そのあと実態を調べ、条件を外した。** 経緯を残す。

### 分かった事実
```
pack_id 列は LB_STRICT_ID_MODE === 'on' のときだけ読む（既定は off）
＝いま本番は**必ず合成ID**（'CT' + 開始ms + '_' + 終了ms + '_' + 行番号）
```

### 外してよい理由（この設計のおかげ）
```
行番号がずれて pack_id が変わっても
  古い pack の行   世代の印が外れる → 読まれない
  新しい pack の行 作られる（used は 0 から）
  引当             毎回「消して入れ直す」ので新しい pack_id を指す
  used             トリガーが新しい行に積み直す
＝読む値は整合する
```

### ★私が書いていた危険は誤りだった
「開始日を直すとチケットが復活する」と書いていた。**起きない。**
棚卸しの照合が切れると `OPENING_PACK_UNRESOLVED` が出て、
**その会員のD1の作り直しが止まる**（I5）。古い行が残り、顧客には写しが出る。
→ 実際に動かして確かめた（`model-doc.test.js` ③-b）。

### 本当に残る危険
```
誤った完全一致   行を移動したあとのIDが、別の既存packの旧IDと**偶然一致する**
                 → 止まらずに、間違ったpackへ棚卸しを割り当てる
                 ★同じ開始日・終了日のpackが複数ある会員で起こりうる
```

### 「採番済み」の代わりの合格条件
`ops/MODEL.md` §4-2 に置いた。芯は**「棚卸しの解決そのものを検査対象にする」**こと。
```
OPENING_PACK_UNRESOLVED = 0 ／ OPENING_OVER_TOTAL = 0
同じ会員の中に、同じ 'CT<開始>_<終了>' のpackが複数ない
＋ 作り直しの完了・世代・照合・shadow・used と引当の一致・写しへの落ち方
＋ 切り替えの作業中は契約表の行の挿入・移動・日付の修正を凍結
```
