# 予約を促すリマインド — 仕様（オーナーと確定済み／反映はオーナー承認後）

> 対象：TOKOWAKA吉祥寺 LINE予約システム
> 実装：`gas/Nudge.js`／テスト：`line-booking/test/nudge-gas.test.js`
> 状態：**コードは書き終えたが、まだ1通も送らない状態で止めてある。** デプロイもしていない。
> 起草：2026-09-30（初稿）／**改訂：2026-09-30（オーナーと設計を詰め切り、条件・文面とも全面差し替え）**

## 0. 結論（先に読むところ）

送るものは **4種** です。**同じ日に複数当たったら、優先順位が上のものだけを送ります（1人1日1通）。**

| 順 | 種別 | いつ | 誰に |
|---|---|---|---|
| **1** | `transfer` 振替のご案内 | 毎日 | 昨日の予約が**当日キャンセル**で、**振替権が未使用かつ有効期限内**の方 |
| **2** | `month_open` 翌月分の解放 | **毎月25日** | 契約が有効な方（固定枠の有無で文面が変わる） |
| **3** | `visit_b` 来店翌日B | 毎日 | 昨日**実際に来店**・**今月の未来予約が0件**・月額残 > 0 の方 |
| **4** | `visit_a` 来店翌日A | 毎日 | 昨日**実際に来店**・**今月の未来予約が1件以上**・月額残 > 0・**前回の visit_a から7日以上**の方 |

**いまは既定で無効です。** Script Properties の `LB_REMIND_ON` を `1` にするまで、何も送りません。
有効化は顧客への発信なのでオーナー承認が必要（憲法第3節-3）。私の判断では行いません。

オーナーにお願いしたいのは次の3つです。

1. GASエディタで **`lbNudgeSetupSheets`** を1回実行（判定に使うシートを用意。§7-0）
2. GASエディタで **`lbNudgePreview`** を1回実行し、「誰に何が飛ぶか」を目で見る（**送信されません**）
3. §8「決めていただきたいこと」を決める → 私が反映 → オーナーがプロパティを立てて有効化

---

## 1. なぜこの4種なのか

**① transfer（振替のご案内）**
当日キャンセルは1回分の消化になりますが、代わりに **6日有効の振替権が1件** 付きます（`transfer_credits`・#9）。
権利があることを本人が知らないまま6日で消えるのが、いちばんもったいない。**権利が発生した翌日に1回だけ伝えます。**
※この文面には残数の話を入れません（オーナー指示）。消化してしまった直後に「残り◯回」と言うのは筋が悪いためです。

**② month_open（翌月分の解放）**
運用は「20日にトレーナーがシフト提出 → 25日に翌月分が解禁」。
会員ホームの残数は「今日」基準なので、25日以降は「今月の残り0回」と見え、**予約できないと誤解して翌月の枠を取りに来ない**
（`next-month-notice.test.js` に記録済みの実害）。画面側は直しましたが、**画面を開かない方**には届きません。だから通知で押します。
固定枠をお持ちの方は25日に `autoBookRecurringPatterns` が翌月分を自動予約済みなので、**取れた事実と変更方法**を伝えます。
固定枠が無い方には、**先着順であること**を伝えてまとめて押さえていただきます。

**③④ visit_a / visit_b（来店翌日）**
セッション後にトレーナーが次回予約を案内しても、その場で取らない方は忘れます。**翌日が最も戻ってきやすい。**
今月の予約が1件も無い方（B）と、1件以上ある方（A）では言うべきことが違うので分けています。
Aは「もう一度いかがですか」という上乗せの誘いなので、**同じ方には7日空けます**（Bには週の上限を設けません）。

## 2. 判定に必要な事実（ここが実装の肝）

### 当日キャンセルと実来店の見分け方

**予約台帳では当日キャンセルも `consumed` として残ります。** 状態だけでは来店と区別できません。

そこで **`transfer_credits` シート**（`LB_TCREDIT_SHEET`・列は `customer_id / granted_at / expires_at / used_at / source_reservation_id`）
の `source_reservation_id` に昨日の予約IDが載っているかで割ります。

| 昨日の `consumed` 行 | 振替権の source に載っている？ | 判定 |
|---|---|---|
| あり | **載っている** | **当日キャンセル** → ①のみ（③④は送らない） |
| あり | 載っていない | **実来店** → ③または④ |

※台帳の備考列は取消時に `resId|当日消化取消` になるため、`|` の手前で切って突き合わせます。

### 残りの判定材料

| 何を | どこから |
|---|---|
| 振替権が使えるか | `used_at` が空 **かつ** `expires_at` が未来（当日キャンセルで1件付与・6日有効） |
| 今月の未来予約 | `line_reservations` で状態が `confirmed`・開始が今より後・**かつ今月中**のもの |
| 月額残 | `_lbSplitRemaining` / `_lbBuildHome`（既存の残数の仕組み。月額の残り回数） |
| 繰越可能数 | `min(月額残, 繰越上限)`。上限＝契約の「繰越上限」列 ＞ `LB_CARRY_CAP_TABLE`（月2:1 / 月4:1 / 月6:2 / 月8:2 / 月12:3）＞ 率fallback |
| 今月の残り日数 | 月末日 − 今日 + 1（今日を含む） |
| 固定枠の有無 | `recurring_patterns` に有効な行があるか（毎月25日に `autoBookRecurringPatterns` が翌月分を自動予約済み） |

### 共通して入れる事実（`transfer` を除く3種）

```
今月はあと ○回 ご利用いただけます。
うち ○回 は繰り越し可能です。（残り○日）
```

## 3. 送る条件（確定仕様）

### 全種に共通（これは緩めません）
- `customer_line_map` の **認証状態 = verified**
- **contract_status = active**（空欄も送りません。判定できない＝送らない側に倒す）
- **lineUserId がある**

### 種別ごと

| 種別 | 条件 | 再送の抑止 |
|---|---|---|
| ① `transfer` | 昨日の予約が当日キャンセル **かつ** 振替権が未使用・期限内 | なし（権利は6日で1件。連日は構造的に起きにくい） |
| ② `month_open` | 今日が解放日（既定25日）**かつ** 契約が有効 | **その月に送ったか**（月キー `2026-10` で冪等） |
| ③ `visit_b` | 昨日実際に来店 **かつ** 今月の未来予約0件 **かつ** 月額残 > 0 | なし（週の上限を設けない＝オーナー指示） |
| ④ `visit_a` | 昨日実際に来店 **かつ** 今月の未来予約1件以上 **かつ** 月額残 > 0 | **同じ方へ7日空ける** |

### 優先順位（1人1日1通）

`transfer` ＞ `month_open` ＞ `visit_b` ＞ `visit_a`

絞って送らなかったものは **一覧に「優先順位で見送り」として出ます**（送られなかったことが見える）。

> ⚠️ **25日に振替が当たった方は、その月の `month_open` を受け取りません**（月キーの冪等が働き、翌日以降に回りません）。
> 該当は「24日に当日キャンセルした方」だけなので少数ですが、**ここは仕様として認識しておいてください**（§8 #4）。

## 5. 文面（4言語・確定）

置き換え記号：`{month}`=翌月／`{pattern}`=固定枠のラベル／`{remain}`=今月の残り回数／`{carry}`=繰り越し可能数／
`{days}`=今月の残り日数／`{quota}`=翌月に押さえたい回数／`{next}`=次のご予約の日時／`{expire}`=振替の期限。
URLは予約画面（LIFF）が自動で入ります。

**言い回しの決まり（オーナー指示）**
- 「消える」「残りわずか」などマイナス表現を使わない
- 「下記よりどうぞ」ではなく **「下記よりお待ちしております」**
- 敬体。上品なトーンを保つ
- **お名前は入れません**（1:1のトークなので本人にしか届かず、名前を扱わない分だけ事故が減る）

## 6. 設定値（Script Properties）

**すべて省略可。既定値はコード側に入っています。** コード変更なしで変えられます。

| キー | 既定 | 何を決めるか |
|---|---|---|
| `LB_REMIND_ON` | 未設定（＝無効） | **`1` のときだけ実送信。これが安全装置の本体。** 空にすれば即止まります |
| `LB_NUDGE_OPEN_DAY` | `25` | 翌月分の解放日 |
| `LB_NUDGE_VISIT_A_DAYS` | `7` | `visit_a` を同じ方へ再送するまでの間隔（日） |
| `LB_NUDGE_MAX_PER_RUN` | `50` | 1回の実行で送る上限。超えた分は翌日へ持ち越し |

## 7. 安全のための造り

| 守り | どう担保しているか |
|---|---|
| **勝手に送らない** | `LB_REMIND_ON=1` 以外は送信処理に入らない。無効時は記録も残さない（後で有効にしたとき再送抑止が誤作動しないため） |
| **1人1日1通** | 4種を1回の走査でまとめて判定し、優先順位で1つに絞ってから送る。見送った分も一覧に出る |
| **繰り返さない** | `nudge_log` に「いつ・誰へ・どの種別を・どの月分を・成功したか」を残す。`month_open` は月キー、`visit_a` は7日で抑止。**未達は「送った」と数えない**ので翌日また試せる |
| **一斉配信にならない** | 1回の上限（既定50通）。超えた分は翌日へ持ち越し |
| **トリガーは1日1回だけ** | 分ごと・時間ごとを作る書き方（`everyMinutes` / `everyHours`）を `Nudge.js` に一切書かず、**テストでソースを機械的に検査**している。過去に細かいトリガーを増やして応答が2倍以上遅くなった再発防止 |
| **1人の不備で全員止まらない** | 会員ごとに try/catch。落ちた会員は理由付きで一覧に出る（`sendLineReminders` と同方針） |
| **情報が足りないときは送らない** | **名簿・予約台帳・振替権シートのいずれかが読めなければ1通も送らず**、理由コード（`NO_MAP_SHEET` / `NO_RESV_SHEET` / `NO_TCREDIT_SHEET`）を返す（fail-closed） |
| **個人情報を出力に残さない** | 一覧・戻り値・ログ行に氏名と lineUserId を入れない。会員は顧客IDの下4桁。内部用の宛先と本文は `_lbNudgePublic()` で必ず落としてから外へ返す |
| **既存を壊さない** | 既存ファイルへの変更はゼロ。シート読み取りと `_lbPush` だけを使う |
| **LINEの通数** | `_lbPush` に用途タグ `nudge_transfer` / `nudge_month_open` / `nudge_visit_a` / `nudge_visit_b` を付けたので、月の通数を何が食っているか用途別に追える |

### `nudge_log` シート（自動で作られます）
`送信日時 / 種別 / customer_id / 対象キー / 結果 / 詳細`。新しい行が上に積まれます（`reminder_status` と同じ）。
**氏名は書きません。** 再送判定に必要なので `customer_id` だけ入ります（制限付きSS内）。
**消さないでください。** 再送抑止の正本です。

## 8. 決めていただきたいこと

| # | 論点 | 私の推奨 | 迷いどころ |
|---|---|---|---|
| 1 | **送信時刻** | **10:00** | 前日リマインドが12時に動いています。同じ時間に重ねるとLINEが2通並ぶので外しました。来店翌日の文面なので、朝のほうが自然だと考えます |
| 2 | **`visit_a` の間隔** | **7日**（確定仕様） | 変えるなら `LB_NUDGE_VISIT_A_DAYS` |
| 3 | **`visit_b` に上限を設けないこと** | **設けない**（確定仕様） | 今月の予約が1件も無い方だけなので、連日になることは構造的に少ない。ただし**月額残が多く、月末まで来ない方には毎日飛びます**。気になるなら上限を入れます |
| 4 | **25日に振替が当たった方が `month_open` を受け取らない件** | **いまのまま** | 該当は「24日に当日キャンセルした方」だけ。翌日に回す仕組みを足すこともできますが、条件が増えるぶん読みにくくなります |
| 5 | **休会中の方** | ⚠️ **除外できていません** | `customer_line_map` に休会を表す値がありません。`suspended` を入れる運用にすれば私が除外します。**運用として休会をどう記録しているか**を教えてください |
| 6 | **英語の月表記** | `October` と綴っています | 日本語・中国語は「10月」 |
| 7 | **`{quota}`（固定枠なしの「◯回分お押さえください」）** | **翌月時点の月額残**（取れなければ契約の頻度） | 繰越ぶんを含めた「翌月に使える回数」です。「契約の回数だけ」にすべきならそう直します |

## 10. 私が気づいた懸念（判断材料）

1. **`transfer_credits` が無いと全リマインドが止まる**（仕様どおり・要件9）
   当日キャンセルと実来店を区別できないまま送ると、**当日キャンセルの方に「昨日はお疲れさまでした」が飛びます。**
   それは避けるべき事故なので止める設計にしました。代わりに `lbNudgeSetupSheets()` で空のシートを先に作れます（§9-4）。

2. **サロンボード側にしか無い予約は見えません**
   「今月の未来予約」の判定は `line_reservations` だけを見ています。
   `syncExistingReservations` が6時間ごとに取り込んでいるので通常は大丈夫ですが、
   **氏名が一致せず `line_unlinked` に落ちている方は危険です**（予約済みなのに `visit_b` が飛ぶ）。
   有効化前に `line_unlinked` を空にしておくのが安全です。

3. **昨日の来店は `consumed` でしか拾えません**
   実施済みの予約が `consumed` に落ちていない（トレーナーの確定操作が漏れている）と、来店翌日の文面が飛びません。
   **空振り側の事故なので害は小さい**ですが、「送られていない」と見えたらまずここを疑ってください。

4. **LINEの月間通数**
   前日リマインドと予約確定通知で既に相当使っています。4種が毎日走ると通数が増えます。
   上限50通/回で抑えていますが、有効化後1か月は `checkLineQuota` の警告に注意が必要です。

5. **繰越可能数の出典**
   `min(月額残, 繰越上限)` で出しています。上限は契約の「繰越上限」列 ＞ 頻度テーブル。
   **契約マスタが引けなかった場合は頻度テーブルへ倒します**（表示を0にするより実態に近いため）。

6. **休会の記録場所が無い**（§8 #5）
