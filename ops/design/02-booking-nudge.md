## 0. 結論（先に読むところ）

作ったのは2つのリマインドです。

| | 何を送るか | いつ | 誰に |
|---|---|---|---|
| **A** | 「次のご予約がまだ入っていないようです」 | 毎日1回 | 最終来店から3日以上経ち、**未来の予約が1件も無い**会員 |

オーナーにお願いしたいのは次の3つです。

1. GASエディタで **`lbNudgePreview`** を1回実行し、「誰に何が飛ぶか」を目で見る（**送信されません**）
2. 下の「§4 決めていただきたいこと」の7項目を決める（数字と、文面の直し）
3. 決まったら私が反映し、オーナーがプロパティを立てて有効化する

## 1. なぜ作るのか

**A（途切れリマインド）**
セッション後にトレーナーが次回予約を案内しているが、その場で取らない方が忘れてしまう。
間隔が空くと成果が戻り、成果が戻ると継続率が落ちる。**継続率はこの事業のLTVそのもの**なので、
「次の予約が無い状態」を放置しないことが一番効く。人力の声かけでは抜けが出るため、機械で拾う。

**B（翌月解放リマインド）**
運用は「20日にトレーナーがシフト提出 → 25日に翌月分が解禁」。
ところが会員ホームの残数は「今日」基準なので、25日以降は「今月の残り0回」と見える。
お客様は**予約できないと誤解して翌月の枠を取りに来ない**（`next-month-notice.test.js` に記録済みの実害）。
画面側は直したが、**そもそも画面を開かない方**には届かない。だから通知で押す。
副作用として、人気の時間帯が「25日に一斉に埋まる」ので、トレーナーの稼働も前倒しで固まります。

## 3. 送る条件（いま入っている判定）

### 共通（両方に効く）
- `customer_line_map` の **認証状態 = verified**
- **contract_status = active**（空欄も送りません。判定できない＝送らない側に倒す）
- **lineUserId がある**（未連携の方は送りようがない。人数だけ数えます）

### A. 途切れリマインド
| 条件 | 既定 |
|---|---|
| 最終来店（`confirmed`／`consumed`）からの経過日数 | **3日以上** |
| 未来の予約 | **1件も無いこと**（1件でもあれば送らない） |
| 使える回数 | **1回以上**（残0の方に「予約して」と言わない） |
| 同じ方への再送 | 前回から **14日** 空ける |
| 来店履歴がゼロの方 | **送らない**（新規登録のみ・取消のみは対象外） |

### B. 翌月解放リマインド
| 条件 | 既定 |
|---|---|
| 送る日 | 毎月 **25日** |
| 翌月に使える回数 | **1回以上**（翌月時点で計算。今月の残数ではない） |
| 同じ月への再送 | **しない**（「2026-10」という月キーで冪等。26日以降に回っても増えない） |
| 未来の予約 | **あっても送る**（翌月はまだ埋まっていないため） |

## 4. 決めていただきたいこと

**すべて Script Properties なのでコード変更なしで変えられます。** 「これで」と言っていただければ私が設定します。

| # | 論点 | 私の推奨 | 迷いどころ |
|---|---|---|---|
| 1 | **送信時刻** | **10:00** | 前日リマインドが12時に動いています。同じ時間に重ねるとLINEが2通並ぶので外しました。夜（19時など）のほうが開封は良いかもしれません。 |
| 2 | **A：何日空いたら送るか** (`LB_NUDGE_IDLE_DAYS`) | **3日** | ご依頼どおり3日。週1ペースの方だと「まだ普通」の段階で来るので、**5日**のほうが煩わしくないかもしれません。 |
| 3 | **A：再送間隔** (`LB_NUDGE_COOLDOWN_DAYS`) | **14日** | 7日だと月2回。14日なら月1回が上限。催促の頻度は期待値より1段弱めておくのが安全だと考えます。 |
| 4 | **A：空きすぎた方を外すか** (`LB_NUDGE_IDLE_MAX_DAYS`) | **60日**（既定は0＝上限なし） | 3か月来ていない方への「次のご予約は？」は的外れで、むしろ退会の引き金になります。**ここは人が電話すべき層**なので、機械からは外すのを推します。 |
| 5 | **1回の上限** (`LB_NUDGE_MAX_PER_RUN`) | **50通** | 有効化した初日は「対象が全員たまっている」状態で走ります。上限が無いと一斉配信になり、LINEの通数（月5,000通）も一気に食います。 |
| 6 | **対象から外す条件** | 下の表のとおり | ★特に**休会中**の扱いは要判断（下記） |
| 7 | **文面（4言語）** | §5 の案 | 直していただく前提です |

### #6 の内訳

| 誰を | いま | 論点 |
|---|---|---|
| 未認証（pending） | **送らない** | 登録途中の方。誘導するなら別の文面が必要です |
| 契約切れ（expired） | **送らない** | 再契約のお誘いは別施策（文面が違う） |

## 6. 安全のための造り（何が起きても顧客に迷惑をかけないため）

| 守り | どう担保しているか |
|---|---|
| **勝手に送らない** | `LB_REMIND_ON=1` 以外は送信処理に入らない。無効時は記録も残さない（後で有効にしたとき再送抑止が誤作動しないため） |
| **繰り返さない** | `nudge_log` シートに「いつ・誰へ・どの月分を・成功したか」を残す。Aは日数、Bは月キーで抑止。**未達は「送った」と数えない**ので翌日また試せる |
| **一斉配信にならない** | 1回の上限（既定50通）。超えた分は翌日へ持ち越し |
| **トリガーは1日1回だけ** | 分ごと・時間ごとを作る書き方（`everyMinutes` / `everyHours`）を `Nudge.js` に一切書かず、**テストでソースを機械的に検査**している。過去に細かいトリガーを増やして応答が2倍以上遅くなった再発防止 |
| **1人の不備で全員止まらない** | 会員ごとに try/catch。落ちた会員は理由付きで一覧に出る（`sendLineReminders` と同方針） |
| **情報が足りないときは送らない** | 名簿や予約台帳が読めない＝誰が対象か判断できない → 送らずに理由コードを返す（fail-closed） |
| **個人情報を出力に残さない** | 一覧・戻り値・ログ行に氏名と lineUserId を入れない。会員は顧客IDの下4桁。内部用の宛先は `_lbNudgePublic()` で必ず落としてから外へ返す |
| **既存を壊さない** | 既存ファイルへの変更はゼロ（`gas-deploy.yml` の許可一覧に `Nudge.js` を足したのみ）。シート読み取りと `_lbPush` だけを使う |
| **LINEの通数** | `_lbPush` に用途タグ `nudge_idle` / `nudge_month_open` を付けたので、月の通数を何が食っているか用途別に追える |

### `nudge_log` シート（自動で作られます）
`送信日時 / 種別 / customer_id / 対象キー / 結果 / 詳細`。新しい行が上に積まれます（`reminder_status` と同じ）。
**氏名は書きません。** 再送判定に必要なので `customer_id` だけ入ります（制限付きSS内）。

## 7. 反映の手順（承認後）

1. （私）文面と数字を決定内容に直す
2. （私）`git push` → GitHub Actions「GASを反映する」を手動実行
3. **（オーナー）`production-gas` の承認ボタンを押す**（スマホのGitHubアプリで可）
4. **（オーナー）GASエディタで `lbNudgePreview` を実行** → 本番データで一覧を確認（まだ送りません）
5. （オーナー）一覧が想定どおりなら、Script Properties を設定
   - `LB_REMIND_ON` = `1`
   - 決めた数字（`LB_NUDGE_IDLE_DAYS` など。既定でよければ設定不要）
6. **（オーナー）GASエディタで `setupNudgeTrigger` を1回実行**（毎日1回のトリガーを登録）
   - ※ **私はトリガーを登録していません。**関数を用意しただけです
7. （オーナー）翌日 `nudge_log` シートを見て、想定どおりの人数に送れているか確認

**5と6は順番が大事です。** 6だけ先にやると毎日空振りするだけ（無害）。
5だけ先にやると次のトリガーまで動かない（無害）。どちらの順でも事故りません。

戻すときは `LB_REMIND_ON` を空にするだけで即止まります。

## 8. 私が気づいた懸念（判断材料）

1. **AとBが同じ日に重なる可能性**
   25日に「翌月分が解放」と「予約が途切れています」が同じ方へ2通飛びます。
   まとめて1通にするか、25日はAを止めるか。**私の推奨は「25日はAを止める」**（Bのほうが行動に繋がる）。ご指示があれば直します。

2. **休会の記録場所が無い**（§4 #6）
   いま休会中の方を機械的に除外できません。運用を教えてください。

3. **前日リマインドとの時刻の重なり**
   前日リマインドが12時。10時を推したのはこのためです。

4. **LINEの月間通数**
   前日リマインドと予約確定通知で既に相当使っています。Aが毎日走ると通数が増えます。
   上限50通/回と再送間隔14日で抑えていますが、有効化後1か月は `checkLineQuota` の警告に注意が必要です。

5. **「未来の予約が無い」の判定は `line_reservations` だけを見ています**
   サロンボード側にしか入っていない予約があると「未来なし」と誤判定して、予約済みの方に催促が飛びます。
   `syncExistingReservations` が6時間ごとに取り込んでいるので通常は大丈夫ですが、
   **氏名が一致せず `line_unlinked` に落ちている方は危険です。** 有効化前に `line_unlinked` を空にしておくのが安全です。

6. **予約状態の呼び名**
   ご依頼では「booked」でしたが、実データは **`confirmed`** です（`consumed`＝消化済み／`cancelled`／`changed`）。
   実装は実データに合わせて `confirmed` と `consumed` を「有効な予約」として扱っています。

7. **`nudge_log` は消さないでください**
   再送抑止の正本です。消すと、次の実行で対象者全員へもう一度飛びます。
