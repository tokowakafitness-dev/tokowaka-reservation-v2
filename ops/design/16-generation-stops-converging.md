# 設計16：世代が追いつかなくなる（段階3-b の土台が働かない）

> 2026-10-10 **第6版（関門①通過）**。Codex に4回差し戻され、5回目で通った。
> 　**第1版** 原因A・Bは承認。**原因Cを「直さない」判断が却下**された。
> 　　　　　 `calcMeta` が一度でも本当に変わると全員が behind になり、
> 　　　　　 キュー投入は3箇所だけなので自然回復しない。
> 　**第2版** 修復を「Worker で直接作り直す」とした。**3つ潰された**。
> 　　　　　 既定が試すだけ／範囲が当月〜翌月に狭まる／
> 　　　　　 ★古い入力で「最新」の印を付ける窓＝**顧客の残数が1回多く見える**。
> 　**第3版** 修復は**積むだけ**にし、作り直しは実績のある既存経路に任せた。
> 　　　　　 ①②③は消えたが、**積み方そのものが4つ潰された**。
> 　**第4版** ★`lbDwEnqueue` は冪等ではなかった（既存項目の `version`・`queuedAt` を
> 　　　　　 書き換える＝処理中の会員の成功した仕事を捨て、列の後ろへ送る）。
> 　　　　　 ★容量が溢れると**先に待っていた予約・取消の会員を捨てる**。
> 　　　　　 間隔は10分ではなく15分。取り出しは `queuedAt` の古い順。
> 　**第5版** ★人数の上限だけでは守れない。**バイト数(8,500)の上限が別にあり**、
> 　　　　　 書く瞬間に古い順で捨てる。積む前にバイト数も見て「超えたら足さない」。
> 　　　　　 結果を真偽値でなく状態で返し、栞を進める条件を分けた。
> 　**第6版** ★`source_at` は NULL を許し、migration 0017 は NULL で初期化している。
> 　　　　　 `MIN(source_at)` は NULL を無視する＝**主の見張りが盲目になる**。
> 　　　　　 新規項目の形（`version:1`・`leaseUntil` なし）と `WRITE_FAILED` の検査も固定。
> 地図：`ops/MODEL.md` §1（真実の在処）§3（不変条件 I9〜I11＝世代）§5（読み取りの契約）

## 1. 何が起きているか（実測）

shadow の心拍を読んだところ、**比べられる会員が 40名 → 3名 に落ちていた。**

```
10/09 夜（全会員を作り直した直後）  世代が追いついている会員: 40名
10/10 夜                            世代が追いついている会員: ★3名

比べ終わった会員: 1名 / 対象 40名（39名が一度も比べられていない）
入口ごと: [compat_member] 枠の後に弾いた behind:1 ／ [compat_home] behind:1
```

`behind` ＝ `built_version < source_version`＝「入力は進んだが、作り直しが追いついていない」。

**これは shadow が正しく働いた結果である。** ベースラインが溜まらない理由を数字で示した。

## 2. なぜ落ちるか（コードから確定・推測なし）

### 原因A：完全同期が「変わっていない行」まで世代を進める

`worker/src/routes/ingest.js`

```js
const full = body.deleteStale === true;
let existing = {};
if (!full) {                      // ★full のときは今の中身を読まない
  … SELECT で existing を埋める …
}

// 行を書くか
if (!full && !replaceCustomer && same(r, existing[String(key)])) { skipped++; continue; }

// 世代を進めるか（★同じ条件を使っている）
if (!full && !replaceCustomer && same(r, existing[String(key)])) continue;
```

`full` のとき `existing` は空のままで、`same()` も呼ばれない
→ **全行が「変わった行」として扱われ、全会員の `source_version` が +1 される。**

`pushToEdgeFullSync` は `ScriptApp.newTrigger('pushToEdgeFullSync').timeBased().atHour(4).everyDays(1)`
＝**毎晩4時に、全会員の世代が1つ進む。**

### 原因B：`calcMeta` が毎晩「全員」を進める

```js
} else if (affectsQuotaInputGlobally(kind) && stmts.length) {
  const st = bumpAllSourceStatement(nowMs);   // ★全員 +1
```

`calcMeta`（契約表の列の並び）は `QUOTA_INPUT_GLOBAL_KINDS` に入っている。
`full` のときは中身が同じでも必ず書かれるので `stmts.length > 0` が常に成立
→ **原因Aを直しても、これだけで毎晩全員が進む。**

### 原因C：追いついていない会員を拾う経路が存在しない

**キューに積む箇所は3つしかない**（`grep` で数えた）。

```
gas/LineBooking.js:4906   予約の書き込みのあと
gas/LineBooking.js:7142   固定枠ぶん
gas/PushToEdge.js:846     会員ぶんの押し出しのあと
```

**完全同期（4時）は1つも積まない**（`_pushToEdgeAllImpl` 885〜935行に `lbDwEnqueue` が無い）。
drain は積まれた会員を1回5名まで作り直すだけなので、**積まれない会員は永久に追いつかない。**


作り直しは段階3-a の二重書きが**書き込みのあった会員ぶんだけ**行う。
`grep` した結果、`quotaBuild` を定期実行するトリガーは**無い**。

```
入力の世代    毎晩 全員 +1
作り直し      活動のあった会員だけ

⇒ 活動のない会員は永久に追いつかない
```

40名 → 3名 は「10/10 に活動があったのが3名だけ」と整合する。

## 3. 何が壊れるか／壊れないか

**顧客に誤った数字は出ない。** 世代が合わなければ読み取りは答えず、写しへ落ちる＝安全側に倒れている（`ops/MODEL.md` §0）。

**壊れるのは段階3-b そのもの。**

```
① shadow がベースラインに到達しない（比べる母数が3名では意味がない）
② 読み取りをD1へ移しても、ほとんどの会員が写しへ落ちる
   ＝「正本をD1にする」目的が達成できない。遅さも鮮度の判定も残る
③ ②に気づかないまま「全員 on」にすると、
   **D1を正本と呼びながら実態は写しを読み続ける**状態になる
```

★②③は「静かに失敗する」形である（止まらない・誰も気づかない）。

## 4. 直し方

### 芯：**「行を書くか」と「世代を進めるか」を別の判断にする**

いまは同じ条件文を2回使っている。これが間違い。

| | 完全同期（full） | ふだんの押し出し |
|---|---|---|
| 行を書く | **全行書く**（`synced_at` が古い行を消す判断に要る） | 変わった行だけ |
| 世代を進める | **変わった行の会員だけ** | 変わった行の会員だけ |

### 具体

1. **`existing` を `full` のときも読む。**
   1日1回・表1つにつき SELECT 1回（契約88行・予約285行・棚卸し39行）。
   読み取りは安いという理由で差分比較を入れた経路なので、方針と矛盾しない。

2. **世代の判定から `!full` を外す**（書き込みの判定は触らない）。

```js
// 行を書くか（★変えない）
if (!full && !replaceCustomer && same(r, existing[String(key)])) { skipped++; continue; }

// 世代を進めるか（★!full を外す）
if (!replaceCustomer && same(r, existing[String(key)])) continue;
```

3. **`calcMeta` の全員進めを「中身が変わったとき」だけにする。**
   行のループで `changedInput` という**独立したフラグ**を立て、それだけを条件にする。
   `stmts.length > 0`（＝書いたか）では full のとき常に真になる。

   ★`stmts` を流用しない理由（関門①の指摘）：`stmts` にはこの後ろに
   世代の文・削除の文が積まれる。数で判断すると、**積む順番を変えた日に静かに壊れる。**

   ★`calcMeta` の行そのものが消える場合は扱えない。送り手は `m.length` が0なら
   **リクエストを送らない**（`PushToEdge.js:922`）ので、受け取る側に「消えた」が届かない。
   完全同期の削除で世代を進める処理も会員別入力（`affectsQuotaInput`）だけが対象
   （`ingest.js:403`）。よって**前提として固定する**：
   「`calcMeta` は正常に読めたなら必ず `contract_cols` 1行を送る」。
   読めなかったときは送らない（押し出しごと中止）＝世代も動かない＝写しへ落ちる側。
   この前提を検査で固定する（§5）。

4. **`existing` が読めなかったら進める**（いまの `catch` は `existing = {}`）。
   `same()` が偽になり全員進む＝写しへ落ちるだけ。
   逆（進めずに古い行を新しいと答える）は顧客に誤った残数を出す。**倒れる向きは変えない。**

5. **削除の経路は触らない。** 既に `staleIds` の会員だけを進めており正しい
   （2026-10-09 の関門②の指摘で直した箇所）。

### 原因C：追いついていない会員を拾う（収束経路）

**第1版では「直さない」と書いたが、関門①で却下された。** 却下の理由は正しい：

```
calcMeta（契約表の列の並び）が一度でも本当に変わると、全員の source_version が +1 される。
キューに積むのは3箇所だけで、どれも「その会員に何か起きたとき」。
⇒ 活動のない会員は、正当な変更のあとも永久に behind のまま
⇒ 「母数を測り直して様子を見る」では、低頻度の正当な変更やキュー漏れを**証明できない**
```

**原因A・Bは「余計に進めるのをやめる」話。原因Cは「進んだぶんが必ず追いつく」話。**
前者を直しても後者は要る。

#### 芯：遅れている会員を**作り直すのではなく、キューに積む**

**第2版では「Worker 側で直接作り直す」と書いたが、関門①で3つ潰された。**

```
① dry=0・alloc=1 を付けないと、既定は試すだけで**何も直さない**（quota.js:48,71,76）
② from/to を渡さないと当月〜翌月だけになる。キュー経路は会員ごとに
   「棚卸しの記録開始月 〜 当月+2か月（先の予約があればそこまで）」を導出している
   （PushToEdge.js:2729,2740,2741）。書き込みの前に世代の印を外すので（quota.js:212）、
   **範囲の外の行が現世代から落ちる**＝行数が合わず読めなくなる
③ ★顧客に実害：キューに積まれたが calcReservations がまだD1に届いていない窓では、
   source_version は進んでいない。そこで修復が走ると**古い入力で「最新」の印を付ける**
   ＝その会員の残数が1回多く見える（二重予約の恐れ）
```

①②③はどれも「キュー経路が既にやっていることを、修復経路でやり直さなかった」ことが原因。
**ならばやり直さない。**

```
足すもの   GET /quota/behind?limit=N&after=<cid>   … 読み取りだけ。遅れている会員のIDを返す
やること   そのIDを lbDwEnsureQueued でキューに積む（★lbDwEnqueue ではない。下の理由）
あとは     既存の drain がいつもどおり処理する
             → 台帳を読む → その会員の計算入力をD1へ送る → 正しい範囲で作り直す
```

これで①②③が同時に消える：

| | なぜ消えるか |
|---|---|
| ① dry/alloc | drain が既に正しく呼んでいる（`PushToEdge.js:2844`） |
| ② from/to | drain が会員ごとに導出している（`_edgeQuotaBuildOne`） |
| ③ 鮮度の窓 | **drain は作り直す前に入力を送る**（`PushToEdge.js:2837`→`2844`）。古い入力で印を付ける窓そのものが無い |

#### 誰が呼ぶか：**新しいトリガーは作らない**

**15分おき**の押し出し（`pushToEdgeLight`・`PushToEdge.js:1011`）の中で、
drain の**前に**「遅れている会員を積む」を1回入れる。★10分ではない（第3版の誤り）。

**キューが空かどうかを条件にしない。** `todo.length===0` は「全員が取り置き中」でも
成立し（`PushToEdge.js:2802`）、キューが空にならない運用では修復が永久に走らない。

#### ★積むのは `lbDwEnqueue` ではない（関門①の指摘・第3版の誤り）

第3版は「`lbDwEnqueue` は冪等だから積みすぎの害が無い」と書いたが、**誤り**。
既にいる会員に対しても `version` と `queuedAt` を書き換える（`PushToEdge.js:2542,2544`）。

```
drain が会員Aを version 3 で取り置いて処理中
→ 修復の巡回がAをもう一度積む → version 4 になる
→ 作り直しは成功したのに _lbDwDone が version 不一致を見て REQUEUED を返す
   （PushToEdge.js:2642-2643）＝**成功した仕事を捨てて、もう一度やる**
```

さらに drain の取り出しは **`queuedAt` の古い順**（`PushToEdge.js:2601`）。
`queuedAt` を押し直すと、その会員は**列の後ろへ送られる**。
＝修復の巡回が、取消を伝えるべき会員を待たせる。

**修復専用の操作を分ける。**

```
lbDwEnsureQueued(customerIds)
  ・キューにいなければ足す。新規の項目は**この形に固定する**：
       q[cid] = { version: 1, queuedAt: Date.now() }
       ★leaseUntil は付けない（取り置きは _lbDwClaim の役目）
  ・既にいれば version・queuedAt・leaseUntil を**一切触らない**
  ・既存の lbDwEnqueue の意味（＝実データが変わった）は変えない
```

★`version: 1` から始める理由：修復で積んだあとに実データの変更が来れば 1→2 になり、
drain が取り置き中なら確実に `REQUEUED` になる（`PushToEdge.js:2642`）。
＝**実データの変更が修復に埋もれない。**

★**真偽値を返さない**（関門①の指摘）。結果によって栞を進めるかが変わるため、
**状態を返して呼ぶ側が判断する**。

| 結果 | キュー | 栞 | なぜ |
|---|---|---|---|
| `ADDED` | 書く | 進める | 積めた |
| `EXISTS` | 触らない | 進める | 既にいる＝目的は達している |
| `CAPACITY` | 触らない | 進める | 空きが無い。同じ区間で足踏みしない |
| `CURSOR_CHANGED` | 触らない | 進めない | 別の実行が先に進めた。結果を捨てる |
| `BROKEN` | 触らない | **進めない** | キューが壊れている。進めるとその会員は1周するまで再試行されない |
| `LOCKED` | 触らない | **進めない** | 同上 |
| `WRITE_FAILED` | 不明 | **進めない** | 同上 |

既存コードも壊れている（`PushToEdge.js:2458`）とロックが取れない（`:2452`）を
区別して扱っている。**同じ区別を引き継ぐ。**

#### ★容量：予約由来の会員を追い出さない（関門①の指摘）

`MAX_QUEUE` は80で、溢れたら**古い順に捨てる**（`PushToEdge.js:2426,2548,2550`）。
古い＝先に待っていた予約・取消の会員である。
**修復を積むために、それを捨てては本末転倒。**「捨てた件数を記録する」は検知であって優先順位の保証ではない。

★さらに**バイト数の上限が別にある**（関門①の指摘・人数ガードだけでは守れない）。

`_lbDwWriteQueue` は 8,500バイトを超えると、守る会員以外を**古い順に捨てて**から書く
（`PushToEdge.js:2478,2497,2511`）。コード自身が「人数の上限だけでは守れない」と書いている（`:2475`）。
＝人数ガードを通しても、**書く瞬間に予約由来の会員が消え得る。**

```
積む前に、2つとも見る（どちらかでも超えたら積まない）
  ① 人数    いまのキュー人数 + ★足りない人数 > MAX_QUEUE - 10
              ★N ではない。候補のうち「まだキューにいない人数」で数える
                （2名とも既にいれば増える人数は0）
  ② バイト  候補を足したあとの JSON が 8,500バイトを超える

  超えたら → **キューを書かない**（既存の「超えたら削って収める」はしない）
            behind_enqueue_skipped_capacity に記録する
            栞は進める（次の巡回で先へ行く。同じ区間で足踏みしない）
```

★バイト数の計算は `_lbDwWriteQueue` の中の `_bytes` を**共通の関数に切り出して使い回す**。
別に書くと、数え方が片方だけ変わった日に静かにずれる。

★`MAX_QUEUE - 10` は**初期の運用値**であって安全の保証ではない。
予約が集中して10件を超えて積まれれば、既存の `lbDwEnqueue` 自身が古い項目を捨てる。
**安全を保証しているのは上の「超えたら足さない」ガードのほうである。**
10枠（drain 約2回分）は「修復が通常の更新を圧迫しない」ための余裕で、実測して調整する。

#### 何人ずつ積むか：**まず2名**

15分おき・drain は1回5名（`MAX_PER_RUN`）。

| N | 40名が追いつく最短 | drain の5枠のうち修復が使う分 |
|---:|---:|---:|
| 1 | 約10時間 | 1 |
| **2** | **約5時間** | **2（実データに3枠残る）** |
| 5 | 約2時間 | 5（★実データが待たされる） |

N=5 にすると修復が全枠を占める。**初期値は2**とし、
キューの長さ・behind の減り方を記録して後から調整する（推測で増やさない）。

#### 飢えないようにする（関門①の指摘）

`customer_id` 順の先頭N名が毎回失敗すると、6人目以降に永久に進まない。
**巡回の栞（しおり）を持つ。**

```
Script Property  LB_DW_BEHIND_AFTER   最後に見た customer_id
毎回             after=<栞> から limit 件
返りが limit 未満（＝末尾に到達）  → 栞を空に戻して先頭から
積めなかった会員（容量不足・既にいる）も**栞は進める**
```

★**栞の更新とキューへの追加は同じロックの中で行う**（関門①の指摘）。

```
① 栞を読む（ロックの外）
② WorkerへGET（★通信中はロックを持たない。15秒のロック待ちを食い潰さない）
③ ロックを取る → 栞が②の時点と変わっていたら**結果を捨てて次回へ**
   変わっていなければ、まとめて追加 ＋ 栞の更新を**同じロック区間で**行う
④ Worker が失敗したら栞を更新しない
栞が消えていた・壊れていたら空扱い＝先頭から（正しさではなく進捗の最適化なので害がない）
```

★**同じロックの中でも、プロパティの2回の書き込みは不可分ではない**（関門①の指摘）。
だから**順序を契約にする**：

```
キューを書く → 成功を確かめる → **最後に栞を書く**

キューを書けて栞を書けなかった  → 同じ区間をもう一度取るだけ（EnsureQueued なので無害）
栞を先に書いてキューを書けない  → ★その区間が1周するまで飛ばされる（これを避ける）
```

`_lbDwWriteQueue` の `setProperty` は例外を握り潰さない（`PushToEdge.js:2521`）ので、
「書けなかったら栞を書かない」は実装できる。

#### なぜ Worker の cron にしないか

`wrangler.toml` に `[triggers] crons` は無く、`scheduled` ハンドラも無い（確認済み）。
入れれば GAS から独立できて筋は良いが、**今回は見送る**：

- 新しい実行経路が増える（取り込みとの同時実行・CPU上限の判断が別に要る）
- いま追っている「日次点検が6分超で落ちる」件と切り分けられなくなる
- そして**そもそも要らなくなった**。修復はキューに積むだけで、作り直しは既存経路が行う

★ロードマップ⑤「GASを外す」でまとめて設計する。**ここには「見送った」と書き残す**
（同じ疑いを二度調べないため）。

#### 直せない会員が巡回に居座る場合（関門①の指摘）

`/quota/behind` は `customer_sync_version` だけを見るので、契約入力が無くなった会員や
何度やっても作り直せない会員を返し続けうる（この表に顧客表への外部キーは無い・
`migrations/0014_customer_sync_version.sql:18`）。

**検索から除外しない。** 除外すると本当の異常を隠す。

★**「繰り返し作り直せない会員を別に数える」のは今回やらない**（関門①の指摘で範囲から外した）。
理由：「何回で繰り返しか」「成功でどうリセットするか」「どこに回数を置くか」が未定義で、
キューの項目は `version`・`queuedAt`・`leaseUntil` しか持たない（`PushToEdge.js:2417`）。
`version` は実データが変わった回数なので失敗回数には使えない。**作るなら別の入れ物が要る。**

いまは**最古の `source_at` の滞留**が主の見張りとして機能するので、それで足りる。
足りないと分かったら、そのときに設計する（推測で入れ物を増やさない）。

#### 追いつかないままになったら気づけるか

追いつかないこと自体は顧客に害を出さない（写しへ落ちるだけ）。
だが**気づけないと3-bが永久に完成しない**ので、見張りを付ける。

★**「前日より増えたら」だけでは足りない**（関門①の指摘）。

```
前日 5名 → 本日 5名 → 翌日 5名  ＝ 永久に鳴らない
```

同じ5名が居座っているのは、まさに検知したい状態である。**滞留の長さを見る。**

`customer_sync_version.source_at` に「入力が進んだ時刻」が入っている（`sync-version.js:41,46`）。
日次点検（7時）で次の3つを見る：

| 鳴る条件 | 重み | なぜ |
|---|---|---|
| ★最古の `source_at` が **6時間**より古い | 主 | 居座っている。件数ではなく滞留そのものを見る |
| 件数が前日より増えた | 主 | 新しく追いつけなくなった |
| 同じ件数が3日続いた | 補助 | 会員が入れ替わって同数のこともあるので、これ単独では重大にしない |

★`behind_enqueue_skipped_capacity`（容量で積めなかった回数）も1行出す。
増え続けているなら、修復が永久に回っていないという意味になる。

#### ★`source_at` が入っていない会員（関門①の指摘・見張りが盲目になる）

`source_at` は NULL を許す（`migrations/0014_customer_sync_version.sql:22`）。
しかも**既存データへ世代を後付けした migration 0017 は `source_at=NULL` で作っている**
（`0017_seed_sync_version.sql:42,44`）。

SQL の `MIN(source_at)` は NULL を無視する。
＝**遅れている会員の `source_at` が全部 NULL なら、主の見張りが何も言わない。**

```sql
SUM(CASE WHEN source_version > built_version AND source_at IS NULL
         THEN 1 ELSE 0 END) AS behind_source_at_missing
```

これを**独立した異常**として扱う。`> 0` なら警告。
★倒れる向き：「時刻が無いから新しい扱い」ではなく、**「滞留を判定できないから警告」**。

6時間の根拠：15分おきに2名ずつなら40名で約5時間。完全同期は4時なので、
正常なら9時ごろには追いついている。**余裕を見て6時間**に置く。鳴りすぎたら実測してから緩める。

★**ただし検知は最長およそ30時間遅れる。** 点検は7時に1回だけ（`LineBooking.js:3349`）。
4時に遅れ始めた会員は7時には3時間なので鳴らず、次の点検は翌日7時＝約27時間後になる。

```
これを許容する（いまは許容する）
  理由：遅れていること自体は顧客に害が無い（写しへ落ちるだけ）。
        早く知りたいのは「3-bが進まない」という私の都合である
もっと早く知りたくなったら
  15分の心拍（押し出しの診断値）に載せる。点検を増やさない
```

shadow の合格判定は既に「比べ終わった会員 35名以上」を見ている＝ここでも露出する。

## 5. 確かめ方（この設計で足す検査）

| 確かめること | どう確かめるか |
|---|---|
| full でも中身が同じなら世代が進まない | 同じ行を `deleteStale:true` で2回取り込み、`source_version` が増えないこと |
| full で中身が変わったら進む | 1行だけ値を変えて取り込み、**その会員だけ** +1 |
| full でも行は全部書かれる | 2回目の取り込みで `synced_at` が更新されること（古い行の削除が壊れない） |
| `calcMeta` は変わったときだけ全員進む | 同じ `calcMeta` を2回 → 誰も進まない／変えて1回 → 全員 +1 |
| `calcMeta` の列が1つ減ったら全員進む | `payload` の `headers` を1つ減らして取り込み → 全員 +1 |
| `calcMeta` は読めたら必ず1行送る | 押し出し側のコードを検査で固定（0行で送る経路が無いこと） |
| 全員進めは `stmts.length` を見ていない | `changedInput` を偽にしたまま行を書かせ、全員進まないこと |
| `existing` が読めないときは進む | SELECT を失敗させ、全員 +1（安全側）になること |
| `scope:'customer'` は同じ行でも・0行でも進む | 既存の不変条件。退行していないこと |
| `staleIds` が読めないときは消さない・時刻も押さない | 既存の不変条件。退行していないこと |
| 遅れている会員を拾える | `GET /quota/behind` が `source > built` の会員だけを返すこと |
| 栞で先へ進む | `after=<cid>` を渡すとそれより大きいIDだけ返ること |
| 先頭N名が失敗しても先へ進む | 1周したあと N+1 以降が拾われること（飢えないこと） |
| 末尾に到達したら先頭へ戻る | 返りが `limit` 未満なら栞を空に戻すこと |
| 修復は**積むだけ**で作り直さない | 修復の経路に `/quota/build` の呼び出しが無いこと |
| 積んだ会員は drain が入力を送ってから作り直す | 既存の順序（入力→作り直し）が壊れていないこと |
| キューの状態で修復を止めない | `todo` が空でも `queued>0` でも、毎回積むこと |
| ★`EnsureQueued` は既存項目を触らない | 既にいる会員に対して `version`・`queuedAt`・`leaseUntil` が変わらないこと |
| ★処理中の会員を再キューしない | 取り置き中の会員を `EnsureQueued` しても `REQUEUED` が起きないこと |
| ★容量が無ければ積まない | キューを `MAX_QUEUE - 10` まで埋めてから巡回させ、1人も追加されないこと |
| ★予約由来の会員を追い出さない | 上の場合に、先に待っていた会員が消えていないこと |
| 積めなくても栞は進む | 容量不足で積めなかった回も `after` が前進すること |
| 栞と追加が同じロックの中 | 通信中はロックを持たず、ロック後に栞が変わっていたら捨てること |
| 栞が消えても壊れない | プロパティを空にしても先頭から回り直すこと |
| ★バイト上限を超えるなら足さない | 8,500バイト直前まで埋めて巡回させ、**既存の会員が1人も消えていない**こと |
| 容量の人数は「足りない人数」で数える | 候補2名のうち1名が既にいるなら、増える人数は1と数えること |
| バイトの数え方が1か所 | `_bytes` が共通化され、修復側に別実装が無いこと |
| キューが壊れていたら栞を進めない | `BROKEN` で栞が動かないこと |
| ロックが取れなければ何もしない | `LOCKED` でキューも栞も変わらないこと |
| Worker が失敗したら栞を進めない | 失敗・不正JSON・合言葉違いのそれぞれで栞が動かないこと |
| 栞の競合では結果を捨てる | `CURSOR_CHANGED` でキューも変わらないこと |
| キューを書いてから栞を書く | 栞の書き込みを失敗させても、次の実行が重複なく回復すること |
| ★キューの書き込みが失敗したら `WRITE_FAILED` | `setProperty` を失敗させ、栞が動かず・既存キューが空で上書きされず・次回同じ栞から再試行されること |
| 新規の項目は `version:1` で `leaseUntil` が無い | 修復で積んだ直後の項目の形を固定すること |
| ★`source_at` が無い会員を警告する | `source > built` かつ `source_at IS NULL` の会員がいると鳴ること |
| 時刻がある会員の最古は正しく出る | NULL が混ざっていても、時刻のある会員の最古を取り違えないこと |
| ★修復中に実データの変更が入っても消えない | `lbDwEnqueue` の `version` 更新を修復が上書きしないこと |
| 窓口は合言葉が要る | `GET /quota/behind` が合言葉なしで拒否されること |
| `limit` に上下限がある | 範囲外を渡したら丸められるか断られること |
| 0件なら栞を先頭へ戻す | 末尾に到達した次の巡回が先頭から始まること |
| 通して最後に追いつく | behind取得→EnsureQueued→drain を通した結合検査で `fresh` になること |
| 滞留を検知する | `source_at` が古い会員を置くと点検が鳴ること（主）／同数3日は補助として出ること |
| 直せない会員を除外しない | 契約入力の無い会員も `behind` に出続けること（数えるのは今回やらない） |
| 削除経路は退行していない | 既存の検査（`dualwrite-*`）が通ること |

★**検査は「壊して落ちる」ことを確かめてから信じる。** 少なくとも次を壊して落ちることを確認する：
`!full` を世代の判定に戻す／`changedInput` を `stmts.length` に戻す／`behind` の条件を `>=` にする。
