# 設計47 定期の押し出しが ScriptLock を握り続け、予約・取消・変更がロック待ちで落ちる

> 2026-11-20・CTO（CEO玄から受けた）。**下書き（関門①の前）**。実装・push・GAS 反映はしていない。
> 版の印：実装時に GAS `LB_HEALTH_BUILD`・`LB_EDGE_BUILD` を実装日に。
> 戻し方：Script Property `LB_EDGE_LEASE`（既定オフ＝今と1文字も同じ ScriptLock の排他）。切り替えはエディタの関数 `lbEdgeLeaseSetOn/Off`（画面からプロパティを足さない・MODEL.md §7）。

## 目的（1行）
定期の押し出し（10分・15分・30分）が ScriptLock を握ったままシートを読み Worker へ送るせいで、同じロックを10秒しか待たない予約・取消・変更が例外で落ちるのを止め、落ちた回数と押し出しがロックを持った時間を毎日数えられるようにする。

### 1-1 起きたこと（実測・本番 `LB_WRITE_PERF`・版 2026-11-18a）
- 11/19 12:01:22・12:01:49・12:02:18 の `changeReservation` が3回続けて `THROW`。最後の印は `preType`、その後の時間（`other` に入る）が 10,079〜10,167ms、`lock`=0。
- `changeReservationLine`（gas/LineBooking.js 9331〜9335）は `_lbWpMark('preType')` の直後に `LockService.getScriptLock().waitLock(10000)`。`waitLock` は取れなければ**例外を投げる**（`tryLock` と違い false を返さない）。印が `preType` のまま約10秒で例外＝**このロック待ちの時間切れと読むのが筋**。例外の文そのものは記録しない（I77）ため、**文言による確認はできない（未確認）**。
- 3回は約66秒にまたがる。各回の待ちは10秒なので、**12:01:12ごろ〜12:02:28ごろの少なくとも約76秒、ScriptLock がほぼ切れ目なく誰かに握られていた**（1つの実行が握り続けたのか、複数が続けて握ったのかは**未確認**）。

### 1-3 押し出しが ScriptLock を必要とする理由
- **コードに書かれている理由は「押し出し同士の重複防止」だけ**：1500〜1501行「押し出し同士が重ならないようにする。定期実行と手動実行が重なると、古い方が後から完了して新しい内容を巻き戻しうる」。`_edgeLocked` の説明（1520〜1529）も押し出し同士の待ち時間の話しかしていない。
- **書き込みとの排他を前提にした不変条件は、コードと MODEL.md からは見つからない**。根拠：
  1. 書き込み直後の会員1人分の送信 `_edgeSendAfterWrite`（1042〜1049）は `_edgeLocked` を**通らない**。`edgeAfterWrite` は `handleLineGet` で書き込みのロックを放した後に呼ばれる（LineBooking.js 270）。つまり**今でも、会員1人分の送信と定期の押し出しは並んで走っている**。
  2. I79（MODEL.md 208）の covers は「写しを作るために台帳を読む**前**に読んだ通し番号」（`_edgeCoversSeqNow` 1162・呼び出し 930／959／1015／1575）。書き込みは台帳を書いた**後**で番号を進める（`edgeAfterWrite` → `lbDwEnqueue` 4221）。押し出しが書き込みの途中の台帳を読んでも、そのとき読んだ番号は書き込みの番号より小さい → `dirty_seq > covers` で門が閉じる（遅いが正しい側）。covers は**置き換え**（MAX にしない）なので、古い押し出しが後から届いても閉じる側に倒れる。
  3. I31（MODEL.md 159）の D1 の残数も `built_covers_seq >= dirty_seq` のときだけ新しいと名乗る＝番号の順序で守っていて、ロックで守っていない。
  4. 枠（slots）の巻き戻しは `LB_SLOTS_LAST_PUSHED_BUILT_AT` の世代比較で守っている（`_edgeSendSlots` 1726〜）。
- `_lbDwCurrentSeqInLock` という名前は「ロックの中で呼ぶ」ことを示すが、中身は Script Property 1つを読むだけ（4213〜4217）。I79 に要るのは「台帳を読む前に読む」順序であって、ScriptLock の中であることではない（と読める）。
- **未確認のまま残るもの（関門①で問う）**：
  - (U1) **書き込みの台帳への書き込みが、番号を進める前に他の実行から見える状態になっているか**（`SpreadsheetApp.flush()` を番号の前に通るか）。変更は 9343 で flush しているが、全経路は確かめていない。★ただしこれは**今の ScriptLock でも防げていない**（書き込みは書き込みのロックを放してから `lbDwEnqueue` で番号を進め、押し出しはその後にロックを取って番号と台帳を読める）。手段Aが新しく開く穴ではないが、手段Aの前提なので確かめる。
  - (U2) covers・世代の門の**外**にある表（trainers・customers・recurring・body・計算入力 calcContracts／calcMeta／calcReservations／opening）で、押し出しが書き込みの**途中の状態**を読んで送ったとき、顧客に誤った値が出る経路があるか。今は ScriptLock で書き込みの区間の途中を読まない。手段Aでは読みうる。計算入力は I53（材料4つが同じ回・45分以内）と I31 で守られていると読めるが、名簿の行の書き換え（会員の紐付け・`MemberMerge`）の途中を `customers` に載せる影響は**未確認**。
  - (U3) 押し出しの本体（`_pushToEdgeAllImpl`・`_pushToEdgeHomeImpl`・`_pushToEdgeSlotsImpl` から呼ばれる関数）の中に、「呼び出し元が ScriptLock を持っている」ことを前提にしたものが無いか。PushToEdge.js の grep では押し出しの本体の中に ScriptLock を取る箇所は見当たらない（1064 は書き込みの経路、1894 は shadow の掃除＝ロックを放した後）。他のファイルから呼ばれる関数までは**未確認**。

## 2. 影響の見積もり

### 2-1 1時間のうち書き込みが落ちうる秒数（★推定・実測ではない）
書き込みは ScriptLock を10秒待つ。1回 H 秒握る押し出しに対して、書き込みが落ちる「到着の窓」は max(0, H−10) 秒。
| 押し出し | 回/時 | 1回に握る秒数 H の出所 | 落ちうる秒/時 |
|---|---|---|---|
| slots | 6 | 約2秒（1647行コメント） | 0 |
| light（`pushToEdgeAll(false)`） | 4 | 約43秒（1526・1684行コメント・2026-10-11）／**11/19 の実測から下限76秒**（1-1・1つの実行と仮定した場合） | 132（43秒）〜264（76秒） |
| home | 2 | 下限 約10秒（LbBatch.js 20「9.7秒」・過去）／上限 4分＋送信（`EDGE.BUDGET_MS`） | 0〜約480 |
| 合計（昼間） | | | **およそ130〜750秒/時（2〜21%）** |

- 4時の完全同期（全部＋残数）は1日1回。深夜で書き込みは少ないが、握る時間は最大（全部＋4分）。
- **3本が毎時0分・30分に重なるかは未確認**。GAS の `everyMinutes(N)` は作成時の位相で動き、時計の0分に揃う保証は無い。重なった場合、light と home は待ち5秒で見送る（`LB_EDGE_LOCK_SKIPS`）ので**握る時間は延びにくい**。延びるのは slots（90秒待つ）が直後に続く分（約2秒）。
- GAS のロックの待ち行列が先着順かは**未確認**（待っていた slots と書き込みのどちらが先に取るか分からない）。
- 書き込みのロックを取れた後も、`edgeAfterWrite` の `lbDwEnqueue`（`_lbDwLocked`・ScriptLock を15秒待つ・3929〜3932）が押し出しと当たれば応答が最大15秒延び、画面の20秒の待ち切り（`liff/index.html` 1084）を越えうる（**コードからの推定・未計測**。`edgeQ` の実測中央は 1.5秒）。

1. `waitLock` の例外 → `handleLineGet` の catch（LineBooking.js 262〜267）が記録して**投げ直す** → `doGet` の catch（gas/コード.js 70〜72）が `{ error: <例外の文> }` を返す（`success`・`code`・`message` が無い）。

   ＝**実際は混んでいただけなのに「その枠は取れない」と読める誤った案内**。11/19 は3回押し直されている。

**UserLock・DocumentLock を使わない理由**
- UserLock：カレンダー同期（`_lbCalSyncCore` 2453 `tryLock(2000)`）と件数の記録（2662 `tryLock(3000)`）が既に使う。押し出しが UserLock を数十秒〜4分握ると、**今度は同期が見送られる**（2450行で避けた問題を別の場所へ移すだけ）。
- DocumentLock：`gas/.clasp.json` に親の文書が無い＝スタンドアロンのスクリプトと読める（**推定**）。その場合 `getDocumentLock()` は null を返す（GAS の仕様）。

## 4. 推奨：A（リース）＋ A2（BUSY）を1回の反映で。A はスイッチ既定オフ

### 4-1 リースの形（A）
- 値：Script Property `LB_EDGE_PUSH_LEASE` ＝ `{ token, until, label, at }`（token は `Utilities.getUuid()`。会員ID・氏名を持たない）。
- 取る：ScriptLock を `tryLock(min(2000, 残りの待ち))` → リースが空か期限切れなら自分を書く → **ScriptLock を放す** → 本体 `fn()` を ScriptLock なしで走らせる。他が持っていれば ScriptLock を放して `Utilities.sleep(2000)` → 待ち時間（slots 90秒・他5秒＝今と同じ）まで繰り返す → 尽きたら見送り（`_edgeRecordLockSkip(label)` は今のまま）。
- 返す：`finally` で ScriptLock を短く取り、リースの token が自分のときだけ消す（期限切れ後に他が取ったリースを消さない）。
- 期限 `LEASE_MS`：10分（GAS の1実行は6分。`LB_DW.LEASE_MS` と同じ余裕の取り方）。落ちた実行のリースは最大10分残り、その間の押し出しは見送られる（写しが古くなる＝Worker は鮮度・I79 で答えず GAS へ＝遅いが正しい）。期限切れのリースを奪った回は数える。
- ★**呼び出し元が既に ScriptLock を持っている場合**（作業依頼の書き込み `EdgeJob.js` 262〜264 が `pushToEdgeAllText` を呼ぶ等）：入口で `hasLock()` を見て、持っていたら**放さない**（リースの読み書きだけする）。放すと作業依頼のロックが途中で外れる。
- **4時の完全同期は ScriptLock のまま**（リースも取る）。消えた行を削除する唯一の経路で、名簿の書き換えの途中を読むと行が消えうる（U2）。深夜で書き込みが少ないので害が小さい。
- スイッチ `LB_EDGE_LEASE !== '1'`（読めない場合を含む）→ 今の `_edgeLocked` と同じ（ScriptLock を本体の間握る）。

### 4-2 A2（書き込み側）
- 予約の芯 6114・取消 8647・変更 9335・オーナー当日取消の取り消し 9203・固定枠 9600／9679・会員の紐付け 687／772 の `waitLock(10000)` を `tryLock(10000)` に替え、取れなければ `_lbWpMark('lock')` の後 `{ success:false, code:'BUSY', message:'混み合っています。少し時間をおいて再度お試しください。' }`（まとめて予約 9980 と同じ文）。
- 画面は変えない：会員の確定画面は `res.message` を出す（4189）→ 正しい案内になる。`BUSY` は SLOT_TAKEN ではないので枠の一覧の取り直しもボタンの封鎖もしない（押し直せる）。
- ★変更 9334 は `try` の**前**でロックを取る＝取れなければ何も書いていない（補償は要らない）。予約の芯 6114 は変更から呼ばれるときは既に持っている（`hasLock`）ので通らない。

### 4-3 なぜ A か
- 書き込みが待つ相手が「他の書き込み（数秒）」だけになる。押し出しの重さ（76秒〜4分）と無関係になる。
- 押し出し同士の重複防止（コードに書かれた唯一の理由）はそのまま残る。
- 変える面積が `_edgeLocked` 1関数に閉じ、既にある型（リース）を使い、スイッチで即戻せる。
- 副次の効果（推定）：通知の送り直しの取り分け（30秒待ち）・作業依頼（30秒待ち）・`lbDwEnqueue`（15秒待ち）も押し出しに待たされなくなる。

### 4-4 判定できないとき何を返すか
| 状況 | 返すもの |
|---|---|
| スイッチが読めない | オフ（今の ScriptLock） |
| リースの値が壊れている | その回は押し出さない（`broken` を数える）。壊れた値を初めて見た時刻を残し、`LEASE_MS` を過ぎたら上書きする（握っていた実行は必ず終わっている）。写しは古くなるだけ＝Worker は答えず GAS |
| リースを取る・返すための ScriptLock が取れない | 取る側は見送り（数える）。返す側は返さない（期限で切れる・数える） |
| 書き込みがロックを取れない | `BUSY`（何も書かない） |

## 5. 「倒れた回数と母数」を日次点検で数える記録

### 5-1 押し出しの側：`LB_EDGE_PUSH_COUNT`（Script Property・直近3日・数だけ）
```
{ 'yyyy-MM-dd': { mode:'S'|'L',
    slots|light|home|full|all: { n, ok, skip, waitMax, holdMax, holdSum, over10Sum, expiredTake, broken } } }
```
- `holdMs`＝本体を走らせた時間。`over10Sum`＝Σmax(0, hold−10秒)（**ScriptLock のときは書き込みが落ちうる窓の秒数そのもの**＝2章の推定を実測に置き換える）。
- 書く場所：オフでは ScriptLock を放す直前、オンではリースを返す ScriptLock の中＝**新しいロックを足さない**。見送り（ロックを取れなかった回）はロック無しで足す（同時に2つ見送れば1つ落ちうる＝**下限**と表示）。
- ★**スイッチがオフのまま先に入れる**（同じ反映）。オンにする前に、今の握る時間と落ちうる窓を数日分測る。

### 5-2 書き込みの側：`LB_WRITE_LOCK_COUNT`（直近3日・数だけ）
```
{ 'yyyy-MM-dd': { <op 9つ>: { n, busy, lockMsMax } } }
```
- `n`＝`_lbWpStart` が対象とした書き込みの数（母数）、`busy`＝ロックを取れず `BUSY` を返した数。`_lbWpFinish` で足す。ロックを取らない（I77 と同じ理由）＝同時に終わった2件の片方が落ちうる＝**下限**と表示。全数が要れば `booking_metrics` との突き合わせを後で考える（今回はしない）。
- `LB_WRITE_PERF` のリング（60件・標本）は今のまま。コード `BUSY` で行が残る。

### 5-3 日次点検（`dailyHealthCheck`／作業依頼 `remaining {writePerf:true}` に1行ずつ・数だけ）
| 条件 | 重さ |
|---|---|
| 昨日の書き込みの `busy` ≥ 1 | warn（op ごとの `busy/n`） |
| mode S で `over10Sum` > 0 | warn（落ちうる窓の秒数・最長の `holdMax`） |
| mode L で `expiredTake` ≥ 1 | warn（6分で落ちた押し出しがある） |
| `broken` ≥ 1 | high |
| light・home の `holdMax` > 300秒 | warn（6分の制限に近い） |
| 昨日の記録が無い（押し出しが走った証拠が無い） | high |

個人情報：どの記録も op 名・押し出しの種類・数・ミリ秒だけ。会員ID・氏名・LINE ID・予約ID・例外の文を持たない。

### 5-4 天井
- Script Property が4つ増える（`LB_EDGE_LEASE`・`LB_EDGE_PUSH_LEASE`・`LB_EDGE_PUSH_COUNT`・`LB_WRITE_LOCK_COUNT`）。画面からは足せない（50個を超えている）＝コードが書く／切り替えはエディタの関数。値は各1KB未満の見込み（3日×5種×9項目）。
- トリガー：0本増（上限20本）。
