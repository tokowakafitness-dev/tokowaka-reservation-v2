## 0. 目的（1行）

録音の文字起こしから、AI に**まず「今日のセッションで実際に何があったか」を推論してまとめさせ**、それをもとに種目・重さ・回数・セットと種目の備考・お客様の状態・次回やることをカルテの形に割り振り、
**不明確なところに「要確認」の印を付けた下書きを1画面で一度に見せ、トレーナーが直して入れる**。AI の出力は今どおり保存しない（I71・I76-6）。

## 5. Worker（routes/karte-ai.js）

### 5-1 形式の選び方（高1・中7）
```
KARTE_AI_FORMAT   未設定（キーが無い・空文字）＝v1／"v1"／"v2"（厳密一致）。それ以外の値＝AI を閉じる
要求の client_ai_format   数値の 2 のときだけ「画面が v2 を扱える」。無い・他の値は v1 の画面
使う形式 = (KARTE_AI_FORMAT === "v2" && body.client_ai_format === 2) ? v2 : v1
```
- 不正な `KARTE_AI_FORMAT`（"V2"・"2"・"v3" 等）は、切替の段（外へ送る前・数える前）で 503 `AI_NOT_CONFIGURED` detail `FORMAT`。`k_training` の起動の印 `aiDraft` も偽になる（ボタンが出ない）。日次点検（karte-ai-health）に `formatBad` を出し warn。
- 応答の `draft.v` に**実際に使った形式**（1 か 2）。`karte_ai_log.fmt` にも実際に使った形式。
- `client_ai_format` の型が数値でない（"2" の文字列）は v1（400 にしない＝古い画面を壊さない）。知らない鍵の検査（KEYS）には足す。
- 今の liff/karte.js（キーを送らない）は、`KARTE_AI_FORMAT="v2"` でも v1 を受け取る＝今のカードの流れのまま（検査 V2-12）。

### 5-2 指示（AI_SYSTEM v2・要点）
1. **最初に、文字起こし全体から「今日のセッションで実際に何があったか」を推論して `summary.flow` に時系列の短い文で書く**（言い直し・聞き違い・予告と実施の区別を前後の流れから推論してよい）。
2. その要約に沿って、種目・セット（重さ・回数）・セットの備考・種目の備考・お客様の状態・次回やること・お客様へ・次回までに を割り振る。
3. セットごとに `basis`：文字起こしにその数字がそのまま出ている＝`said`、流れからの推論＝`inferred`。どちらも `evidence` に根拠の部分を**一字一句そのまま**80字以内で抜き出す。数字が分からなければ null にして `unsure` に理由。
4. 迷ったもの（予告か実施か・どの種目の数字か・聞き違いの疑い）は `unsure` に理由。項目に結びつかない不明点は `unclear`。
5. 体の痛み・怪我・診断・服薬・体調不良は `caution` にだけ書く（要約・unsure にも書かない）。疲れ・可動域・フォームの癖・意欲など医療でない状態は `condition`。
6. 雑談・政治・宗教・思想信条・性的指向・家族の事情・第三者の話は出さない。人の名前を出さない（「お客様」「トレーナー」と書く）。
7. アプリが付けた見出し・時刻・話者の行は内容として扱わない。

### 5-3 出力の形（AI_SCHEMA v2・additionalProperties:false・全部 required）
```
summary:       { flow: string[] }                     ★先頭（先に推論させる）
exercises[]:   { name, heard, note,
                 sets[]: { weight_kg: number|null, reps: integer|null, basis: "said"|"inferred",
                           evidence, unsure, note } }
condition[]    お客様の状態（医療でないもの）
caution[]      体の状態
coaching[]     指導の要点
hearing[]      生活・食事・睡眠・仕事・目標・運動歴
next_actions[] 次回やること（トレーナー向け）
member_message, member_todo[]   お客様に見える文（今どおり）
unclear[]:     { text, evidence }
```
- 構造化出力（`output_config.format`）と考える処理（thinking を省略＝adaptive）の併用は、今の設計39 が既に同じ形で送っている（effort だけ low→medium）。「形の順序で要約が先に作られるか」は §16 の未確認。

#### 5-3-2 上限（中5・切らない＝超えたら AI_BAD_OUTPUT か、画面で押せない）
| 項目 | AI が直接返せる上限 | 1件の字数 | 備考 |

| summary.flow | 12件 | 120字・合計1,000字 | 社内メモ2,000字に入る大きさに抑える |

| 状態（sourceStatus） | 条件（Worker が判定・AI の申告をそのまま信じない） | 画面 |
|---|---|---|
| `match` | 種目名がある・根拠と unsure と note に健康語が無い・`verifySet` が通る・`unsure` が空 | 数字を入れた行・印なし・初期値「採用」 |
| `inferred` | 根拠が伏せた文字起こしにそのまま在る（健康語なし）が、数字が根拠のトークンに無い／`basis==="inferred"`／`unsure` が空でない。重さ 0＜w≤500 の 0.1刻み・回数 1〜100 | 数字を欄に入れて「要確認」＋理由と根拠。確定か直すまで入らない |
| `nobasis` | 根拠が見つからない・数字が範囲外か null・**根拠か unsure に健康語**（高3） | 欄は空で「要確認：数字を確かめられません」。AI の読みは参考（D2）。打つまで入らない |
- 今の `unverified` は w・r を既に返している。**変わるのは「推論の値を、トレーナーの明示の確定で記録の下書きのセットに入れてよい」こと**。
- 顧客への誤った数字の守り：①含めてよい組み合わせを純粋データで判定（§7-4）②記録の画面に入った後も ✓ は全部外れたまま（I57）③D1 に入るのは「保存する」を押したときだけ。セットの数字は会員のカルテ（`MEMBER_KARTE`・いまは off）と「お客様の見え方」に出る＝**要確認のまま保存される経路を作らない**。

### 5-5 全自由文の表（高3・中11）
Worker の validateDraft が、下の**全部の行**に同じ4つを当てる：①健康語（AI_HEALTH＝画面の MEMO_HEALTH と同じ式）②名前の印（敬称・回目・初回・体験＝PII_WEAK）③第三者の語（下）④再マスク。

| 自由文 | 健康語に当たったら | 名前の印・第三者の語に当たったら |
|---|---|---|
| summary.flow[i] | その文を消して caution へ | 文を残し `blocked:'person'`（画面で採用できない） |
| condition[i] | 同上 | 同上 |
| next_actions[i] | 同上 | 同上 |
| unclear[i].text・.evidence | text を caution へ・evidence は空に | 同上 |
| exercises[i].note | 「種目名：」を付けて caution へ | 同上 |
| sets[j].note | 同上・セットは残す（状態は変えない） | note に `blocked:'person'` |
| **sets[j].unsure** | 同上・**そのセットを nobasis へ倒す** | unsure を「（理由は表示できません）」に・セットは inferred 以上にしない |
| sets[j].evidence | 同上・nobasis へ（今どおり） | 根拠は伏せた文字起こしの切り出し＝再マスクのみ |
| coaching[i]・hearing[i] | caution へ（今どおり） | `blocked:'person'` |
| member_message・member_todo[i] | caution へ（今どおり） | `blocked:'person'`（お客様に見える＝採用不可） |
| caution[i] | — | 再マスクのみ（入れる操作が無い） |
- **第三者の語**（`AI_THIRD`）：`〔人〕`（伏せた名前）・夫・妻・旦那・奥さん・嫁・息子・娘・子ども・父・母・兄・弟・姉・妹・彼氏・彼女・友達・友人・上司・同僚・部下・先輩・後輩・義。**伏せすぎる向きに倒す**（「母趾」等で当たっても採用できないだけ・表示はされる・トレーナーが自分で書ける）。一覧は画面と同じ式を検査で一致させる。
- 健康語の境界（D3 の推奨のまま）：AI に「医療でない状態は condition」と指示しても、**健康語の式に当たれば caution に倒す**（筋肉痛は「痛」で caution）。
- 画面も `blocked` の行・健康語の行は採用できない（Worker と画面の二重。画面は MEMO_HEALTH・MEMO_PII_WEAK・AI_THIRD で同じ判定）。

### 5-6 呼び出し・記録（高4・中6）

#### 5-6-1 呼び出し
- v2：`effort:'medium'`・`max_tokens:16000`・`stream:true`。v1：今どおり（effort low・8000・非ストリーミング・60秒）。
- **Worker の締切 90秒**（AbortController。Anthropic への接続の開始から）。超えたら 504 `AI_TIMEOUT`（途中の出力は捨てる）。画面の締切は 110秒（§6-4）。
- 再試行しない（今どおり）。1回押す＝1日の回数1。

#### 5-6-2 SSE の読み方（中6）
- `res.body` を `getReader()` で読み、`TextDecoder('utf-8', { fatal: true })` を **`decode(chunk, { stream: true })`** で使い、最後に `decode()` で閉じる（マルチバイトの途中で切れても壊さない・壊れたバイトは AI_BAD_OUTPUT）。
- 上限：累積 **512KB**・イベント **20,000件**・1イベント **64KB**。超えたら読み取りを止めて（reader.cancel）AI_BAD_OUTPUT。
- 順序の状態機械：`message_start`（1回だけ）→ `content_block_start`（index ごとに1回）→ `content_block_delta`（開いている index だけ）→ `content_block_stop` → `message_delta`（stop_reason・usage）→ `message_stop`（1回だけ）。`ping` はどこでも無視。**重複した start・閉じた index への delta・開いていない index・message_stop の後のデータ・未知のイベント型**は AI_BAD_OUTPUT。`error` イベントは AI_HTTP（detail は error.type の許可リストの語だけ・本文は出さない）。
- text の差分（`text_delta`）だけを変数に足す。thinking の差分は捨てる。`message_stop` が来ずにストリームが終わったら AI_BAD_OUTPUT（`detail:'NO_STOP'`）。stop_reason が refusal／max_tokens は今と同じコード。
- **生のイベント・差分・途中の文字列を console・D1・KV・応答・エラー文に出さない**（今の I76-3 と同じ。検査で console と応答と D1 の全行に身代わりの合言葉が出ないことを確かめる）。

#### 5-6-3 記録（高4：言い方を正す）
- 記録（`karte_ai_log`・access_log）は**終了処理まで届いた呼び出し**について残る（成功・失敗とも）。Worker が強制終了された（基盤の時間・CPU の上限・デプロイ等）ときは終了処理が走らず**残らない**。
- 残らなかった数は数えられる：**1日の回数（`karte_ai_usage.n`）− その日の karte_ai_log のうち回数を数えた後の行（result が ok・timeout・http_error・refused・truncated・bad_output・error）**＝「終了処理まで届かなかった回数」。日次点検（karte-ai-health）に `lost` として出し、1以上で warn。
- 列を足す（migration 0033・ALTER ADD COLUMN だけ・既定値なし・以前の行は NULL）：`fmt`（実際に使った形式 'v1'/'v2'）・`client_req_id`（画面が作る乱数の番号・中身なし・36字まで・形が違えば NULL）・`n_inferred`・`n_nobasis`・`n_unclear`・`n_summary`・`n_blocked`・`stream_events`・`stream_bytes`。`result` の値は増やさない（CHECK を作り直さない＝0018 の教訓）。`AI_BUILD` を更新。
- 画面は要求に `clientReqId`（今の KEYS に既にある鍵）を付け、失敗の1行に番号の末尾4字を出す（記録と突き合わせられる・オーナーが CEO に伝えれば探せる）。
- 記録が書けない（D1 の失敗）は今どおり応答を変えない（console は固定の文）。

### 5-7 入力の長さ・見出し
- 上限は今のまま：本文 128KB・`AI_TEXT_MAX` 3万字。日本語の会話は1分あたりおおよそ 150〜300字（トレーニング中は無言の時間がある）→ **60分で 9,000〜18,000字の見込み**（未実測）。`karte_ai_log.chars_in` と添付の「N字を入れました」で実測してから広げるか決める。広げるなら 4.5万字・本文 192KB を1つの変更で（index.js と画面の上限を同時に・検査で一致を固定）。
- **見出し行（低12）**：自動では消さない。`attClean` に「行全体の完全一致」の許可リスト `ATT_HEADER_LINES` を置き、**最初は空**。実物の書き出しの見出しの文言を確かめてから足す（見出しは個人情報ではないのでコードに書ける）。それまでは欄に残り、AI には「アプリが付けた見出しは内容として扱わない」と指示（害は無い）。

### 7-2 I71 をどう守るか（中9）
1. 応答は端末のメモリ（この関数の変数）にだけ置く。localStorage・sessionStorage・console に入れない（I63）。画面を離れる・文字を変える・別の顧客＝捨てる。
2. **最後のボタンの定義：「画面に並んだ採用中の全項目を一括で承認する明示の操作」**。ボタンの直上に区分ごとの採用件数（セット・種目のメモ・社内メモ・要約の有無・次回やること・お客様に見える件数）を出し、押す前に何が入るかが見える。開いただけでは何も入らない。下書き（localStorage）に書くのはこのボタンの1回だけ（既存の `commit()`）。
3. 初期値で「採用」になるのは：match のセット・一覧と完全一致の種目・健康語と名前の印と第三者の語の無い種目のメモ／指導／ヒアリング／状態／次回やること（どれもお客様に見えない）だけ。**要約・要確認・お客様に見える欄・種目名が一覧に無い種目・要確認の点は初期値で入らない**。
4. 体の状態（caution）は入れる操作が存在しない。`blocked` の行・健康語の行も採用の操作が無い。
5. 判定は §7-4 の純粋データだけで行い、DOM の状態を読まない。

### 7-4 確認の状態（純粋データ・高2）
```
rv = {
  v: 2, gen,                                  // 応答の世代（画面の照合）
  summary: { lines:[...], include:false },
  exercises: [{ id, nameStatus:'known'|'unresolved'|'named'|'excluded', name, heard,
                note: { text, blocked, include },
                sets: [{ id, sourceStatus:'match'|'inferred'|'nobasis',   // ★Worker の判定・画面で変えない
                         resolution:'unresolved'|'confirmed'|'edited'|'excluded',
                         aiW, aiR,          // AI の値（参考・変えない）
                         w, r,              // いまの欄の値
                         evidence, unsure, note:{ text, blocked, include } }] }],
  condition/next/unclear/coaching/hearing: [{ text, blocked, include }],
  member: { message:{ text, blocked, include:false }, todo:[{ text, blocked, include:false }] },
  caution: [ text ]                           // 表示だけ
}
```
- **sourceStatus は応答から一度だけ作り、以後変えない。** トレーナーの操作は resolution・w・r・include だけを変える。
- 初期の resolution：match＝`confirmed`（採用）／inferred・nobasis＝`unresolved`。
- 操作：［確定］＝`confirmed`（inferred だけに出る。nobasis には出さない）／欄の値を変えた＝`edited`（変えた後の値が範囲内のときだけ。空・範囲外は `unresolved` に戻す）／［外す］＝`excluded`／match の［採用✓］を外す＝`excluded`、付け直す＝`confirmed`。
- **含めてよい組み合わせ（これ以外は出さない）**：

| sourceStatus | 含める resolution | 含めない |
|---|---|---|
| match | confirmed・edited | excluded（unresolved にはならない） |
| inferred | confirmed・edited | unresolved・excluded |
| nobasis | **edited だけ** | unresolved・confirmed（作れない）・excluded |
- さらに種目の `nameStatus` が `known` か `named` のときだけ、その種目のセットを含める。**種目名を選び直したら（named→unresolved・別の名前へ）、配下の全セットの resolution を unresolved に戻す**（match も含む＝別の種目の数字として承認させない）。
- `reviewOpen(rv)`：unresolved のセット数＋nameStatus unresolved の種目のうちセットのあるもの＝「要確認あと N 件」。0 でなければ最後のボタンは押せない。

### 7-5 next_plan を運ぶ線（中10）
