> 2026-10-09・CEO玄／関門①（実装の前）用
> ★**第1版は関門①で不合格。** 月次の処理を日次と取り違えており、そのまま実装すると
>   **全トレーナーに毎日LINEが飛ぶ**設計だった。第7節に差し戻しの内容を残す。
> ★ただし調査の副産物として、**いまそこにある危険**を1つ見つけて先に潰した（第8節）。

## 1. なぜ急ぐのか

```
GASのトリガーは20本が上限
いま常設が18本。余裕は2本
```
★**一回限りのトリガー（after）を作る余地が2本しかない。**
```
_lbWarmContract          契約を温める（登録のあと）
_lbSyncAfterRegister     登録のあとの同期
LB_CALSYNC.AFTER_HANDLER 書き込みのあと1秒後（カレンダー同期）
```
これらは**書き込みのたびに作られる**。同時に3件の書き込みが起きると、
3本目が作れず**黙って止まる**（＝二重書きの速い道が止まる）。

★いまのところ失敗の実績は0件（`LB_TRIGGER_FAIL` に記録する仕掛けがあり、
　日次点検の `trigger_create_fail` は出ていない）。**まだ起きていないが、余裕が無い。**

## 3. ★減らす（3本・18→15）／第2版

**同じ間隔・同じ時間帯のものだけを束ねる。時刻は動かさない。**
★**月次のものは、束ねたラッパーの中で日付で絞る**（第7節の誤りの直し）。

| | 束ねるもの | 新しいハンドラ | 中でどう呼ぶか |
|---|---|---|---|
| ① | `warmupCache` ＋ `pushToEdgeSlots`（10分） | `lbTick10m` | 毎回どちらも |
| ② | `refreshPaceBoard` ＋ `autoBookRecurringPatterns` | `lbDaily6`（毎日6時） | ペース表は毎日／**自動予約はJSTの25日だけ** |
| ③ | `lbNudgeDaily` ＋ `sendShiftReminders` | `lbDaily10`（毎日10時） | うながしは毎日（**必ず先**）／**シフト連絡はJSTの20日だけ** |

### ★月次を日付で絞る（これが無いと誤送信）
```
autoBookRecurringPatterns   毎月25日6時   固定枠の翌月自動予約
sendShiftReminders          毎月20日10時  トレーナーへシフト提出の連絡
```
`sendShiftReminders` には**送信済みの判定が無い**。毎日呼ぶと
**全トレーナーに毎日LINEが飛ぶ**。だから：
```
ラッパーの中で JST の日付を見て、その日だけ呼ぶ
★加えて「その月に送ったか」の印を足す（時間帯の再実行・手で呼んだときの二重送信を防ぐ）
```

### ★失敗を「try で囲む」だけでは検知できない
```
pushToEdgeSlots は**内部で例外を飲んでログにするだけ**。外側の catch に届かない
lbNudgeDaily はロックが取れないと送らずに終わる（ALREADY_RUNNING）
  ★しかも**翌日に再試行できない**（その日の分は永久に取りこぼす）
```
```
だから   子処理は**成功・失敗を戻り値で返す**形にする
         ラッパーが「開始・結果・所要時間」を**個別に**記録する
         ALREADY_RUNNING も「実行済み」ではなく**失敗**として数える
         日次点検が、新しいラッパーの最後の成功時刻を見る
```

### 実行時間は先に測る
```
②の autoBookRecurringPatterns は全パターンを走査し、予約を作り、
  顧客・トレーナー・オーナーへ通知する。**「軽い」は未確認**
→ 束ねる前に、各子処理の所要時間を1回測って記録する（6分の制限）
★別々の `atHour(6)` は6時台の別の時点に走りうるが、束ねると**必ず直列**になる
```

### 束ねないもの（理由）
```
15分 と 30分（pushToEdgeLight / pushToEdgeHome）
  → home の押し出しは42秒かかる。15分の処理に足すと重くなる
3時・4時・7時・8時・9時・12時   時刻が違う。動かすと「いつ届くか」が変わる
dailySync（6時間）・weeklyPaceReport（週1）・lbCalSyncTick（5分）
```

### ★既存のセットアップ関数を揃える（これを忘れると二重実行）
```
setupEdgeTrigger / setupLineTriggers / setupNudgeTrigger / setupRecurringTriggers
  は**旧ハンドラしか知らない**
→ 新ラッパー導入後にこれらを実行すると**旧トリガーが復活**し、
  うながし・シフト連絡・自動予約が**二重に実行される**
→ 新構成に揃えるか、実行を拒否する
```

### ★日次点検の必須一覧も変える
```
いまの一覧は旧名（lbNudgeDaily 等）。新ラッパーにすると
正常でも `trigger_missing` が出る
```

## 4. 入れ替えの手順（★ペア単位・オーナーの操作が1回）

一括で消して一括で作ってはいけない。**途中で作成が失敗すると旧トリガーだけ失う。**

```
1. コードを反映する（私）
2. ★オーナーがGASエディタで `lbSetupTriggers()` を1回実行する
     ① 実行前の全トリガーを記録する（ハンドラ名・種別・周期）
     ② 対象のペアだけを削除する
     ③ 対応するラッパー1本を作る
     ④ 作れたことを確かめる
     ⑤ 次のペアへ
     ⑥ 最後に期待する集合・重複・総数を照合して出す
     ★作成に失敗したら、そのペアの旧トリガーを**復元する**
3. 日次点検で本数が15本になったこと／必須の一覧が揃っていることを確かめる（私）
```

## 6. これで足りるか

```
18 → 15本。余裕5本
```
★**「足りる」とは言えない。** 一回限りのトリガーは削除→作成にロックが無く、
　同種の要求が競合すると複数本作られうる（Codex関門①の指摘⑨）。
　15本は**安全の保証ではなく、暫定的な余裕**。

### 本数の正確な言い方
```
コードから期待される常設ハンドラ   18種類
本番の点検が数えた総トリガー数     18本
★本番18本の内訳は未確認（点検は getProjectTriggers().length を数えるだけで、
  一回限りのものも重複も含む）
lbCalSyncTick は5分（確認済み）
```
★ただし**恒久的な解決ではない**。新しい定期処理を足すたびに減る。
　次に上限が近づいたら、15分/30分の統合か、GASを外す判断になる。

## 7. ★関門①で不合格（2026-10-09・指摘9件・却下0）

### 私の重大な誤り
```
autoBookRecurringPatterns   毎月**25日**6時（固定枠の翌月自動予約）
sendShiftReminders          毎月**20日**10時（トレーナーへシフト提出の連絡）
```
私は `atHour` だけを見て **`onMonthDay` を見ていなかった**。
第3節のとおり束ねて毎日呼ぶと：
```
sendShiftReminders に送信済みの判定が無い
→ ★全トレーナーに**毎日**LINEが飛ぶ
```
**顧客（トレーナー）に誤送信を起こす設計だった。** 関門①で止まって良かった。

★原因は今日すでに学んだ形の変形：**出力の一部だけを見て判断した**
　（`grep -oE "atHour\([0-9]+\)"` で `onMonthDay` が視野に入らなかった）。

### ほかの指摘
```
② 「try で囲む」では失敗を検知できない
   pushToEdgeSlots は**内部で例外を飲んでログにするだけ**。外側の catch に届かない
   → 子処理が成功・失敗を**戻り値で返す**形にし、ラッパーが記録する
③ 「②③も軽い」は未確認（autoBookRecurringPatterns は全走査＋通知まで送る）
④ lbNudgeDaily はロックが取れないと送らずに終わる。しかも**翌日に再試行できない**
   → ALREADY_RUNNING も「実行済み」ではなく失敗として記録する
⑤ 既存のセットアップ関数が新ラッパーと共存できない
   setupEdgeTrigger / setupLineTriggers / setupNudgeTrigger / setupRecurringTriggers は
   旧ハンドラしか知らない。新ラッパー導入後に実行すると**旧トリガーが復活**
   ＝本数が増えるだけでなく、うながし・シフト連絡・自動予約が**二重に実行**される
⑥ ★★setupTriggers() は名前で絞らず全部消す（第8節で先に潰した）
⑦ 入れ替えは一括でなく**ペア単位**で（途中で作成が失敗すると旧トリガーだけ失う）
⑧ 本数の表現：「コードから期待される常設ハンドラは18種類。本番の総数も18本。
   ただし**本番18本の内訳は未確認**」と書くべき。
   LB_CALSYNC.TICK_HANDLER は `lbCalSyncTick`・**5分**
   ★導入後は日次点検の必須一覧を新ラッパー名に変えないと `trigger_missing` が出る
⑨ 一回限りのトリガーの同時本数は3本に限定できない
   （削除→作成の全体にロックが無いので、同種が競合して複数本作られうる）
   → 「余裕5本なら足りる」とは**保証できない**
```

### 第2版で直すこと（まだ実装していない）

## 8. ★先に潰した危険（調査の副産物・2026-10-09 に実装）

```
setupTriggers()（gas/コード.js）
  作られた当時トリガーは3本だった。いまは18本ある
  getProjectTriggers() を**名前で絞らずに全部消し、3本しか戻さない**
  → 押し出し・作業依頼・カレンダー同期・うながし・固定枠の自動予約・
    シフト連絡・日次点検・完全同期が**丸ごと止まる**
  ＝顧客の残数が固まり、リマインドが届かず、予約が自動で作られない

★そして日次点検が「setupTriggers を実行し直すと戻ります」と**案内していた**
★さらに**検査がその案内を守っていた**（entry-customer-id.test.js ⑥-b）
  検査は正しいものを守らなければ、**間違いを固定する道具になる**
```

### 直したこと
```
setupTriggers()        実行を拒否する（throw）。用途ごとの関数を名指しで案内
setupBasicTriggersOnly() 昔の3本だけを名前で絞って入れ直す（他には触らない）
日次点検の案内         「実行しないでください」＋用途ごとの関数を名指し
検査                   trigger-safety.test.js（12本）で固定。
                       entry-customer-id.test.js ⑥-b を「危険な案内をしていない」に反転
```
