## 1. いま何が起きているか（事実）

```
顧客の画面に出る残数   GASが計算して押し出した「写し」（member_home）を読んでいる
D1の枠と引当           作ってあり、計算と40名全員一致（5回連続）
二重書き               稼働中。予約が動けば追従する（10/08 本番で実測）
```

**写しを読んでいる**ので、次の手当てが必要になっている。

```
15分の遅れ     押し出しは15分ごと（＋書き込み直後に1回）
35分の猶予     書き込みの直後は、画面がWorkerではなくGASへ直接聞く
鮮度の判定     computed_at が古ければ答えない（readHome）
```

## 2. 3-bで変えること（1行）

```
いま   残数 ＝ member_home（GASが計算した写し）を読む
あと   残数 ＝ monthly_quota と ticket_packs の行から**その場で引き算する**
```

**「古いかも」という概念が消える。** 枠と引当は二重書きで即時に更新されるので、
押し出しを待つ必要がなくなる。

## 4. 設計の芯：切り替えを「会員ごと」にできる形にする

一斉に切り替えない。**1人から始めて、おかしければその人だけ戻す。**

```
LB_D1_REMAIN_MODE   'off'（既定）／'shadow'／'on'
  off     いまのまま（写しを読む）
  shadow  D1からも読んで**両方を比べ、食い違いを記録する。顧客に出すのは写しのまま**
  on      D1から読んだ値を顧客に出す

LB_D1_REMAIN_ALLOW  'on' のときに、D1から読む会員のIDを並べる（空＝全員）
```

★`shadow` を必ず通す。**顧客に出す前に、本番の実データで食い違いを数える。**
　照合（quotaBuild verify）は私が回すときだけ。shadow は**顧客が画面を開くたびに**比べる。

## 5. どこを変えるか

```
読む場所   worker/src/routes/boot.js の readHome（member_home を読む）
足すもの   同じ形の答えを monthly_quota / ticket_packs / reservation_allocations から作る関数
```

### 作る関数（Worker側）
```
readRemainFromD1(env, customerId, targetMs)
  → member_home と**同じ形**（type / quota / thisMonth / carryover / remaining /
    ticketRemaining / monthlyRemaining / … ）を返す
```

★**同じ形で返す**のが要点。呼ぶ側を変えずに差し替えられる＝戻すのも一瞬。

### 計算の規則（既に決まっているものを使う）
```
月額の残   coverage が 'limited' なら quota − used ／ 'uncovered' なら 0 ／
           月額の契約が無ければ null
チケット   有効なパックの（total − opening_used − used）の合計
```
**これは照合（quota-verify）が既に使っている式**。新しい計算を持ち込まない。

## 6. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | D1の行が古いまま顧客に出る | 二重書きで即時更新。**それでも遅れたら？**→ 第7節 |
| ② | 月の境目（25日以降は翌月が開く） | `member_home` は当月と翌月を持つ。D1も同じ2か月を返す |
| ③ | 超過（支払い待ち）の見せ方が変わる | 照合と同じ式を使うので変わらない（残は0で止まる） |
| ④ | 計算が「要確認」の会員 | D1には枠が作られていない。**答えずに写しへ落とす**（fail-safe） |
| ⑤ | 検証用の会員が混ざる | 一覧には出るが、計算は契約どおり。影響なし |
| ⑥ | 新しく入った会員 | 契約の押し出し→枠の作成の前は枠が無い。④と同じく写しへ落とす |
| ⑦ | 切り替えたあと戻せない | モードと会員の指定で戻せる。**既定は off** |

## 7. ★それでもD1が遅れたらどうするか（いちばん大事な論点）

二重書きは「速い道（1秒後）」と「心拍（15分）」で動く。**速い道が止まれば15分遅れる。**
いまは誰も読んでいないので無害だが、3-b後は**顧客に古い残数を見せる。**

```
案A  D1の行に「いつ時点か」を持たせ、古ければ答えない（写しへ落とす）
案B  予約の確定直後だけ、その会員はGASへ直接聞く（いまの35分の猶予と同じ考え）
案C  二重書きを同期呼び出しに戻す（確定が遅くなる）
```

**推奨はA＋B。**
- A：`monthly_quota.updated_at` と `reservation_allocations` の最新時刻を見て、
  **その会員の予約の最終更新より古ければ答えない。** 比べる相手は「全体の同期時刻」ではなく
  **その会員の予約の最終更新時刻**（これは `reservations` の写しにある）。
- B：確定直後の短い窓だけGASへ落とす（既にある仕組みを流用）。

★Cは採らない。軽量化で 5,836ms → 1,703ms まで削った経路を戻すことになる。

## 8. 実装の順序

```
1. readRemainFromD1 を作る（純粋に近い形・Nodeでテストできるように）
2. モードの読み取りと切り替え（off / shadow / on・会員の指定）
3. shadow：両方を読んで食い違いを記録する窓口（私が作業依頼で数える）
4. 鮮度の判定（第7節A）
5. 作ったデータでの検証（既存の25場面を流用し、同じ答えになることを見る）
6. shadow を本番でON（顧客に出るものは変わらない）← ここまでオーナー承認不要
7. 食い違い0が続いたら、1人だけ 'on'（★オーナー承認）
8. 全員 'on'（★オーナー承認・関門③）
```

**6までは顧客に影響しない。** 7で初めて顧客が見る数字の出どころが変わる。

## 9. 3-bが済むと何が消えるか

```
15分の遅れ     消える（枠と引当は即時）
35分の猶予     消える（自分が取った枠が「まだ空いている」ことが起きない）
鮮度の判定     残す（第7節Aとして、より厳しい形で）
写しの押し出し 残る（予約一覧・空き枠・氏名などは引き続き写しを使う）
```

★**残数だけを先にD1へ移す。** 予約一覧や空き枠まで一度に移さない。
　1つずつ移して、各段で戻せる状態を保つ。

# ★関門①で前提が崩れた（2026-10-09・Codex指摘）

上の設計は「残数だけ差し替えれば済む」という前提で書いた。**成立しない。** 3つ崩れた。

## ① 「同じ形で返す」は3表だけでは作れない

`member_home` の中身は残数だけではなく、**表示の補助**が混ざっている。
D1の3表（枠・チケット・引当）から作れないものがある。

| 作れないもの | なぜ | いまの出どころ |
|---|---|---|
| `carryover`（繰越） | `quota` は「頻度＋繰越」。**頻度が3表に無い**ので分解できない | 計算 |
| `thisMonth`（今月の予約件数） | 引当の件数とは一致しない（超過・振替は引当を作らない） | 台帳 |
| `overageCount`（支払い待ち） | 未割当の予約は**引当の行が作られない**＝3表に現れない | 割当の結果 |
| `displayRemaining` / `paymentRequired` | 上に依存 | 同 |
| `reviewRequired` | 「要確認」の理由が3表に無い | 計算 |

★`overageCount` が作れないのは重い。**0として扱うと、支払いが必要な方に「残り0回」だけが出る**（マイナスと支払いの案内が消える）。

### 直し方（枠の行に2つ足す）
```
monthly_quota.base_freq   その月の頻度   → carryover = quota − base_freq
monthly_quota.overage     その月の未割当件数（割当の結果から分かる）
```
どちらも**枠を作るときに既に手元にある**（`buildQuotaForCustomer` が `res.freq` を、
`buildAllocationsForCustomer` が `skippedUnallocated` を持っている）。
`thisMonth` は予約の写し（`reservations`）から数える。二重書きが会員ごとに更新している。

## ② 鮮度の判定（案A）が成り立たない

比べる相手にできる時刻が、いまのD1に無い。

```
monthly_quota.updated_at   ★取消のトリガーで**過去に戻る**
                           （削除した引当の古い decided_at を書き戻す・0009:109）
reservations.synced_at     内容が変わった時刻ではない。差分同期は変わっていない行を書かない
                           → 「変わっていないので古い」と「同期が止まって古い」を区別できない
line_reservations col11    予約を**作った**時刻。取消・変更では動かない
reservation_allocations.decided_at  D1側で作り直した時刻＝比べたい対象そのもの
```

### 直し方（会員ごとの世代を持つ）
```
customer_sync_version
  customer_id
  source_version     GASが書き込みのたびに1つ増やす
  built_version      枠と引当を作り直したときに、同じ値を書く
```
**顧客に答えるのは source_version === built_version のときだけ。**

★`source_version` をD1へ送る費用は増えない。`edgeAfterWrite` は既に
その会員の予約の写しを同期で押している（`_edgePushReservationsFor`）。そこに相乗りする。

★それでも守れない範囲がある（正直に）：
　押し出しそのものが止まれば `source_version` すら届かない。
　そのときD1は「自分が古いこと」を知れない。
　→ 元栓（EDGE_PUSH_ON）と押し出しの鮮度を**別に**見る必要がある（決定0075の②で入れた）。

## ③ `/boot` は答えられなくてもGASへ落ちない

`readHome` が null でも、`routeBoot` は `home: null` を含む**成功**を返し、
`_fallback` を立てない（boot.js:106）。
「null ならGASへ聞き直す」が成立するのは compat 経路だけ（compat.js:94 → index.js:241 → LIFF）。

→ **boot でも落ちるようにする。** `homeFallback: true` を載せ、画面は残数だけGASへ聞き直す。
　★「要確認」で写しも無い会員は、**0回と見せない。**
　　「残数を確認できません。担当へご連絡ください」にして予約の操作を閉じる。

## ④ 混在期間に矛盾が見える（5通り）

| 状態 | 顧客に見えること |
|---|---|
| D1の残数が新・予約一覧が古い | 残数は減ったのに、新しい予約が一覧に無い |
| D1の残数が新・空き枠が古い | 残数は減ったのに、取った枠がまだ空いて見える |
| D1の残数が古・一覧が新しい | 予約は一覧にあるのに残数が減っていない |
| D1の残数が古・取消が新しい | 予約は消えたのに残数が戻らない |
| D1の残数が新・取消前の一覧 | 予約が一覧に残っているのに残数だけ戻る |

→ **残数と予約一覧の世代が一致しないときは、両方を写し（GAS）へ落とす。**
　 片方だけ新しい表示をしない。boot の答えに `remainSource`（copy / d1 / fallback）を載せる。

## ⑤ その他（式に書き漏らしていた）
```
coverage='unlimited'   いまは作られないが、以前作った行が残りうる
                       「月額契約が無い（null）」と混同しない規則が要る
期限の境界             ホームの「いまの残数」と「予約する日の残数」で有効なチケットが違う
                       Date.now() と targetMs を使い分ける
確定直後の猶予（案B）  ブラウザ側の印なので、**同じ端末しか守らない**
                       トレーナー操作・別端末・カレンダー取込では窓を張れない
```

# 直した実装の順序

```
0. 枠の行に base_freq と overage を足す（migration・作るときに手元にある値）
1. 会員ごとの世代（customer_sync_version）を足す
   GASの書き込み → source_version++／作り直し → built_version
   ★押し出しに相乗りするので費用は増えない
2. readRemainFromD1：残数と、0で足した2つから carryover / overage を作る
   thisMonth は予約の写しから数える
3. boot で答えられないときにGASへ落ちる形にする（homeFallback）
4. 世代が一致しないときは両方を写しへ落とす
5. shadow（両方を読んで食い違いを数える。顧客に出すのは写しのまま）
6. 作ったデータでの検証（既存の25場面で同じ答えになることを見る）
7. shadow を本番でON ← ここまで顧客に影響しない
8. 1人だけ on（★承認）→ 全員 on（★承認・関門③）
```

**0〜1が増えた。** ここを飛ばすと「同じ形」も「鮮度」も作れない。
