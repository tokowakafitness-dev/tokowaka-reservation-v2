# 頻度0は「上限なし」ではなく「月0回」

> 2026-10-08・オーナー承認済み
> 関門①（実装の前）用

---

## 1. オーナーの判断（根拠になった事実）

> おそらくこの会員は、9月まで月2回の契約であり、10月は9月のうち残数1回を引き継いで
> 実施するが、10月自体の契約はまだ未定のため、取り急ぎ契約期間中としての扱いになる様に
> 頻度0で月額のチケット付与がない形で契約している。なので推奨でいい。

**＝ 頻度0は「その月の付与が0回」という意思表示。** 上限なしではない。

### 実データ（会員#4537）
```
9月まで   種別=通常 / 月額 / 頻度2 / 期間 2026/07/05〜2026/09/30
10月      種別=通常 / 月額 / 頻度0 / 期間 2026/10/01〜2026/10/31 / 繰越上限2
                            ↑ 空欄ではなく、はっきり 0
10月の枠  繰越ぶんの1回だけ。10/10に1件予約済み＝使い切り
```

---

## 2. いま何が起きているか（直す理由）

```
会員の画面      予約できる残り = 0       （monthlyRem が null → 0 として足している）
実際の予約      ★何回でも通る            （degradedUnlimited で canBook を無条件に true）
```

**表示と実際が逆向きにずれている。** 繰越を使い切ったあとも予約が通る。
売上の取りこぼしであり、顧客にも「残0なのに取れる」という矛盾を見せている。

`gas/Allocate.js`:
```js
var degradedUnlimited = ent.hasMonthly && (covFreq === 0);        // 664
if (degradedUnlimited && wantKind !== 'pair') { canBook = true; } // 698 ★枠を見ない
```

---

## 3. 変える規則（3行）

```
いま   契約が覆わない              → 残数 0
       覆って頻度>0                → 残数 枠 − 使った数
       覆って頻度0                 → 残数 null（上限なし）／予約は無条件に可

これから 契約が覆わない            → 残数 0                      （変えない）
         覆っている（頻度0を含む）  → 残数 枠 − 使った数
                                      枠＝頻度＋繰越。頻度0なら繰越ぶんだけ
         予約可否                   → 通常の判定（枠に入るかどうか）に一本化
```

`degradedUnlimited` という概念を**無くす**。

---

## 4. ★`null` の意味が1つに戻る（ここが要点）

いま `monthlyRem === null` は**2つの意味**を兼ねている。

```
① 月額契約が無い（チケットのみの会員）
② 頻度0＝上限なし扱い
```

これに依存している箇所が複数ある（`!!sp.hasMonthly` と組み合わせて見分けている）：
```
gas/LineBooking.js:697   hasNormalRoute = (monthlyRem == null) ? !!hasMonthly : (monthlyRem > 0)
gas/LineBooking.js:3636  monthlyRoute   = 同じ形
gas/LineBooking.js:3704  monthlyRoute   = 同じ形
gas/LineBooking.js:680   _tot           = (monthlyRem == null ? 0 : …) + ticketRem
gas/LineBooking.js:7236  リマインド・変更の比較で null を -1 として扱う
```

**②が消えると、null は①だけの意味に戻る。**
上の `(monthlyRem == null) ? !!hasMonthly : …` は、①のとき `hasMonthly` が false なので
**そのまま正しく働く。書き換えなくてよい。**

ただし `gas/LineBooking.js:3665` の早期return（`if (b.degradedUnlimited) return {remaining:null,…}`）は
**到達しなくなる**ので消す。残すと「無くした概念の分岐」が残り、読む人を誤らせる。

---

## 5. 空欄（未入力）はどうするか

いまの読み取りは**空欄と0を同じ0に潰している**。
```js
var freq = cc.freq >= 0 ? Number(r[cc.freq] || 0) : 0;
```

オーナーの承認は「頻度0＝月0回」について。**空欄は別の話**（意思表示ではなく入力漏れ）。

```
扱い   空欄も 0 として計算する（＝繰越ぶんだけ。上限なしにはしない）
       そのうえで**台帳の検査で指摘する**（_contractOddities に既にある）
```

**予約を止めない。** 空欄が事故で入ったとき、予約を拒むと正当な会員が取れなくなる。
0として扱えば枠は繰越ぶんだけになり、無制限にはならない（穴は閉じる）。
入力漏れは検査で見えるので、直せる。

★検査の文面は直す。いま「上限なしとして扱われ、消化の記録も残りません」と書いてあるが、
この変更後は「繰越ぶんだけになります」が正しい。

---

## 6. D1側（同時に直る）

`coverage` の3状態のうち `unlimited` が**使われなくなる**。
```
uncovered  契約が覆っていない      → 見せる残数 0
limited    覆っている              → 見せる残数 quota − used
unlimited  （もう作られない）
```

**列の定義は残す**（既に本番D1に入っている行があるため・値としては出なくなる）。
照合は3状態すべてを扱えるままにしておく＝古い行があっても壊れない。

これで**D1移行のブロッカーが消える**：
「GASは予約を許すのに引当がどこにも作られない」という分裂が無くなる。

## 7. この会員に起きる変化（唯一の該当者）

```
いま      画面の残り 0 ／ 予約は何回でも通る
これから  画面の残り 0 ／ 予約は通らない（枠1・使用1）
```
**画面の表示は変わらない。予約が止まるだけ。** すでに繰越1回を使い切っているため。

★もし今日このあと予約が入ると、いまの実装では通ってしまう。
**この変更を入れるまでの間だけ、その穴が開いている。**

## 8. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 他に頻度0の月額契約を持つ会員がいたら、その人の予約が止まる | **該当は1名のみ**（D1の覆い方の内訳で確認済み：unlimited 1行）。実装後に dry 実行で再確認する |
| ② | 空欄の行があると、繰越ぶんだけになって予約が止まりうる | 実装後に dry 実行で確認。あれば報告してから本番へ |
| ③ | `null` を「上限なし」と読む箇所の取り残し | 第4節で洗い出した5箇所はそのまま正しく働く。3665行だけ消す |
| ④ | ペアの扱い | いまも `degradedUnlimited` はペアを対象外にしている。概念が消えるので区別も消える（通常の判定に一本化） |
| ⑤ | GASとWorkerの写しがずれる | `allocate-drift.test.js` が1文字単位で照合する。両方に同じ変更を入れる |
| ⑥ | 既存の golden テスト | 頻度0を使っているテストがあれば期待値が変わる。変える前に必ず確認する |

## 9. 実装の順序

```
1. gas/Allocate.js と worker/src/allocate.js に同じ変更（drift testが照合）
   ・monthlyRem の分岐を2つに
   ・coverage を uncovered / limited の2つに
   ・degradedUnlimited を廃止
2. gas/LineBooking.js:3665 の早期returnを消す
3. _contractOddities の文面を直す（空欄＝繰越ぶんだけになる）
4. テストを直す／足す（頻度0・空欄・繰越だけの月・ペア）
5. Worker を push（自動デプロイ）→ dry 実行で該当者と空欄行を確認
6. 問題なければ GAS 反映（オーナー承認）＝ここで顧客に効く
```

**5までは顧客に影響しない**（Worker側は枠と引当を作るだけ・誰も読まない）。
**6で初めて予約可否が変わる**＝関門③を通す。
