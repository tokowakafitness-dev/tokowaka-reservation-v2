## 3. 顧客への影響を消す3つの手当て

### ① LINEの通知を飛ばさない
`custInfo.suppressNotify = true`（固定枠の自動予約が既に使っている仕組み）。
**実在の会員に「予約しました」が届いては困る。**

### ② 請求に乗せない
カレンダーの予定名に `[TEST] ` を付ける。billing は `[RESERVED]`／`[消化]` が
先頭でないものを集計から外すので、`[TEST]` 付きは素通りする。

**ただし、いまこの印は staging のときだけ付く**（`_lbIsStaging()` は
`STAGING_SPREADSHEET_ID` が設定されているときだけ真。本番では設定しない）。

→ **検証の実行中だけ印を付けられるようにする。**
```
検証の関数が最初に  Script Properties の LB_VERIFY_RUN を '1' にする
予約の作成が        _lbIsStaging() || LB_VERIFY_RUN === '1' のとき [TEST] を付ける
検証の関数が最後に  LB_VERIFY_RUN を消す（finally で必ず消す）
```
★ここだけ**予約の作成経路に手を入れる**。印を付けるだけで、可否や残数には触らない。

### ③ 終わったら必ず取り消す
作ったものを覚えておき、最後に逆順で消す。
```
消せなかったものは   一覧で出す（「何が残ったか」が分からないまま終わらせない）
途中で落ちても       finally で取消を試みる
```

## 4. 会員をどうするか（★オーナーの判断が要る）

C1・C2・C3・C6 は会員が必要。2つの道がある。

| | 道 | 良い点 | 悪い点 |
|---|---|---|---|
| **A** | **検証用の会員を1行作る**（名簿＋契約に1行） | 実在の方に一切触れない | 全会員の一覧・照合に1名増える（39→40名） |
| B | 実在の会員を使い、終わったら取り消す | 増えない | その方の残数が一時的に動く。通知を止め損なうと届く |

**私の推奨はA。** 理由：
1. **実在の方の残数を動かさない。** 取り消しが失敗したら、その方の残数が狂ったまま残る
2. 通知の止め忘れが致命的にならない（検証用の会員はLINE未連携にできる）
3. 次回以降の検証も同じ会員で足りる（毎回の準備が不要になる）

**Aの悪い点（1名増える）への手当て**：氏名を `検証用（予約しないでください）` にし、
一覧では分かるようにする。照合の対象にも入るが、契約どおりに計算されるので一致する。

## 5. 通す順序（依存があるので固定する）

```
1. C5 ブロック枠          10/21 07:00-08:00  会員不要・いちばん単純
2. C4 未登録客の枠確保    10/21 09:00-10:00  会員不要
3. C1 代行予約            10/21 11:00-12:00  検証用の会員
4. C2 まとめて予約        10/21 13:00・15:00 検証用の会員（2件）
5. C3 振替予約            10/21 17:00-18:00  ★振替権が必要（下記）
6. C6 後付けの紐付け      10/21 19:00-20:00  ★未紐付けの行が必要（下記）
```

### C3（振替）の下準備
振替権は「当日取消」で付く。検証用の会員で1件作って当日取消すると権利が付くが、
**当日取消は残数を消化したまま残す**ので、検証用の会員の枠を1つ消費する。
→ 枠を多めに持たせた契約にする（例：頻度8）。

### C6（後付けの紐付け）の下準備
未紐付けの行は「カレンダーに手入力して氏名が一致しなかった予約」。
→ 検証用の会員の氏名と**わざと違う名前**でカレンダーに1件作り、取込を走らせる。
   取込は6時間ごとなので、検証の関数から直接呼ぶ（`dailySync`）。

## 6. 各入口で確かめること

通したあと、**その会員ぶんの照合**を走らせて一致を見る。

```
入口を通す → 待ち行列に積まれたか → 二重書きが処理したか → 照合が一致するか
```

C4・C5（会員が無い）は**引当を作らないのが正しい**（`consumes_quota = 0`）。
「引当が増えないこと」を確かめる。

## 7. 壊れうるところ（正直に）

| | 懸念 | 手当て |
|---|---|---|
| ① | 取消に失敗して10/21に予定が残る | 一覧で出す。オーナーが手で消せる形にする |
| ② | `LB_VERIFY_RUN` が消えないまま残る | finally で消す。残っても印が付くだけで害は小さい。日次点検で「残っている」と出す |
| ③ | 通知の止め忘れ | 検証用の会員をLINE未連携にする（Aを採る理由） |
| ④ | 検証用の会員が各種の一覧に出て紛らわしい | 氏名に「予約しないでください」と入れる |
| ⑤ | 検証中に本物の予約が入って競合する | 10/21は検証用（オーナー承認）。ただし念のため、開始時に10/21が空かを確かめてから進む |
| ⑥ | 6分の実行制限 | 6つ＋下準備＋照合は重い。**入口ごとに区切って何度でも再開できる**形にする |
