# ③ 予約の入り方に応じて休憩を自動で入れる（設計）

**目的**：同じトレーナーで3時間連続のセッションが成立した瞬間に、**その直後15分を休憩としてトレーナーのカレンダーに実際に確保する。**

**この段の性質**：**カレンダーに書く。**（①が読み取りのみ、②が顧客へ送る。③は初めて「予定を作る」段である）
書くのは **トレーナーのカレンダーに15分の休憩1件だけ**。予約・台帳・残数・請求には一切触らない。

> 起草：2026-10-02／状態：**設計のみ。コードは書いていない。**

---

## 0. 結論（先に読むところ）

| # | 論点 | 結論 |
|---|---|---|
| ① | いつ入れるか | **即時（予約確定の中で同期的に書く）＋ 毎日1回の掃除バッチ**の二本立て |
| ② | どこに入れるか | **トレーナーのカレンダーだけ。B1には絶対に書かない。** タイトルは `休憩（自動）` |
| ③ | キャンセルで連続が崩れたら | **消す。** ただしキャンセル処理の中では消さず、掃除バッチと次の予約確定で収束させる |
| ④ | 自動と手動の区別 | **説明欄のマーカー**（`auto_break：consec180` 他）。既存の `channel：` の前例に乗る |
| ⑤ | トレーナーが消したいとき | **既存の `listAdminSlots` / `deleteAdminSlot` に乗る。ただし両関数の拡張が必要**（今はB1しか見ていない） |
| ⑥ | 顧客にどう見えるか | **既存の `SLOT_TAKEN`「この時間帯は選択されたトレーナーが対応できません。」そのまま。** 新しい文言は作らない |
| ⑦ | 段階導入 | `LB_AUTO_BREAK` を `（未設定）→ dry → on` の3段。既定は未設定＝何も書かない |

**オーナーの元の要望（「3セッション終了後の15分後からしか予約できない」）は、この設計で自動的に満たされる。**
休憩が `_lbIsBusyTitle` によって「埋まり」になるため、休憩の直後（＝連続終了＋15分）が次に予約できる最初の時刻になる。
**予約を断る制限（枠を落とす判定）を新しく作る必要はない。** 後述 §3-3。

## 1. なぜ「断る」ではなく「入れる」なのか（設計の土台）

オーナーの発言がこの設計の起点である。

> 休憩を入れる運用に関しては、トレーナーも予約の状況次第で休憩が必要になるかが決まるため、事前に入れられないのが問題です。
> 予約が入らなければ、その時間は休憩になるので。なので、予約の入り状況により自動で休憩を入れてあげる仕組みが必要ってこと。

この一文には**2つの要求**が入っている。両方を満たせるのは「入れる」方式だけである。

| 要求 | 「断る」方式（枠を落とす） | 「入れる」方式（休憩を書く） |
|---|---|---|
| 3時間連続の直後に休ませる | ○ | ○ |
| **トレーナー本人に休憩が見える** | **×**（システムの中だけで起きる。カレンダーには何も現れない） | ○（Googleカレンダーに予定として出る） |
| **他の予約経路からも塞がる** | **×**（サロンボード・手動作成・管理画面の枠作成は素通りする） | ○（カレンダーが正本なので全経路で効く） |
| 事前に休憩を置かずに済む | ○ | ○ |

**「入れる」を採る理由は、2段目と3段目である。**
この店の予約はカレンダーが正本で、`_lbReserveCore` を通らない作成経路が実在する
（`makeAdminBooking`＝未登録客の枠確保、`makeBlock`、サロンボード由来の手動予定）。
枠を落とす判定をLINE予約の確定経路にだけ置くと、**それ以外の経路から3時間連続が作られ、制限が黙って無効になる。**
カレンダーに休憩を書けば、空き枠生成（`buildAvailableSlots`）・LINE確定（`_lbCheckTrainerAvailable`）・
管理画面の枠作成（`_lbAdminSlotGuard` はB1だけ見るので効かない＝§6落とし穴8）に加えて、
**トレーナーが自分の目で見る**という最も強い経路が効く。

## 2. 実測が決めたこと（確認せず設計に織り込む）

過去30日の実測（`consecutiveSessionsText`・EdgeAudit.js）。

```
180分以上の連続       6件（うち240分以上 2件）
  同じ日に2回起きた日が1日ある（1日1回しか入れない作りは不可・§6落とし穴2）
「休憩」を含む予定     0件（3名とも。誰も使っていない）
180分制限で落ちる枠   7枠 / 378枠（1.9%）
120分制限なら        21枠 / 378枠（5.6%）
```

この数字から、確認を取らずに決めたことが4つある。

| 決めたこと | 根拠 |
|---|---|
| **しきい値は180分**（120分にしない） | 180分なら空き枠への影響1.9%。120分は5.6%＝約3倍。顧客が選べるトレーナーは実質2名しかいないため、2名しかいない状態で5.6%落とすのは売上に触る。1.9%は許容できる |
| **休憩は15分**（連続とみなす隙間と同じ） | オーナーの原文が「15分後から」。かつ **休憩の長さ＝隙間のしきい値** であることが「休憩が必ず収まる」不変条件を作る（§6落とし穴9） |
| **書き込みは非常に稀**（＝即時でも遅くならない） | 月6件。予約確定が月に数百件あるのに対し、書き込みが発生するのは**0.2%以下の確定だけ**。①の判断を決定づける |
| **「手で入れた休憩」との衝突は当面起きない** | 休憩を含む予定が30日で0件。自動と手動の区別（④）は**将来のため**の造りであって、今日の衝突を解くためではない。だから区別は軽く作ってよい |

> ★「過去30日に6件しか起きていないなら、やらなくてよいのでは」という読み方はしない。
> 240分（4時間連続）が2件ある。これは1人のトレーナーが休みなしに4時間施術した実績であり、
> **オーナーが問題視しているのはセッションの質**であって頻度ではない。頻度が低いことは
> 「導入してもほとんど誰も困らない」という**導入を後押しする事実**として読む。

## 3. 仕組みの前提（コードを読んで確認した事実）

### 3-1. 休憩ブロックの仕組みは完成している

`休憩` を含む予定をトレーナーのカレンダーに入れると、次の2か所が自動的に埋まりとして扱う。

| 場所 | 関数 | 挙動 |
|---|---|---|
| 空き枠の生成 | `コード.js` `buildAvailableSlots` | `_lbIsBusyTitle` が真 → `trainerReserved` に入り、吸着方式の空きブロックから引かれる＝空きが分断される |
| 予約の確定 | `LineBooking.js` `_lbCheckTrainerAvailable` | `_lbIsBusyTitle` が真 → `reserved` に入り、重なれば `notBooked=false` → `SLOT_TAKEN` |

**つまり③で新しく作るのは「休憩を書く部分」だけで、「休憩が効く部分」は既にある。**

### 3-2. 2つの判定が正しく働く（落とし穴1の検証）

新しいタイトルを `休憩（自動）` とした場合の、既存3判定の評価結果を追った。

| 判定（場所） | 結果 | なぜそれが正しいか |
|---|---|---|
| `isShiftEvent`（`コード.js`） | **false** | キーワード（出勤可能／出勤／シフト／available）を含まない。**出勤シフトと誤認されない** |
| `_lbIsBusyTitle`（`コード.js:227`） | **true**（`休憩` を含む） | 席を塞ぐ。空き枠が分断される＝**意図どおり** |
| `_lbIsSessionTitle`（`コード.js:241`） | **false**（`休憩` を含むので先に弾かれる） | 施術ではない。連続の数え方に影響しない＝**意図どおり** |

**評価順も確認した。** `buildAvailableSlots`（327行付近）と `consecutiveSessionsText`（1700行付近）は
どちらも `isShiftEvent` → `_lbIsBusyTitle` → `_lbIsSessionTitle` の順に見る。
`休憩（自動）` は1段目で落ち、2段目で埋まりになり、3段目でセッションから外れる。**狙った通りの3段通過である。**

この結果、**自動で入れた休憩が次の連続判定を汚さない。**
「セッション→自動休憩15分→セッション」は、`_consecRuns` では休憩が入らないため
**隙間15分＝しきい値ちょうど＝別の塊**になる（`_consecRuns` は `diff < gapMs` で畳むので、15分ちょうどは畳まれない）。
つまり **休憩を挟んだ時点で連続のカウンタが0に戻る。** これがオーナーの要望の本質（質の回復）に一致する。

### 3-3. だから「枠を落とす判定」は作らない

休憩が埋まりである以上、連続が成立した直後15分は**空き枠から自動的に消える。**
4本目を取ろうとした顧客は、15分後（＝休憩明け）の枠しか選べない。
そして15分後に取った4本目は、休憩で区切られているので**新しい塊の1本目**になる。

```
10:00-11:00 ①    ┐
11:00-12:00 ②    ├ 180分の塊が成立
12:00-13:00 ③    ┘
13:00-13:15 休憩（自動）  ← ここで書く
13:15-14:15 ④    ← 新しい塊の1本目（カウンタが戻る）
```

**オーナーの元の要望（3セッション終了後15分後から）が、副作用として完全に満たされる。**
`buildAvailableSlots` にしきい値判定を足す必要はない。**足さないほうがよい** ――
表示と確定の2か所に同じ判定を書くことになり、ずれたときに「画面に出るのに取れない」が起きる
（この種の事故は①の設計で既に1度踏んでいる）。

### 3-4. 連続の実測は再利用できる

`EdgeAudit.js` に純粋関数が揃っている。GASのグローバル空間なので `LineBooking.js` からそのまま呼べる。

| 関数 | 使い道 |
|---|---|
| `_consecRuns(intervals, gapMinutes)` | セッションの区間配列を「連続の塊」に畳む。`spanMinutes` が判定の軸 |
| `_consecWithSlot(runs, slotStart, slotEnd, gapMinutes)` | **この枠を入れたら塊が何分になるか。** ③の中核。既存の塊の前・間・後ろ、どこに挟まっても正しく判定する |

> ★`_consecWithSlot` が「前・間」も見ることは③にとって必須である。
> 11:00と12:00が既にあって10:00が入ると180分の塊ができる。
> 「直前が2連続か」だけを見る実装は、この入り方を取りこぼす。
> 既存関数はこれをテスト（`consec-sessions.test.js`）で固定済み。**自分で書き直さない。**

### 3-5. コードを置く場所（新ファイルを作らない）

**新しい `.js` ファイルは作らない。**
`.github/workflows/gas-deploy.yml` の押し出す対象の許可一覧に新ファイルを足すと**人間のレビューが必要**になり、

## 4. 設計

### ① いつ入れるか — 即時（同期）＋ 毎日1回の掃除

**結論：予約確定の中で同期的に書く。加えて毎日1回、掃除と取りこぼし回収のバッチを回す。**

#### 即時とバッチの比較

| | 即時（確定の中で書く） | バッチ（1日1回まとめて） |
|---|---|---|
| 3連続成立から休憩が入るまで | **0秒** | **最長24時間**。その間に4本目が入る |
| 予約の応答時間への影響 | 下記のとおり**実質ゼロ** | なし |
| `_lbReserveCore` を通らない経路（admin_hold・手動作成）の回収 | **できない** | **できる**（カレンダーを読むので経路を問わない） |
| 連続が崩れた休憩の掃除 | できない（キャンセル経路に別途必要） | **できる** |
| 失敗したときの再試行 | その場では不可 | **翌日自動で拾う** |

**どちらか一方では足りない。穴の性質が違う。**
即時は「成立の瞬間」を押さえ、バッチは「経路の抜け・崩れ・失敗」を拾う。**両方入れる。**

#### 「即時は遅くなる」への回答（API呼び出しの見積もり）

オーナーの最優先課題は予約確定の速度である。だから**何回APIを叩くかを数えた。**

現在の `_lbReserveCoreImpl`（LineBooking.js:3774〜）のカレンダー操作：

| # | 操作 | 種別 |
|---|---|---|
| 1 | `getCalendarById(CAPACITY_B1)` | 読み |
| 2 | `calB1.getEvents(start, end)` | 読み |
| 3 | `getCalendarById(trainer.email)`（`_lbCheckTrainerAvailable` 内） | 読み |
| 4 | `cal.getEvents(start, end)`（同） | 読み |
| 5 | `calB1.createEvent(...)` | **書き** |
| 6 | `getCalendarById(trainer.email)`（再取得） | 読み |
| 7 | `tcal.createEvent(...)` | **書き** |

**合計7回**（`LB_1F_TRAINER_BLOCK=on` ならさらに +2）。

③で増える分：

| 何を | 増える回数 | 理由 |
|---|---|---|
| 連続の判定に必要な予定の読み出し | **+0回** | `_lbCheckTrainerAvailable`（#3・#4）が**既にそのトレーナーのカレンダーを読んでいる。** 取得する時間の幅を広げるだけ＝**呼び出し回数は変わらない**（下記） |
| 休憩の書き込み | **+1回**（`createEvent`） | ただし**3時間連続が成立したときだけ。** 実測で月6件＝確定の0.2%以下 |
| 休憩のカレンダー取得 | **+0回** | #6で取った `tcal` のハンドルをそのまま使い回す |

**つまり平均で +0.002回、最悪ケースで +1回（書き込み1件・体感0.2〜0.4秒）。**
「いまの予約確定が既に遅い」という問題に対して、③は**ほぼ何も足さない。**

> ★ここが①の判断を決めた。「3連続のときだけ書く」という条件が付くので、
> 速度の負担は**実際に3連続を作った、その1人の顧客**にだけ掛かる。
> 全員の応答を遅くして穴を塞ぐ設計にはなっていない。

#### 読み出しの幅を広げる方法（既存関数を壊さない）

`_lbCheckTrainerAvailable(trainer, start, end, excludeStart)` は `cal.getEvents(start, end)` を呼ぶ。
連続を数えるには**その日の全体**が要る。そこで**任意の第5引数 `scan` を足す。**

```
_lbCheckTrainerAvailable(trainer, start, end, excludeStart, scan)
  scan を渡したとき … getEvents の範囲をその日の [00:00, 翌00:00) に広げ、
                      集めた shifts / busy / sessions を scan に詰めて返す
  scan を渡さないとき … いまと完全に同じ（範囲も戻り値も変わらない）
```

**判定結果が変わらないことの確認：**
- `onShift` は `start >= sh.start && end <= sh.end`（**包含**）。範囲を広げると包含しないシフトも配列に入るが、包含判定で落ちる → 結果は同じ
- `notBooked` は `start < r.end && end > r.start`（**重なり**）。遠い予定は重ならない → 結果は同じ
- `excludeStart` は開始時刻の完全一致。同一カレンダーで同一ミリ秒の開始は対象の予定だけ → 結果は同じ

**呼び出し元は2か所しかない**（`LineBooking.js:3835` の確定経路と `:6415` の `_lbPickBalancedTrainer`）。
`scan` を渡すのは**確定経路だけ。** `_lbPickBalancedTrainer` はトレーナーごとにループで呼ぶため、
**広げるとペイロードが3倍になる。渡さない**（挙動も変わらない）。

> ★なぜ「その日の全体」で、±4時間のような幅ではないのか。
> 営業は7:00〜24:00（`BUSINESS_START` / `BUSINESS_END`）で、連続が日をまたぐことはない。
> ±4時間だと9時間を超える連続で塊の終端を取りこぼし、**休憩を置く位置を間違える。**
> 日の全体なら営業時間内で取りこぼしがゼロになり、読み出し回数は変わらない。

#### 書く位置（確定フローのどこで）

```
… 残数チェック → B1競合 → トレーナー空き照合（ここで scan を受け取る）
  → B1カレンダー作成 → トレーナーカレンダー作成
  → recordReservationLine（★台帳コミット＝ここで予約は成立）
  → ★③ 自動休憩（try/catch・非致命）
  → 通知push（既に非致命）
  → return success
```

**台帳コミットの後に置く。** 理由は2つ。
1. 予約の成立を③の失敗で覆さない（§6落とし穴6）
2. 通知の前に置くと、将来トレーナー通知に「休憩を入れました」を足せる

### ② どこに入れるか — トレーナーのカレンダーだけ

**結論：トレーナーのカレンダーのみ。B1には書かない。**

「B1に書くのは間違いのはず」という読みは**正しい。コードで裏が取れた。**

| 根拠 | 場所 |
|---|---|
| `buildAvailableSlots` は B1の予定を**全トレーナーのbusyに合算**する（`busy = trainerReserved[id].concat(eventsB1)...`） | `コード.js:352` 付近 |
| `_lbReserveCoreImpl` は B1の重なりがあれば**トレーナーを問わず** `SLOT_TAKEN` を返す | `LineBooking.js:3820`付近 |

**つまりB1に15分の休憩を書くと、休んでいないもう1人のトレーナーの枠まで消える。**
顧客が選べるトレーナーは実質2名しかいないので、これは**空き枠を2名ぶん同時に削る**ことになる。
休憩はトレーナー個人のものであり、部屋の予約ではない。**B1には書かない。**

B1に書かないことの副作用も確認した。

| 気になる点 | 確認結果 |
|---|---|
| 請求（billing）が誤計上しないか | billingはB1の `[RESERVED]` / `[消化]` を見る。**B1に書かないので接触しない** |
| `syncExistingReservations` が予約として取り込まないか | 走査対象は **B1と1Fだけ**（`scanTargets`）。トレーナーカレンダーは読まない。**接触しない** |
| `_lbDeleteReservationEvents` が消してしまわないか | 顧客名での部分一致で消す。**休憩のタイトルに顧客名を入れない**ので一致しない（§6落とし穴10） |

#### タイトル

```
休憩（自動）
```

**アンダースコアを使わない。これは意図的な判断である。**

`_lbClassifyBooking`（`BookingRules.js`）は `_` で分割して3つ以上なら `種別_担当姓_顧客` と解釈する。
`休憩_自動_3時間連続後` と書くと **`種別=休憩` / `担当姓=自動` / `顧客=3時間連続後` として `parsed=true` になる。**
いまこの関数がトレーナーカレンダーを読む経路は無いが、将来1つ足された瞬間に
**休憩が予約として分類される**（担当姓が引けないので `blocksTrainer=false`、未知種別で `mode=other`＋`anomaly`）。

`休憩（自動）` は分割が1つなので `parsed=false` で確実に無視される。
**全角括弧にしておくだけで、将来の誤分類を構造的に封じられる。** コストはゼロなので、そうする。

staging では既存の慣例に合わせて `[TEST] ` を前置する（`_lbIsStaging()` が真のとき）。
`[TEST] 休憩（自動）` も `休憩` を含むので `_lbIsBusyTitle` は真。**判定は変わらない。**

### ③ キャンセルで連続が崩れたら — 消す（ただし遅延で）

**結論：自動で入れた休憩は、連続が崩れたら消す。ただしキャンセル処理の中では消さない。**

#### まず事実関係を押さえる

キャンセルは2種類あり、**どちらもトレーナーのカレンダーからセッションが消える。**

| | 無料取消（前日17:00まで） | 当日消化（それ以降） |
|---|---|---|
| 関数 | `_lbDeleteReservationEvents` | `_lbConsumeReservationEvents` |
| B1側 | 削除 | `[消化]` にリネーム（席は開放・請求に計上） |
| **トレーナー側** | **削除** | **削除**（実施されないため） |

**つまり当日消化でも、トレーナーのカレンダーからは ✅ が消える。**
連続の判定は `_lbIsSessionTitle`（＝トレーナーカレンダーの ✅）で行うので、
**どちらのキャンセルでも連続は崩れる。そしてトレーナーは実際にその時間が空いている。**

#### 消すか残すか

| | 消す | 残す |
|---|---|---|
| トレーナーの休息 | 連続が無くなったので不要。**「休息が失われる」ことにはならない** | 確保されるが、**根拠だった連続はもう存在しない** |
| 空き枠 | 無駄に減らない | **15分の穴が残り、吸着方式が空きブロックを分断する** |
| トレーナーの納得感 | 頼んでいない休憩が、根拠なく残り続ける状態を避けられる | **「なぜここに休憩があるのか」が誰にも説明できない予定になる** |
| 実装の重さ | 掃除の仕組みが要る | 不要 |

**消すほうを推奨する。決め手は3つ目である。**

残す側の「トレーナーの休息は確保される」という主張は、この場面では成り立たない。
キャンセルが起きた以上、トレーナーの1時間がまるごと空いている。**休息は既に確保されている。**
そこに15分の休憩を残すのは休息の確保ではなく、**由来を説明できない予定を増やす**ことである。

自動化の信用は「なぜそうなっているかを説明できること」で保たれる。
根拠が消えた休憩を残すと、トレーナーは次からこの仕組みの出力を信用しなくなり、
**手で消すようになる。そうなれば仕組みそのものが死ぬ。**

空き枠の損失そのものは小さい（15分の穴。吸着方式では「13:00開始の選択肢が消えて13:15開始になる」程度）。
だから**空き枠の損失は決め手にしない。信用を決め手にする。**

#### ただしキャンセル処理の中では消さない

キャンセル経路（`cancelReservationLine`）に掃除を足すと、次の問題が出る。

- キャンセルは `LockService` の中で動き、台帳の書き換え・カレンダー操作・通知を既に行っている。**ここにカレンダーの読み出しと削除を足すと、キャンセルが遅くなる**
- 1件のキャンセルが崩す塊は1つに限らない（変更で予定が動いた場合など）。**キャンセル経路に正しい掃除を書くのは、掃除バッチを書くより難しい**
- 顧客を待たせている処理に、**失敗したら何も起きないほうがマシな処理**を足したくない

**代わりに2つの経路で収束させる。**

| 経路 | いつ | 何をするか |
|---|---|---|
| **掃除バッチ** | 毎日1回 | 全トレーナー・地平の全範囲を読み、**いま成立している連続の直後15分**に該当しない自動休憩を消す |
| **次の予約確定** | そのトレーナー・その日に次の予約が入ったとき | 同じ日の自動休憩を再計算し、該当しないものを消す（読み出しは既に広げてあるので**追加の読みはゼロ**） |

**最長で24時間、根拠のない15分の休憩が残る。** これは許容する。
失うのは15分の開始選択肢1つであり、キャンセル自体の確実さと速度のほうが重い。

#### 消していいものの条件（誤削除を構造的に防ぐ）

**次の全部を満たすものだけ消す。1つでも欠けたら触らない。**

1. トレーナーのカレンダーの予定である（**B1は絶対に触らない**）
2. 説明欄に自動マーカー `auto_break：` がある（＝手で入れた休憩は対象外）
3. **開始時刻が未来**である（過去の予定は履歴なので触らない）
4. タイトルが正規の形（`休憩（自動）`／staging は `[TEST] ` 前置）と**完全一致**する
5. 長さが正規（15分）と一致する
6. **いま成立しているどの塊の直後15分にも該当しない**

> ★4と5が「トレーナーが受け入れた休憩を守る」仕掛けである。
> トレーナーが自動休憩を**動かした・名前を変えた・長さを変えた**場合、それは
> 「本人が自分の休憩として引き取った」と読む。**システムは二度と触らない。**
> 判定は正規形との一致だけで済み、追加の記録は要らない。

### ④ 自動と手動の区別 — 説明欄のマーカー

**結論：説明欄（description）に機械可読なマーカーを書く。タイトルは人が読むためのもの。**

既存の前例に乗る（`LineBooking.js:3863` / `:4196` / `makeBlock`）。

```
担当：鈴木 神海感留
auto_break：consec180
run：2026-10-05T10:00+09:00〜2026-10-05T13:00+09:00
対象：鈴木 神海感留(B)
作成：自動（予約確定 2026-10-02 14:05）
```

| 行 | 何のためか |
|---|---|
| `auto_break：consec180` | **自動と手動の区別の正本。** 削除判定と件数の集計はこの行だけを見る。`consec180` はしきい値の由来（将来120分に変えたら `consec120`）|
| `run：…〜…` | 根拠になった塊。後から「なぜこの休憩が入ったか」を人が追える |
| `対象：名前(ID)` | **⑤のために必須。** 既存の `deleteAdminSlot` は `desc.indexOf('(' + tr.trainerId + ')')` で「自分が作ったものか」を判定する。この書式に合わせることで、権限判定のコードを変えずに「自分の休憩だけ消せる」が成立する |
| `作成：自動（…）` | 人が見てすぐ自動だと分かる |

**顧客の氏名・customer_id は書かない。** 休憩は特定の予約のものではなく、塊全体に対応するものである。
3本の予約の誰の名前を書いても嘘になる。そして休憩の予定は**トレーナー本人以外にも見える**ので、
書かないほうが事故が少ない。`run：` の時刻だけで追跡は足りる。

**タイトルにも `（自動）` を入れる**理由：トレーナーはGoogleカレンダーのアプリで一覧を見る。
説明欄は開かないと見えない。**一覧で自動だと分かることに価値がある。**
ただし**削除判定はタイトルではなく説明欄で行う**（タイトルは人が変えられるため）。

### ⑤ トレーナーが消したいとき — 既存の管理画面に乗る（拡張が必要）

**結論：`listAdminSlots` / `deleteAdminSlot` に乗る。ただし両関数は今のままでは自動休憩を扱えない。**

**コードを読んで分かったこと（ここは見落としやすい）：**

```
listAdminSlots  （LineBooking.js:4220）… CALENDAR_IDS.CAPACITY_B1 だけを走査する
deleteAdminSlot （LineBooking.js:4243）… CAPACITY_B1 から getEventById する
```

**どちらもB1しか見ていない。** ②でトレーナーカレンダーにしか書かない以上、
**拡張しなければ管理画面には1件も出てこない。**

必要な拡張（3点）：

| # | 何を | どこ |
|---|---|---|
| 1 | `_lbAdminSlotKind(desc)` に3つ目の種別を足す（`auto_break：` があれば `'auto_break'`） | `LineBooking.js:4215` 付近 |
| 2 | `listAdminSlots` が**B1に加えてトレーナー3名のカレンダーも走査**し、`auto_break` だけを拾う | 同4220 |
| 3 | `deleteAdminSlot` が、B1に無ければ**トレーナーカレンダーからも探す** | 同4243 |

**読み出しの増加：管理画面で +3回。** これは予約確定の経路ではなく、
トレーナーが「枠の一覧」を開いたときだけ走る画面なので**許容する**（速度の最優先対象ではない）。

**乗ることで自動的に効く既存の守り**（書き足す必要がない）：

- 一般トレーナーは `desc.indexOf('(' + tr.trainerId + ')')` で自分のものだけ ← ④の `対象：名前(ID)` で成立
- オーナーは全部見える・消せる（`_lbIsOwnerRole`）
- **会員の本予約は絶対に消せない**（`_lbAdminSlotKind` が空なら `NOT_ADMIN_SLOT` で拒否）

**トレーナーが消した休憩が復活しないこと。**
削除後、同じ日に次の予約が入ると即時判定が走り、同じ塊に対して休憩を書き直す恐れがある。
**これを防ぐために「1つの塊につき1回だけ書く」を記録で担保する**（§4-⑦のログシート）。
冪等キーは **`トレーナーID + 塊の終了時刻`**。行があれば二度と書かない。

> ★このキーの選び方が②（同じ日に2回）も同時に解く。
> 塊が2つあれば終了時刻が2つ違うので、キーも2つ。**1日1回という制約がどこにも入らない。**
> そして3連続が4連続に伸びた場合は塊の終了時刻が変わるので、**新しいキー＝新しい休憩**になる。

### ⑥ 顧客にどう見えるか — 既存の `SLOT_TAKEN` そのまま

**結論：新しい文言は作らない。既存のトレーナー向け `SLOT_TAKEN` をそのまま使う。**

何が起きるかを正確に書く。

```
顧客Xが予約画面を開く → 13:00 の枠が見えている
   （この時点で ①②③ の3連続はまだ成立していない、または表示キャッシュが古い）
顧客Yが 12:00 を確定 → 3連続が成立 → 13:00-13:15 に休憩が自動で入る
顧客Xが 13:00 を送信 → _lbCheckTrainerAvailable が休憩と重なりを検出
   → SLOT_TAKEN「この時間帯は選択されたトレーナーが対応できません。」
```

**この文言（`LineBooking.js:3836`）が既にこの場面に正しい。**
部屋が埋まったのではなく、**そのトレーナーが対応できない**のだから、文言が事実と一致している。
（部屋側の `SLOT_TAKEN`「すでに予約が入りました」は B1競合用。こちらは使われない）

**新しい文言を作らない理由：**
- 「3時間連続のため休憩が入りました」と説明すると、**顧客にトレーナーの稼働状況を開示する**ことになる。店の内情を顧客に説明する必要はない
- 文言を増やすと4言語ぶん（日英簡繁）の翻訳が必要になる。②で確立した `LB_ST` の仕組みに乗る手間に対して、得るものがない
- **既存の文言で事実として正しい**

**頻度の見積もり：** 休憩が入るのは月6回。そのうち「ちょうどその直後の枠を、ほぼ同時に別の顧客が送信していた」
ケースだけが衝突する。**年に数回あるかどうか。** 既に同じ状況は普通の予約の競合で日常的に起きており、
顧客はこの文言を見慣れている。

**表示キャッシュとの関係も確認した。** `_lbReserveCoreImpl` は意図的に `invalidateCache()` を呼ばず、
`warmupCache`（10分ごと）に委ねている（体感短縮のため）。
**自動休憩も同じ扱いにする＝キャッシュを捨てない。** 表示の反映は最大10分遅れるが、
確定時の `_lbCheckTrainerAvailable` が確実に止めるので二重予約は起きない。**既存の予約と完全に同じ性質である。**

## 5. 設定値（Script Properties）

**すべて省略可。既定値はコード側に入れる。コード変更なしで変えられる。**

| キー | 既定 | 何を決めるか |
|---|---|---|
| `LB_AUTO_BREAK` | 未設定（＝無効） | `dry` で記録のみ／`on` で実書き込み。**これが安全装置の本体** |
| `LB_AUTO_BREAK_LIMIT_MIN` | `180` | 連続のしきい値（分）。**超えたら**休憩を入れる（`>` 判定。180分ちょうどでは入れない） |
| `LB_AUTO_BREAK_MIN` | `15` | 休憩の長さ（分） |
| `LB_AUTO_BREAK_GAP_MIN` | `15` | 連続とみなす隙間（分）。`_consecRuns` に渡す |

> ★`LB_AUTO_BREAK_MIN > LB_AUTO_BREAK_GAP_MIN` を**コード側で禁止する**（起動時に弾いて無効化し、ログに出す）。
> 理由は §6落とし穴9。この不変条件が崩れると、休憩が次のセッションに重なる。

> ★しきい値は `>` で判定する（`consecutiveSessionsText` の `span > LIMIT3` と同じ）。
> 180分**ちょうど**（60分×3本）では入れない、ではない ―― `_consecRuns` の `spanMinutes` は
> 10:00-13:00 なら180。`> 180` だと3連続で入らない。**`>=` にする。**
> 実測の「180分以上 6件」はこの数え方。**`>= LIMIT` で揃える**（`consecutiveSessionsText` の ① は `>=`、③ は `>` で
> 既にずれている。③の実装は `>=` に統一し、ずれをテストで固定する）。

## 6. 落とし穴

### 1. 自動休憩が次の連続判定に混ざらないか（★検証済み）

**混ざらない。§3-2で3つの判定を1つずつ追った。**

| | 期待 | 実際（`休憩（自動）`） |
|---|---|---|
| `isShiftEvent` | 偽（シフトではない） | **偽**（キーワードなし） |
| `_lbIsBusyTitle` | 真（席を塞ぐ） | **真**（`休憩` を含む） |
| `_lbIsSessionTitle` | 偽（連続に数えない） | **偽**（`休憩` で先に弾かれる） |

**この3つを `busy-title.test.js` に追加して固定する。**
既にこのファイルがあり、タイトルと期待結果の対応表になっている。**新しいタイトルを1行足すだけ。**

さらに `consec-sessions.test.js` に「自動休憩を挟んだ4本目が新しい塊になる」ケースを足す。
`_consecRuns` の `diff < gapMs` 判定（15分ちょうどは別の塊）に依存しているので、
**この境界が変わったら落ちるようにしておく。**

### 2. 同じ日に2回3連続が起きる（実測で発生済み）

実測の1日に `12:00〜15:00` と `15:30〜18:30` の2件がある。**この日は休憩が2件必要。**

**「1日1件」という制約をどこにも書かない。** 冪等キーを `トレーナーID + 塊の終了時刻` にすることで、
塊の数だけ休憩が入る。日付は冪等の軸に**しない。**

掃除バッチも同じ。「その日の自動休憩を1件探す」ではなく、
**「いま成立している全部の塊の直後15分」の集合と、「いまある自動休憩」の集合を突き合わせる。**

> 15:00〜15:15 の休憩と 15:30 の次の塊の関係も確認した。
> 休憩の終わり15:15から次のセッション15:30までは15分空く＝しきい値ちょうど＝別の塊。
> そして休憩自体はセッションではないので塊に入らない。**2つの塊として正しく数えられる。**

### 3. 振替・変更で予約が動いたとき（★二重に走らせない）

`changeReservationLine`（`LineBooking.js:6122`）は次の順で動く。

```
1. 旧行を changed に落とす（台帳）
2. _lbReserveCore(..., 'change') で新枠を作る   ← ★この時点で旧カレンダー予定はまだ残っている
3. 成功したら _lbDeleteReservationEvents で旧カレンダー予定を消す
```

**2の時点で旧予定がカレンダーに残っているのが罠である。**
10:00の予約を11:00へ動かすとき、12:00と13:00が既にあると、
**旧10:00も数えてしまい 10:00〜14:00＝240分の塊を誤検出する。**

**対処：`_lbReserveCoreImpl` は既に `exStart`（`body.excludeStartISO`）を持っている。**
`_lbCheckTrainerAvailable` がこれで旧予定を除外しているのと**同じ除外を、連続のセッション収集にも適用する。**
`scan` に詰める `sessions` から、開始時刻が `exStart` と一致する予定を落とす。
**`_lbCheckTrainerAvailable` の中で1回除外すれば、空き照合と連続判定の両方に効く。**

**二重に走らないこと：** `_lbReserveCore` の呼び出しは変更フロー全体で**1回だけ**。
よって③も1回だけ走る。`makeRecurringReservationLine` は N 回呼ぶが、
各回が別の日（週次）なので別の塊＝別のキーになり、二重にはならない。

**3の後の掃除：** 旧予定が消えることで、旧の位置にあった休憩の根拠が崩れることがある。
**キャンセルと同じ扱いで、掃除バッチと次の確定に任せる。** 変更経路に掃除を足さない。

### 4. トレーナー代行（`trainer_manual`）で入れた予約

**休憩を入れる。** オーナーの問題意識は「セッションの質」であり、
誰が予約を入力したかは**トレーナーの疲労と無関係**である。代行でも3時間連続は3時間連続。

`_lbReserveCore` を通る channel（`line` / `change` / `transfer` / `trainer_manual`）は**全部対象にする。**
**例外は `perf_test` だけ**（内部の計測。`_lbBookingGate` も同じ扱いにしている）。

**`_lbReserveCore` を通らない経路が2つある。これは即時では拾えない。**

| 経路 | 関数 | 即時 | バッチ |
|---|---|---|---|
| 未登録客の枠確保 | `makeAdminBooking`（`LineBooking.js:4180`付近） | **×** | **○** |
| ブロック（仮押さえ） | `makeBlock`（同4301） | × | ―（`ブロック` はセッションではないので塊に入らない。正しい） |

**`makeAdminBooking` が3連続を作るケースは即時では拾えない。**
これが**掃除バッチが「掃除」だけでなく「取りこぼし回収」も担う理由である。**
バッチはカレンダーを読むので、**どの経路で作られた予約かを問わない。**

> ★`makeAdminBooking` にも即時判定を足す案は採らない。
> `_lbAdminSlotGuard` はB1だけを見る設計（出勤シフト内外を問わない＝トレーナーの意図的な枠確保を許す）で、
> ここに連続の判定を足すと**「トレーナーが意図して押さえた枠」に自動で休憩が割り込む**。
> バッチなら翌日4:00にまとめて入るので、トレーナーが見てから消す余裕がある。

### 5. 体験90分が混ざる（★分で数える）

**分で数える。セッションの本数で数えない。**

| 組み合わせ | 塊の長さ | 180分以上か |
|---|---|---|
| 60 + 60 + 60 | 180分 | **はい** → 休憩 |
| 60 + 90 | 150分 | いいえ |
| 60 + 90 + 60 | 210分 | **はい** → 休憩 |
| 90 + 90 | 180分 | **はい**（2本でも） → 休憩 |

`_consecRuns` の `spanMinutes` は実際の予定の開始・終了から計算されるので、**本数を一切前提にしない。**
`parts`（セッション数）**をしきい値に使わない。**

**新しい枠の長さも実測で渡す。** `_lbReserveCoreImpl` は契約種別が体験なら
`TRIAL_SESSION_MINUTES`（90分）で `end` を作っている。**この `end` をそのまま `_consecWithSlot` に渡す。**
60分と決め打ちしない。

> ★`90+90=180` で2本でも休憩が入ることは、仕様として正しい。
> オーナーの原文は「3セッション（3時間）連続」だが、括弧の中が本質である。
> 問題は**連続した時間の長さ**であって本数ではない。

### 6. 書き込みが失敗したとき（★予約は絶対に巻き戻さない）

**予約を巻き戻さない。休憩なしで通し、記録に残す。**

「予約を巻き戻すのは顧客に最悪」という読みは正しい。
顧客にとって「予約が取れなかった」と「トレーナーの休憩が入らなかった」の重さは比較にならない。

**実装上の担保（既存の造りに乗る）：**

```
recordReservationLine（★ここで予約は成立）
  ↓
try { 自動休憩を書く } catch (e) {
   Logger.log（警告）
   auto_break_log に 結果=write_failed で記録
}
  ↓
通知（既に try/catch で非致命）
  ↓
return success
```

**③を `_lbReserveCoreImpl` の大きい try/catch の**外**には置けない**（同じ関数の中なので）。
だから**③を自前の try/catch で必ず包む。**
包み忘れると `catch (e)` に落ちて **`capEv.deleteEvent()` / `tEv.deleteEvent()` の巻き戻しが走り、
成立した予約のカレンダー予定が消える**（台帳には残る＝最悪の不整合）。

> ★これは③で最も危険な実装ミスである。**「③は必ず自前の try/catch で包む」をテストで固定する。**
> `Nudge.js` が「既存ファイルへの変更ゼロ」で済ませたのに対し、③は `_lbReserveCoreImpl` の中に手を入れる。
> **既存の巻き戻し機構に触る変更である**ことを忘れない。

**失敗したものは翌日4:00の掃除バッチが拾う。** `auto_break_log` に `write_failed` が残っていて、
かつ塊がまだ成立していれば、バッチが書く。**冪等キーの行は「書けた」ときだけ `created` を立てる。**

**失敗が続いた場合**：`dailyHealthCheck`（7:00）に「直近24時間の `write_failed` 件数」を足し、
0でなければ知らせる。既にこの関数は「悪化時だけメール」の造りになっている。

### 7. カレンダーAPIの呼び出しが増える（★見積もり済み）

**§4-① に表で出した。結論を再掲する。**

| | 現在 | ③導入後 |
|---|---|---|
| 予約確定1回の呼び出し数 | **7回** | **7回**（3連続が成立しない＝99.8%以上）／**8回**（成立したとき） |
| 連続の判定に必要な読み出し | ― | **+0回**（既存の `_lbCheckTrainerAvailable` の範囲を広げるだけ） |
| 平均の増加 | ― | **+0.002回** |

**掃除バッチの呼び出し数**：トレーナー3名 × 1回 = **3回**（`consecutiveSessionsText` と同じ読み方）。
1日1回なので日に3回。これは誤差。

**管理画面（`listAdminSlots`）**：B1の1回に加えてトレーナー3名で **+3回。**
予約確定の経路ではないので許容する。

> ★「読み出しの範囲を広げても呼び出し回数は変わらない」が③の速度設計の中核である。
> `getEvents(start, end)` を `getEvents(日の始まり, 日の終わり)` にしても、**APIを叩く回数は1回のまま。**
> 返るデータが1時間ぶんから1日ぶん（1トレーナーで数件〜十数件）に増えるだけで、転送量は無視できる。
> **新しい読み出しを足さずに連続を判定できる**ことが、即時方式を成立させている。

### 8. 管理画面の枠作成が休憩を無視する（★新しく見つけた穴）

`_lbAdminSlotGuard`（`LineBooking.js:4160`付近）は**B1の競合だけ**を見る。
出勤シフト内外も問わない（トレーナーの意図的な枠確保を許す設計）。

**つまり自動休憩が入っている時間に、管理画面から枠を作れる。**

これは**仕様として許す。** 理由：
- `makeAdminBooking` を使うのはトレーナー本人かオーナーである。**本人が自分の休憩に重ねると決めたなら、それは本人の判断**
- 自動休憩はトレーナーのカレンダーに見えているので、**知らずに重ねることはない**
- ここを塞ぐとシフト外の特別対応（翌月シフト提出前の先取りなど）ができなくなる

**ただし掃除バッチの判定には影響する。** 休憩に重なるセッションができると、
`_consecRuns` はその休憩を無視して前後を1つの塊に畳む（休憩はセッションではない）。
**結果として、より長い塊として検出され、その終端に別の休憩が置かれる。** これは意図どおりである。

### 9. 休憩の長さと隙間のしきい値の関係（★不変条件）

**`休憩の長さ ≤ 連続とみなす隙間` でなければ、休憩が次のセッションに重なる。**

いまは両方15分なので**休憩は必ずぴったり収まる。** 証明：

```
塊の終わりを E とする。E の後に次のセッションがあるなら、その開始は E + 15分以降
   （E + 15分未満なら同じ塊に畳まれているので、E は塊の終わりではない）
休憩は [E, E + 15分) → 次のセッションと重ならない
```

**この不変条件は設定で壊せる。** オーナーが後から「休憩は30分にしたい」と言った場合、
隙間が15分のままだと `[E, E+30分)` が次のセッション（E+15分開始）に重なる。

**対処（2段構え）：**
1. `LB_AUTO_BREAK_MIN > LB_AUTO_BREAK_GAP_MIN` のとき、**③を自動で無効化し、ログに理由を出す**（黙って壊れた状態で動かさない）
2. それでも重なる可能性に備え、**書く直前に「次の埋まりの開始時刻」で休憩を切る**（clip）。切った結果が0分なら書かず `skip_no_room` を記録

**シフトの終わりも同じ扱いにする。**
塊が退勤時刻ちょうどに終わる場合（実測の 17:00〜21:00 のような例）、休憩は**シフトの外**に出る。
シフト外には空き枠が無いので実害はないが、**トレーナーのカレンダーに意味のない予定が増える。**
→ **シフトの終わりで切る。切った結果が0分なら書かず `skip_outside_shift` を記録。**
（記録を残すので、毎日のバッチが何度も同じ判定を繰り返さない）

> ★この「切る」判定は純粋関数にする（`BookingRules.js`）。
> 入力＝塊の終わり／休憩の長さ／次の埋まりの開始／シフトの終わり、出力＝休憩の区間 or null。
> **Nodeでテストできる形にする。** カレンダーを読まないと確認できない形にしない。

### 10. 予約のキャンセル・変更が自動休憩を巻き込まないか（★検証済み）

`_lbDeleteReservationEvents` と `_lbConsumeReservationEvents` は、
**[start, start+60分) の範囲の予定のうち、タイトルに顧客名を含むもの**を対象にする。

| 検証点 | 結果 |
|---|---|
| 自動休憩のタイトルに顧客名が入るか | **入らない**（`休憩（自動）` のみ。④で氏名を書かない方針を決めた） |
| よって顧客名の部分一致にかかるか | **かからない。巻き込まれない** |
| 範囲が重なることはあるか | ある（13:00の予約をキャンセルすると [13:00, 14:00) を走査し、13:00-13:15 の休憩が範囲に入る）。**だが顧客名で一致しないので削除されない** |

**この安全性は「タイトルに顧客名を書かない」という一点に依存している。**
`cancel-events.test.js` に「自動休憩はキャンセルで消えない」を追加して固定する。
将来誰かがタイトルに会員名を入れた瞬間に落ちるようにしておく。

### 11. 掃除が「いま成立している塊」を取り違えると、入れたばかりの休憩を消す

掃除バッチは「成立している塊の直後15分」の集合を作り、それに該当しない自動休憩を消す。
**この集合の作り方を間違えると、正しい休憩を消してしまう。**

**集合の作り方を即時側と完全に同じにする。**
- 同じ `_consecRuns` / `_consecWithSlot` を使う（複製しない）
- 同じ `gap` / `limit` / 休憩の長さを使う（プロパティから読む・定数を2か所に書かない）
- **同じ「切る」純粋関数を通す**（シフト終わり・次の埋まりでの clip）

**切った結果と比較する。** 「塊の終わりの直後15分」ではなく、
**「切った後の休憩の区間」と一致するか**で判定する。そうでないと、
シフト終わりで切られて10分になった休憩を「15分と違う」として毎日消してしまう。

さらに**保険**として、`created` した休憩は**その日のうちは消さない**（`auto_break_log` の実行日時で判定）。
入れた直後に自分の掃除で消える事故を構造的に防ぐ。

### 12. 休憩が0件という実測が、導入後に意味を変える

実測で「`休憩` を含む予定は3名とも0件」だった。
**③を入れると、この数字が増える。** `consecutiveSessionsText` の
「`休憩` を含む予定の件数（シフトに休憩が入っているかの実測）」は
`title.indexOf('休憩') >= 0` で数えているので、**自動と手動を区別せず合算する。**

**対処**：`consecutiveSessionsText` の休憩カウントを **自動／手動に分けて表示する。**
分けないと、今後「トレーナーが休憩を使い始めたか」を測れなくなる
（自動が増えただけなのに、運用が変わったと誤読する）。

判定は説明欄の `auto_break：` で行う。**EdgeAudit.js の表示を1行足すだけ。**

## 10. オーナーの要望と現実の仕組みのズレ（私が気づいた点）

1. **「3セッション連続」は本数ではなく時間で判定される。**
   体験は90分なので `90+90=180分` の**2本**でも休憩が入る。
   オーナーの原文は「3セッション（3時間）」だが、括弧の中が本質だと解釈した。
   **2本で休憩が入るのは意図と違う、ということであれば言ってほしい。**

2. **「予約を断る制限」を別に作る必要がない。**
   休憩が埋まりとして扱われるので、連続終了後15分は自動的に予約不可になる。
   オーナーの元の要望（「15分後からしか予約できない」）は③の副作用として完全に満たされる。
   **制限と休憩は2つの機能ではなく、1つの機能である。**

3. **休憩は顧客に見えない。説明もしない。**
   顧客から見ると「その時間はトレーナーが対応できない」だけで、理由は伝わらない。
   トレーナーの稼働状況を顧客に開示する必要はないと判断した。

4. **過去30日に「休憩」を使ったトレーナーが1人もいない。**
   これは③が**誰の運用も壊さない**ことを意味する一方で、
   **トレーナーが休憩という概念をカレンダーで扱う習慣を持っていない**ことも意味する。
   自動で入り始めたとき「これは何か」と戸惑う可能性がある。
   **段1（`dry`）の後、段2に進む前に、トレーナー2名へ一言伝えることを勧める**（対外発信ではないので承認対象外だが、黙って入れるより摩擦が少ない）。

5. **未登録客の枠確保（`makeAdminBooking`）からできた3連続は、翌日まで休憩が入らない。**
   この経路は `_lbReserveCore` を通らないため即時判定が効かない。
   ここを即時にすると「トレーナーが意図して押さえた枠に自動で割り込む」ことになるので、
   **あえてバッチに任せた。** トレーナーが見てから消す余裕を残す設計である。

6. **③は `_lbReserveCoreImpl` の中に手を入れる、最初の変更になる。**
   ②（`Nudge.js`）は「既存ファイルへの変更ゼロ」で済んだが、③は予約確定の中核と
   既存の巻き戻し機構（`catch` 内の `deleteEvent`）に隣接する。
   **包み忘れると成立した予約のカレンダー予定が消える**（§6-6）。
   実装時はここに最大の注意を払う。レビューもここを最優先で見てほしい。
